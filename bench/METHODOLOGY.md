# JHYY 基准方法学

> 本篇是 `bench/` 那些数字的**唯一口径说明**。
> 读数字之前先读这里 —— 否则很容易把"jhyy 比 gcc 慢 2 倍"读成
> "jhyy 的代码生成差 2 倍"（**不是这个意思**，见 § 参照系）。

配套：[`README.md`](README.md)（怎么跑）· [`baseline/RESULTS-<日期>.md`](baseline/)（历次基线快照）
· [`docs/perf/`](../docs/perf/)（仓库层面的性能基线文档）。

## 1. 参照系

### 为什么只有 C

JHYY 是一门**系统语言**（自举 · 无 GC · 原生机器码 · 显式指针 · 可预期 ABI）。
它的对标系就是 C —— 不是 Python、不是 Node、不是 JVM。

**跟脚本语言比"跑得快不快"没有意义**：那测的是解释器启动开销，不是代码生成质量。
真要比，也得把"kernel warm"与"end-to-end"分开报，代价远大于收益。

### gcc `-O0` 是下限，`-O2` 是目标 —— 两个都报

| 参照 | 是什么 | 怎么用 |
|---|---|---|
| **gcc `-O0`** | 代码生成质量的**下限**。`--no-optimize` 的 gcc，产出的是"编译器不做任何优化"时该有的样子 | **主比值**。jhyy 的数字该跟它对齐 |
| **gcc `-O2`** | 用户体感的**目标**。社区反复打磨过的实现（内存池 / SIMD / 向量化 / 多线程） | **参照，不是及格线** |

⚠️ **`-O2` 不是及格线**。gcc 自己在这几道题上也不快多少
（见 [`docs/perf/self-backend-baseline-2026-10-29.md`](../docs/perf/self-backend-baseline-2026-10-29.md)）。
拿 `-O2` 当门槛会得到一个**连 gcc 自己都达不到**的数字。

⚠️ **两件事叠加会骗人**：JHYY 现在**没有任何优化开关**，且**寄存器分配未接线**
（每个 SSA temp 都物化成栈槽 ⇒ 机器指令里 49%~68% 是访存）。
⇒ **所有 jhyy 数字都是 `-O0` 级别的代码生成。**

## 2. 测量维度

| 维度 | 怎么测 | 是不是硬门 | 为什么 |
|---|---|---|---|
| **正确性** | jhyy 产物的 stdout 与 **gcc `-O0`** 产物的 stdout **逐字相同** | ✅ 硬门 | 确定性 |
| **静态指标** | 从生成的 `.s` 统计:指令数 / 访存指令数 / 帧大小 / `___chkstk_ms` 次数 | ✅ 硬门 | 「源码 × 编译器」的**确定性函数** ⇒ 逐字节相同 ⇒ 跨机器不漂 |
| **二进制体积** | 产物的字节数 | ✅ 硬门 | 同上 |
| **墙钟** | min / median / p95（warmup 1 次丢弃） | ❌ **只报告** | 共享 runner 的宿主负载不可控 —— 拿它当硬门只会制造假红 |
| **编译耗时** | `jhyy compile` / `gcc` 的墙钟 | ❌ 只报告 | 同上 |
| **测量地板** | 一个空程序从"被 harness 拉起"到退出的时间 | ❌ 只报告 | 见 § 3 |

## 3. 计时方法

### 为什么不用 `date +%s.%N`

本仓**实测过**：MSYS2 的 `date +%s.%N` 量 `sleep 1.0` 量出 **1.445~1.756 秒**
（误差 45%~76%）。旧的 `bench.sh` 用的就是它 ⇒ 它的历史数字不可信。

⇒ 本套件用 CPython 的 `time.perf_counter()`（→ Win32 `QueryPerformanceCounter`），
并且**直接从 Python 起进程**，绕开 MSYS2 bash 的 fork+exec 开销。

### 报分布，不报单次

每道题跑 **N 次**（默认 7，第一轮热身丢弃），报 **min / median / p95**。

- **比值用 min** —— 抗噪。
- **median / p95 一并列出** —— 只报 min 会把"运气好的一次"当成典型值；
  而 median 与 min 差得远，说明这台机器当时有负载，读者自己会判断。

⚠️ **墙钟的 run-to-run 波动可以很大**：同一台机器、同一份代码，两轮之间
`partial_sums` 的比值测到过 **2.77x ↔ 3.47x**（约 25%）。
⇒ **墙钟绝不进 CI 硬门**，也**不该被当成精确值引用** ——
它只说明"大概在什么量级"。

### 测量地板（measurement floor）

一个空程序（`fn main_jhyy() -> i32 { return 0; }`）从"被 harness 拉起"到退出的时间。

⚠️ **它含两层，不是一层**（实测，40 次采样）：

| 层 | gcc | jhyy |
|---|---|---|
| **harness 自己的进程创建开销**（Python `subprocess` + Windows `CreateProcess` + ucrt64 初始化） | ~19 ms | ~19 ms |
| **程序自己的启动开销**（jhyy 多出来的那层：C 运行时 shim） | — | **~6 ms** |

⇒ **jhyy 程序启动比普通 C 程序贵约 6ms**（25.5ms vs 19.3ms，分布很窄 ⇒ 真实差异，不是噪声）。
这是 C 运行时 shim 的代价：`GetCommandLineW` / `CommandLineToArgvW` / 编码转换 /
`setvbuf(_IONBF)`（见 `compiler/runtime/runtime.c`）。

⇒ **两个比值都要报**：

| 比值 | 是什么 | 用途 |
|---|---|---|
| **raw** | `(jhyy_min) / (gcc_min)` | **用户体感**：含启动开销，短程序会被压缩到 1 附近 |
| **扣地板** | `(jhyy_min - jhyy地板) / (gcc_min - gcc地板)` | **代码生成质量**：只比程序自身的工作 |

⇒ 表里还给出**地板占比**。占比 > 25% 的题会被标 `*` ⇒ **该题太短，比值不可靠**
（历史遗留的 `ack` / `nq` 就是这种：它们太短，跑起来的时间大部分是启动开销）。

### 冷启动只能近似

Windows 上不 drop 页缓存（非管理员做不到）⇒ "冷"只能用
**首次在一个全新临时目录里运行**近似。**这不是真正的冷缓存测量**，口径写明。

## 4. 题目设计规则

### 4.1 每个题目只打印一个 checksum

⚠️ **JHYY 产物的 stdout 是无缓冲的**
（`compiler/runtime/runtime.c` 的 `setvbuf(stdout, NULL, _IONBF, 0)` ——
该行的自陈注释："代价：每次 printf 一次 write 系统调用"）。

⇒ 任何大量输出的程序在 jhyy 上会退化成 **syscall 瓶颈**，
而 C 侧默认是全缓冲 ⇒ 拿"输出 megabytes"的题去比，
测的根本不是代码生成，是 syscall 次数。

⇒ **所有题目一律「内部算完，只打印一个 checksum」。**
这也顺带把 IO 从热路径里彻底拿掉了 ⇒ 题目不依赖 libc stdio。

### 4.2 checksum 是反死代码消除的锚

每道题的 `task.jhyy` 里有一句 `// CHECKSUM: <值>`，
`task.meta` 里也有同一个值。harness 断言它**出现在输出里**。

⇒ 现在还没有优化器，所以这条约定暂时是空的；但 **`-O1` 落地后它就有了牙齿**：
优化器一旦把整段计算吃掉，checksum 就会消失 ⇒ 门红。
**约定要在优化器存在之前立好**，否则到时候没人记得要加。

### 4.3 两个 twin 必须算法对等

同样的算法、同样的数据结构、同样的求值顺序。

⇒ 否则比的是"手调过的 C" vs "朴素 jhyy"，不是代码生成质量。
（gcc 的 `-O2` 实现被社区用内存池 / SIMD / 多线程反复打磨过，jhyy 侧是朴素实现 ——
这是**调优不对称**，见 § 5 第 4 条。）

### 4.4 浮点题按 IEEE-754 位模式比对

JHYY **没有浮点格式化器**（`std::fmt` 只有 i32/i64/hex）⇒ 不比十进制渲染。

**做法**：指针别名取位模式 ——
`let p: *u64 = &v as *u64; let bits: u64 = *p;`（**实测与 C 的 `memcpy`+`uint64_t` 逐字节相同**），
再用一个本地写的 `hex64` 打成 16 位小写 hex（C 侧 `printf("%016llx", bits)`）。

⚠️ **不能用 `std::fmt::fmt_hex_u32`** —— 它的 val 是 `i32`，循环是 `while v > 0`
⇒ **≥ 0x80000000 的值它输出空字符串**。

⚠️ **指针别名是实现行为、不是规范承诺**（规范 § 4.3 只说指针↔指针 `as` 可用，
没说"load 宽度由 pointee 类型决定"）⇒ 必须有回归用例锁住它。

⚠️ **字节一致性只与 gcc `-O0` 的产物比** —— `-O2` 可能**重排浮点运算**
⇒ `-O2` 的浮点结果**不参与逐字节校验**，它只是计时列。

⚠️ **两边必须调同一个 libm，且不开 `-ffast-math`**
（`sqrt` 在 x86-64 上是正确舍入的 ⇒ `sqrtsd` 与 libm 位模式一致；
但 gcc 的 `pow(x,1.5) → x*sqrt(x)` 改写只在 `-funsafe-math-optimizations` 下发生）。

### 4.5 ⭐ 浮点不能进变参调用

⚠️ **JHYY 不能给 C 变参函数传浮点** —— 实测 `printf("%f", x)` 输出 `0.000000` /
`6.95e-310` 这样的垃圾值。根因是 **JHYY 没有实现 MS x64 的变参约定**
（不置 `al` = XMM 个数，也不为 FP 实参做 GPR 副本）。

⇒ 本套件任何地方都不得把浮点放进变参调用。
（非变参的混合 FFI 是正确的 ⇒ `extern fn mix(a: i32, b: f64) -> f64` 不受影响。）

### 4.6 libc 依赖要逐题标注

`task.meta` 的 `libc` 字段写这道题有多少落在 libc 上：

| 值 | 含义 |
|---|---|
| `none` | 纯 JHYY 代码生成 |
| `libm` | 用到 `sqrt` / `pow`（走 libm） |
| `malloc` | 用到堆分配（走 libc `malloc`） |

⇒ **JHYY 产物链 ucrt64 libc**，`std::math` 与 `std::arena` 最终都落在 libc 上
⇒ 用到它们的题，**分数的一部分在测 libc**，不是 JHYY 的代码生成。
⇒ 表里逐题标注，并至少给出一道 `libc = none` 的题作对照。

## 5. 已知偏差清单

> 这一节是"对外发布"的核心成本。**写不清楚，数字就会被误读。**

1. **JHYY 没有任何优化开关** ⇒ 所有 jhyy 数字都是 `-O0` 级别的代码生成质量。
   ⇒ 头条结论只能是"代码生成质量 vs gcc `-O0`"。
2. **gcc `-O0` 与 `-O2` 都报**；`-O2` 是参照，**不是及格线**。
3. **JHYY 产物链 ucrt64 libc** ⇒ 用到 libm / malloc 的题**部分在测 libc**。
4. **调优不对称**：gcc `-O2` 的实现被社区反复打磨，jhyy 侧是朴素实现；
   且两个 twin 必须**算法对等** ⇒ 只报同一环境内的相对倍数，**不做跨语言排名**。
5. **JHYY 的 stdout 是无缓冲的** ⇒ 大量输出的程序会退化成 syscall 瓶颈
   ⇒ 本套件所有题目只输出一个 checksum。
6. **JHYY 不能给 C 变参函数传浮点** ⇒ 浮点只能比位模式（§ 4.5）。
7. **浮点位模式比对依赖指针别名**（实现行为，非规范承诺）⇒ 有回归用例锁住它。
8. **字节一致性只与 gcc `-O0` 的产物比** ⇒ `-O2` 可能重排浮点。
9. **跨机器绝对数字不可比**（Turbo Boost / 共享宿主噪声）⇒ 只报同环境相对倍数 +
   完整机器规格。
10. **微基准 ≠ 真实程序** ⇒ 必须同时给出**自举编译耗时**这条真实程序数据。
11. **测量地板**（harness 自身的进程创建开销 + jhyy 自己的启动开销）
    是所有数字的共同下限 ⇒ 必须公布；**jhyy 程序启动比普通 C 程序贵约 6ms**
    ⇒ 短程序上这个固定开销占比很大 ⇒ **表里标出地板占比，占比 >25% 的题比值不可靠**。
12. **冷启动只能近似**（Windows 上不能 drop 页缓存）。
13. **Windows-only** ⇒ ucrt64 + MSVCRT 的 `printf` 语义是平台相关的
    ⇒ 数字与 Linux/glibc 的数字**不可比**。
14. **反 DCE 约定**：每题固定 checksum，优化器吃掉计算即门红。
15. **题集有偏** ⇒ 几道微基准 + 一条真实程序数据，**不是**语言能力的完整画像。
16. **本套件测的是「代码生成」，不是「标准库」** —— 标准库的质量是另一根轴。

## 6. 复现

`bench/baseline/RESULTS-<日期>.md` 带完整机器规格（OS / CPU / gcc 版本 /
jhyy 版本 / 提交 sha / 运行次数）。

⚠️ **发布快照前确认机器空闲** —— 墙钟的 run-to-run 波动可达 25%（实测），
有别的进程在跑时同一份代码能测出完全不同的比值（实测 mandelbrot 在两轮之间
2.71x ↔ 1.48x）。`--publish` 会自动把采样次数提到 ≥15。

在**同一台机器**上跑 `python bench/bench.py --report`，
应当得到同一量级的相对倍数。
**跨机器的绝对数字不可比** —— 这是 Turbo Boost 与宿主噪声决定的，不是方法问题。

## 7. 静态指标基线绑定编译器版本

`bench/baseline/static.json` 与 `scripts/dev/bench/runtime_perf.baseline.json`
里的数字是**「源码 × 编译器」的函数** ⇒ 改后端就会变。

⇒ **改后端后必须重取基线**（`--update-baseline`），
⇒ **并在 commit / 基线文档里写明理由**（本仓既有规矩）。
⇒ 尤其：v4.4.x 的寄存器分配会改掉每一个 `.s` ⇒ 那之后基线必然要重取一次。
