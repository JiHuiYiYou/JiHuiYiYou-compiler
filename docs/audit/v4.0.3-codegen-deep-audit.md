## 1-iter RCA (per `feedback_rca_first_root_cause`)

3 W 都是同根因:**jhyy-side codegen per-function state management 索引语义错位 + alloc/formula pool 物理 disjoint 不保证**。3 个 W 是同一 root cause 的 3 个 surface symptom。

| W | 症状 | 3-W shared 根因 |
|---|------|------------------|
| W-072 (ex W-074.6) | v3 binary frame blow-up 484KB → SEGV | alloc pool 不 cover formula pool 高 local_max 路径;frame_size 公式错的 |
| W-097 | jhyy-side emit multi-field-access `* 8` operand swap | jhyy-side codegen const-fold/reassociation `*8` 跟 `-1` 嵌套时 drop operand;hoist 不全 cover |
| W-101 | emit_binop ceqw store clobber address-holder pointer r8=0 | alloc slot 跟 formula slot 物理 overlap,binop 写 formula slot clobber alloc'd address-holder pointer |

**W-101 root cause (具体):** `cg_alloc_slot` (state.jhyy:857-870) hardcodes `next_offset = -8192` on first call. For `parser__parse_expr` with `local_max=2060`:
- formula pool range: `[rbp-16520, rbp-32]` (formula `-(32 + (local_max+1)*8)` for local_t 0..local_max)
- alloc pool start: `-8192` (HARDCODED)
- **OVERLAP**: formula pool range `[-16520, -32]` ∩ alloc pool start `[-8192, ...]`. When alloc returns slot `-16512` (e.g., 8B pointer-slot near formula pool end), it conflicts with formula slot for local_t 2056 (`-(32 + 2056*8) = -16480`). When `emit_binop` writes formula slot for `ceqw` result temp, it clobbers the address-holder pointer → r8=0 SEGV.

**Per `feedback_codegen_amd64_multifn`:** 单 function 测试 PASS,2+ function 测试 fail — 因为只有大 fn (parser__parse_expr, 28-fn 28k tokens) 才有 high local_max;小 fn (e.g., 5-10 temps) 用 `-(32+t*8)` ≤ -80,跟 alloc start -8192 留 8KB gap,no overlap。

**W-101 fix attempt #1 RCA (REVERTED 2026-10-09 v4.0.2.7 wip):** 4 文件修改,关键错因 = `state.jhyy:854-907` 读 `per_fn_max[cur_fn_idx]` (在 body 路径 = function_index + 1) 当 current fn max,**正确索引 = `cur_fn_idx - 1` = function_index**。也 = 当前 fix attempt #1 引入 silent fail 因为 emit_func_header 跟 body 路径都用错索引 → frame_size 算法错。

**W-097 root cause (具体):** jhyy-side codegen 在 `ptr_add_u8(field_a, ((field_b - N) * 8))` 多层嵌套表达式时:
- const-fold 阶段: `((cur_fn_idx - 1) * 8)` 折成 `(cur_fn_idx * 8 - 8)` 或 `(cur_fn_idx * 8) - 1`
- imul emit 阶段: `imulq $8, %rax` (cur_fn_idx * 8) 后,sub `1` 没 emit 进 insn stream
- 实际: `mov $cur_fn_idx, %rax; imulq $8, %rax; (no sub $0x1, %rax)` → prev_pfm 读当前 fn 的 max,不读 prev fn 的 max → local_max 算错 → frame 484KB
- **已 ship fix:** hoist `(cur_fn_idx - 1) * 8` 到 explicit local var (emit_ctrl.jhyy:537-539, state.jhyy:1605-1607, emit_call.jhyy:181-184, emit_mem.jhyy:206-210)
- **未 ship (audit expansion 2026-10-09):** 25 sites 跨 10 src0/ 文件需要 verify hoist pattern (见 § 4)

**W-072 (W-074.6) residual 根因:** Stage 1 (jhyy.exe 编 main.jhyy) PASS per 3 sub-bug 真修;Stage 2 (jhyy_v2/v3 self-compiled) fail 同样根因 = W-101 + W-097 综合。fix attempt #1 v4.0.2.7 反而更坏(引入新 codegen bug,jhyy_v1 binary silent fail)。

### 维度 2: formula pool 跟 alloc pool 物理 disjoint

**Formula pool** (state.jhyy:806, 843, 845):
- formula = `-(32 + local_t * 8)` for local_t 0..local_max
- 范围: `[rbp - 32 - (local_max+1)*8, rbp - 32]`
- 例: local_max = 2060 → 范围 = `[rbp - 16520, rbp - 32]`

**Alloc pool** (state.jhyy:857-870, cg_alloc_slot):
- start = **hardcoded -8192** (init_off first call)
- advance = `next_offset - aligned` per alloc
- 范围: `[rbp - 8192 - per_fn_alloc - derived_count*8, rbp - 8192]`
- 例: per_fn_alloc = 4096, derived_count = 100 → 范围 = `[rbp - 17168, rbp - 8192]`

**物理 disjoint 分析 (per fn):**

| local_max | formula 范围 end | alloc 范围 start | gap | overlap? |
|-----------|------------------|------------------|-----|----------|
| 5 (小 fn) | `rbp-72` | `rbp-8192` | 8120 bytes | NO overlap ✅ |
| 256 (中 fn) | `rbp-2080` | `rbp-8192` | 6112 bytes | NO overlap ✅ |
| 1024 (大 fn) | `rbp-8224` | `rbp-8192` | -32 bytes (formula 越界 32) | **OVERLAP** ❌ |
| 2060 (parser__parse_expr) | `rbp-16520` | `rbp-8192` | -8328 bytes (formula 越界 8KB+) | **OVERLAP 大** ❌ |

**根因:** `cg_alloc_slot` start = `-8192` 是 v2.11.23 ship 时假设 `local_max ≤ 1024` 的 upper bound (formula end = `rbp-8224` 还在 alloc start 上方)。当 `local_max > 1020` (formula end ≥ rbp-8192),formula 跟 alloc 物理 overlap → 同 offset 处 alloc'd pointer 跟 formula slot 互相 clobber。

**Fix direction:** `cg_alloc_slot` init_off 必须 dynamic per fn:
```jhyy
// 在 emit_func_header 算完 local_max 后,把 init_off 写入 state
(*s).alloc_init_off = -(32 as i64) - (local_max + (1 as i64)) * (8 as i64) - (64 as i64);  // 64B gap safety

// cg_alloc_slot first call:
if (*s).next_offset == 0 {
    (*s).next_offset = (*s).alloc_init_off;
}
```

**frame_size 公式需同步改** (见 § 5)。

### 维度 3: address-holder 指针存储

**Alloc 流程** (codegen_amd64_emit_mem.jhyy:259 `emit_alloc`):
- emit `subq $N, %rsp` (per-alloc slot reserve)
- 写 result temp 的 slot offset via `cg_alloc_slot` (state.jhyy:857)
- 写 `temp_holds_address[result_id] = 1` (bitmap, v3.2.4 真修 256→1024→4096)

**Pointer load/store 流程** (emit_call.jhyy:1062 `emit_copy` + emit_mem.jhyy:389 `emit_store` + emit_mem.jhyy:635 `emit_load`):
- load: 若 `temp_holds_address[src_id] == 1`,emit `mov<size> (offset_holder), %reg` (indirect)
- store: 若 `temp_holds_address[dst_id] == 1`,emit `mov<size> %reg, (offset_holder)` (indirect)

**Clobber 风险分析** (per W-101 RCA):
- alloc result temp → temp_id 写入 alloc slot at e.g., `rbp-16512` (alloc pool start -8192 - 0 = -8192, advance by alloc_size → e.g. -8200, ... -16512)
- formula slot for some other local_t (e.g., 2058 = `-(32+2058*8)` = `-16496`) clobbers alloc'd pointer slot at `-16496` ←同 offset? 不, 这里是 alloc slot 在 -16512 跟 formula slot -16496 不一样 offset,但 alloc slot 在 alloc pool range (假设 -16520..-8192),formula slot 在 formula pool range (-16520..-32) — **fully overlapping**!
- 反向: alloc slot = -16512; formula slot for local_t 2058 = -16496 (差 16); formula slot for local_t 2057 = -16488 (差 24); etc. 实际**overlap 在 -16520..-8192 range**:
  - alloc slot 1: -16512 (advance -8200 from -8192)
  - alloc slot 2: -16520 (advance 8 from -16512)
  - 跟 formula slot for local_t 2056..2060 (offset -16480..-16512) **完全相同 offset**
- emit_binop ceqw 把 result 写回 local_t 2058 的 formula slot at -16496 → 但 alloc slot -16512 没有被它写,**如果** alloc'd pointer 实际存在 -16512,而 binop 写的 -16496 不是 alloc'd pointer,那 -16512 的 alloc'd pointer 没被 clobber
- **但**: W-101 1-iter RCA 说 `parser__parse_expr+54146` SEGV in `mov %eax,(%r8)` with r8=0 — r8 = address-holder pointer 来自 alloc result,**如果** r8 来自 alloc slot **被 emit_binop store 覆盖 clobber 为 0**,SEGV site 一致

**W-101 sub-mechanism 推测 (1-iter):** 当 alloc pool start = -8192,而 formula pool end = -16520 (for local_max=2060),**所有 alloc slot 都落在 formula pool 范围内**。emitter 任何写 formula slot 的指令(emit_binop step 5 final store via `cg_offset_for_temp_with_target` 走 formula fallback)都 clobber 某个 alloc'd pointer(无差别)。r8 拿到被 clobber 的 alloc slot 时是 0 → SEGV。

**Fix direction:** 修 alloc pool disjoint (维度 2) 后,alloc slot 移到 formula pool 下方(-16520 - 64 = -16584 起),formula 写不到了。但**也需 verify 维度 4 (W-097 hoist 全 cover)**。

### 维度 5: frame_size 公式正确性

**Current frame_size 公式** (emit_ctrl.jhyy:541-573):
```jhyy
let local_max: i64 = pfm_val - prev_pfm;  // current fn max - prev fn max
let mut frame_size: i64 = (local_max + 1) * TEMP_SLOT_BYTES();  // formula pool size
// alloc pool size
let alloc_pool_size = 8192 + pfa_v;  // 8192 base + per_fn_alloc
// 16-align
n = (frame_size + 15) & -16;  // Win
n = (frame_size + 15) & -16;  // SysV
```

**Bug 分析:**
- formula pool = `(local_max+1) * 8` 字节,从 rbp-32 向下
- alloc pool = `per_fn_alloc + derived_count*8` 字节,**预期从 -8192 起向下**
- **frame_size = max(formula_pool, alloc_pool)**,但:
  - formula pool 范围 = `[rbp - 32 - formula_pool, rbp - 32]`
  - alloc pool 范围 = `[rbp - 8192 - alloc_pool, rbp - 8192]`
  - frame_size 必须 ≥ 32 + formula_pool (即 formula pool 末端到 rbp) **AND** ≥ 8192 + alloc_pool (alloc pool 末端到 rbp)
  - 当前公式 `max(formula_pool, 8192 + alloc_pool)`:
    - formula_pool = (local_max+1) * 8
    - **错:** 应该是 `32 + (local_max+1)*8` (= formula pool 末端到 rbp-32 的距离) 而非 `(local_max+1)*8` (= formula pool 长度)
  - **后果:** local_max=10 → formula_pool=88, frame_size=88 → n=96(16-align)。但 formula pool 实际占 rbp-32 - rbp-120,frame 96B 不够 cover formula pool end at rbp-120 → 写 formula slot rbp-120 越界 96B frame → SEGV

**等下,verify:** 实际 main.jhyy regress 159/160 PASS 跟 Stage 1 jhyy.exe 编 main.jhyy OK,说明 frame_size 公式至少在 stage 1 是 work 的。让我重新推算:

- local_max=10 → formula `-(32 + 10*8) = -112` for local_t=10 → 最深的 formula slot at rbp-112
- frame_size = (10+1) * 8 = 88
- n = (88 + 15) & -16 = 96
- subq $96, %rsp → 栈顶 rbp-96
- 但 formula slot 最深在 rbp-112 → 写 rbp-112 越界 96B frame → 写栈外面 (stack outside frame) → 不 SEGV 因 Windows stack 通常 2MB → 数据可能 garbled 但不 crash

OK 所以 frame_size 公式 "math wrong but practically OK" 因 chkstk_ms 探测预留 4KB 边界,小 fn (local_max ≤ 1024) 即使 frame_size 实际不够 cover formula pool end,数据写到 4KB 探测区(GCC chkstk_ms 已 commit 4KB + 1 page),不 crash。但**写 garbled 数据** — 当 formula slot 在 stack 边界,可能跟 alloc slot 错位 → 高 local_max 路径 alloc 跟 formula 物理 overlap → W-101 真触发。

**Fix direction:** 正确 frame_size 公式:
```jhyy
let formula_pool_end_off = (32 as i64) + (local_max + (1 as i64)) * (8 as i64);  // formula pool 末端到 rbp 距离
let alloc_pool_end_off = (32 as i64) + (local_max + (1 as i64)) * (8 as i64) + (64 as i64) + per_fn_alloc;  // alloc pool 末端
let frame_size = max(formula_pool_end_off, alloc_pool_end_off);
```

**W-101 fix attempt #1 frame_size 公式错因 (REVERTED):** 用 `per_fn_max[cur_fn_idx]` (next fn max) 而非 `per_fn_max[cur_fn_idx-1]` (current fn max) → local_max 算法错 → frame_size 错。

### 维度 6: chkstk_ms probe 触发面

**触发条件** (emit_ctrl.jhyy:601-606):
```jhyy
if target_is_win(target_tag) == 1 && n > 4096 {
    movq $n, %rax;
    call ___chkstk_ms;
}
subq $n, %rsp;
```

**当前触发面** (per W-100/W-101):
- parser__parse_expr frame_size = 16520 → n = 16520 → 触发 ✅
- jhyy_v1 编 main.jhyy → v1 binary frame_size 应 < 4096 for v1 (小, ~200-500 temps)? 实际:  v1 编 main.jhyy emit 10MB .s, frame_size 看 jhyy-side codegen local_max → main.jhyy 28 fns, max local_max ≈ parser__parse_expr 2060 → frame_size ≥ 16520 → 触发

**Chkstk_ms 调用 ABI 顺序** (per emit_ctrl.jhyy:585-600 comment):
```

movq %rsp, %rbp
movq $N, %rax       <- set rax FIRST
call ___chkstk_ms   <- probe pages
subq $N, %rsp       <- allocate
```

**风险点:**
- 错误顺序:subq 先 → rsp 指向 uncommitted → call push return 触发 SEGV
- 当前 emit 顺序 ✅ correct (per W-074.6 sub-bug #3 真修 ship 2026-10-08 v4.0.2.1 wip)

**W-097 真修 ship 后 v4.0.2.5 (2026-10-09):** jhyy_v2 编 main.jhyy → emit .s 完整, main_jhyy label 出现,frame = 16520B, chkstk_ms 触发。但 Stage 2→3 closure 仍 SEGV per W-100 → W-101 (r8=0 NULL deref)。

**Chkstk_ms + alloc/formula overlap 关系:**
- chkstk_ms commit ≥ 4KB pages;rsp = rbp - frame_size ≥ rbp - 16520
- alloc pool range 实际是 `[rbp - alloc_end_off, rbp - alloc_start_off]`
- 当前 alloc start = -8192 hardcoded, alloc end ≈ -8192 - per_fn_alloc - derived*8
- 跟 formula pool 范围 overlap 在 `[rbp - max(formula_end, alloc_start), rbp - min(formula_end, alloc_start)]` = `[rbp - 16520, rbp - 8192]` (huge overlap)
- chkstk_ms 已 commit 这些 pages → 写 alloc slot 跟 formula slot 物理同 offset,**clobber** 必然发生
- W-101 SEGV site = r8 = 0 = alloc'd address-holder pointer 被 emit_binop store clobber 为 0 (因为该 pointer 写到 alloc slot 跟某个 formula slot 同 offset,binop store 写该 formula slot 时 clobber pointer)

**Fix:** 修 alloc pool disjoint (维度 2) → alloc pool 移到 formula pool 下方,no overlap → chkstk_ms commit 整个 range, 写 alloc/formula 都 no clobber。

```jhyy
fn cg_alloc_slot(state: *u8, size: i64) -> i64 {
    let aligned = (size + (7 as i64)) & ((0 as i64) - (8 as i64));
    let s = state as *CGState;
    // v4.0.3 (W-101 alloc pool disjoint 真修):alloc pool 起始 offset 动态
    // = -(32 + (local_max+1)*8 + 64) — formula pool 下方 + 64B gap safety。
    // emit_func_header 在算 local_max 后, 调 cg_state_set_alloc_init_off
    // 写入此值。cg_alloc_slot first call 用此值 (not hardcoded -8192)。
    if (*s).next_offset == (0 as i64) {
        if (*s).alloc_init_off == (0 as i64) {
            // safety fallback: legacy 8192 (pre-v4.0.3 binary compat)
            (*s).next_offset = (0 as i64) - (8192 as i64);
        } else {
            (*s).next_offset = (*s).alloc_init_off;
        }
    }
    let off = (*s).next_offset - aligned;
    (*s).next_offset = off;
    (*s).total_alloc = (*s).total_alloc + aligned;
    return off;
}
```

```jhyy
    formula_pool_end_off

    alloc_pool_end_off

    (frame_size + (15 as i64)) & ((0 as i64) - (16 as i64))
```
