## Sprint 详细

### v1.3.1 — `null` 关键字

**目标**: 引入 `null` 关键字作为 `0 as *T` 的语法糖。

**Why this matters**: src0/ 里 `0 as *u8` / `0 as *Node` / `0 as *Sym` 共 **659 处** (audit 2026-08-12),是 src0/ 最常见的单一模式。引入 `null` 后:
- `let p = 0 as *u8;` → `let p = null;` (sema 从上下文推断 `null` 的目标类型)
- 跟 `0 as *T` 完全语义等价 (零成本 — emit IL 都 emit `0`)

**端改动**:

| 端 | 改动 |
|----|------|
| lexer | 1 个新 token `null` (在 `compiler/src/lexer.c` / `compiler/src0/lexer.jhyy` 同时加) |
| parser | `null` → `NODE_INT_LIT(0)` + `type_ptr` 留 NULL (sema 阶段 infer) |
| sema | `null` 遇到 `*T` 上下文 → 自动 fill `type_ptr` (跟 `0 as *T` 现有路径镜像) |
| codegen | **不变** (NODE_INT_LIT 路径已支持 infer 后的 pointer emit) |

**Lang-spec 增量** (per `v1.3.8` 一次性):
- 新增 § `null` 关键字 — 描述为 `0` literal 在 pointer 上下文的 sugar,emit 相同 IL

**Scope 限制**:
- `null` 仅在 `*T` / `*u8` / `*Fn` 等 pointer 上下文合法,在 `i32` / `i64` 上下文应当**报错** (没有 `null` 整数)
- 跟 `0 as i32` 区分:`0 as i32` 合法,`null` 不合法 (语义不对)
- 不支持 `null + 1` 这种 arithmetic (null 不是数字)

**验证**:
- 反向测试: `let p = null; let q = *p;` → emit 跟 `let p = 0 as *u8; let q = *p;` byte-equal
- 拒绝测试: `let x = null;` (在非 pointer 上下文) → SemaError "[null] requires pointer type"
- regress.py 50/50 + regress_v1.py 50/50 持平
- Stage 1 byte-equal 7/7 持 (null 跟 0 as *u8 同一 emit)
- Stage 2 N=3 7 行 cascade 持

**实施步骤**:
1. lexer 加 `null` token (v0 端 + jhyy 端)
2. parser 识别 `null` → NODE_INT_LIT(0),type_ptr 留 NULL
3. sema 走 NODE_INT_LIT 现有路径,看到 type_ptr==NULL 且此时期望 *T → 自动 fill
4. 写 `null_basic.jhyy` 测试 (反向 / 拒绝)
5. 跑双 regress 50/50 + Stage 1 byte-equal 验证
6. src0/ 抽 10+ 处 `0 as *u8` → `null` 验证 (commit example,主提交保持原状)

**风险 / 守门**:
- sema infer 时如果 context 不是 pointer,`null` 应报错 → 跟现有 `0 as i32` 行为对比
- `null` 跟 `0 as *u8` emit byte-equal (Stage 1 验证) → 不影响 closure

**不动**:
- 不改 v0 C-side codegen emit (C 端已能 emit NODE_INT_LIT(0))
- 不改 ABI (`null` 是 source-level sugar,emit IL 一样)
- 不改 `0 as *T` 现有路径 (保持 backward compat)

**留给后续**:
- v1.3.8 lang-spec 增量章节

### v1.3.2 — `else if` 语法糖

**目标**: `if a { ... } else if b { ... } else { ... }` 语法糖替代 `if a { ... } else { if b { ... } else { ... } }`。

**Why this matters**: src0/ 里 `else {` 模式 (嵌套 if) 共 **350 处** (audit 2026-08-12)。引入 `else if` 后:
- 纯 parser sugar — `else if` desugar 成 `else { if ... }`,**不碰 sema/codegen**
- 0 风险,纯语法糖,不改 emit

**端改动** (最小):

| 端 | 改动 |
|----|------|
| parser | TOKEN_ELSE 后遇到 TOKEN_IF → 不要求 `{`, 直接开新 if parse (一行) |

**Lang-spec 增量**:
- § 控制流 — 加 `else if` 语法格式说明

**Scope 限制**:
- 只支持 `else if` (链式不支持 `else if ... else if ...` 二级以上? — 实际是支持的,递归 desugar)
- 不支持 `else if with {` 分开花括号 (强制同 `else if COND { ... }` 形式)

**验证**:
- 反向测试:`else if` 跟 `else { if ... }` 应当 emit 完全相同 IL
- regress.py 50/50 + regress_v1.py 50/50 持平
- Stage 1 byte-equal 7/7 持 (parser desugar 0 IL 影响)
- Stage 2 N=3 7 行 cascade 持

**实施步骤**:
1. parser 在 `parse_if` 函数的 else 分支检查:如果是 TOKEN_IF 直接 parse 内部 (不开 `{`)
2. 写 `else_if_basic.jhyy` 测试 (3 层嵌套 if)
3. 跑双 regress 50/50 + Stage 1 byte-equal 验证
4. src0/ 5+ 处 `else { if ... }` → `else if ...` 验证 (commit example)

**风险 / 守门**:
- 极低 — 但要 verify `else if` 跟 `else { if ... }` byte-equal (同 emit)
- 注意 `else if` 不能 split 在多行 (e.g. `else\n if ...` 应拒绝 — 跟 `else if` 同 token 区分)

**不动**:
- sema / codegen (完全不变)
- v0 C-side (跟 v1.3.1 同 — lang-spec 增量)

**留给后续**:
- v1.3.8 lang-spec 增量章节

### v1.3.3 — `sizeof` 内建函数

**目标**: `sizeof(TypeName)` 编译期常量表达式,替代 `type_size(*Type)` + 手写 cast。

**Why this matters**: **VariantDesc heap overflow 根因** (`v1.0-post-50-53-plan.md` § 4.3) — `VARIANT_DESC_SIZE` 手写 16 时已是错的 (真值是 24)。编译器知道所有类型的 size/layout,只是没暴露给用户。

src0/ 里现有直接 manual size 假设:
- `40 as i64` (IRVal struct size in phi_buf) — audit required
- `16 as i64` (CGContext 字段 offset) — 已知 (audit 2026-08-12)
- `32 as i64` (缓冲区 sret slot 容量) — audit required

**端改动**:

| 端 | 改动 |
|----|------|
| parser | `sizeof(TypeName)` → NODE_SIZEOF(TypeName) |
| sema | sema 阶段求值 → 替换成 NODE_INT_LIT (走 `type_size(*Type) -> i64`) |
| codegen | **不变** (NODE_INT_LIT 路径已有) |

**Lang-spec 增量**:
- § 内建函数 — 加 `sizeof` 描述 (只支持 type name,不支持 expression)

**Scope 限制**:
- 只支持 `sizeof(TypeName)` — `CGContext` / `IRVal` / `IRBuf` / `i32` / `[*]u8` 等
- **不**支持 `sizeof(*ptr)` / `sizeof(expr)` — 留给 v3.x 编译期 trait
- 类型必需是已 declared 的 (跟 `let x: T` 同样的 type-resolution 路径)

**验证**:
- 反向测试:`sizeof(CGContext)` 跟 `72 as i64` byte-equal (CGContext 已知 72 bytes)
- 拒绝测试:`sizeof(unknown_type)` → SemaError "unknown type"
- 拒绝测试:`sizeof(1 + 2)` → SyntaxError "sizeof requires type name"
- regress.py 50/50 + regress_v1.py 50/50 持平
- Stage 1 byte-equal 7/7 持 (const-fold 替换 NODE_INT_LIT)
- Stage 2 N=3 7 行 cascade 持

**实施步骤**:
1. parser 加 `sizeof` 关键字识别 (跟 `null` 同,1 token)
2. parser 解析 `sizeof ( TypeName )` → NODE_SIZEOF
3. sema 阶段:求值 NODE_SIZEOF → NODE_INT_LIT (i64, semantic const)
4. 写 `sizeof_basic.jhyy` 测试 (覆盖 5+ 类型)
5. 跑双 regress 50/50 + 1 处 `72 as i64` → `sizeof(CGContext)` 验证
6. src0/ 1-3 处 manual size 改 `sizeof` 验证 (commit example)

**风险 / 守门**:
- sema 求值复杂表达式时顺序 — 必须保证 declare 在 sizeof 之前 (跟现有 type-res 路径)
- 警惕 sizeof 在 array decay 路径的歧义 (e.g. `sizeof(T)` vs `sizeof(T[N])`) — 简化只看 type name

**不动**:
- codegen (const-fold 完就等同 NODE_INT_LIT)
- ABI (sizeof 在编译期,无 ABI 层)

**留给后续**:
- v1.3.8 lang-spec 增量章节

### v1.3.4 — `for x in slice` 语法糖

**目标**: `for x in arr` 替代 `for i in 0..len { let x = arr[i]; }`。

**Why this matters**: src0/ 现有 `for i in 0..len` 模式是典型 boilerplate。引入 `for x in slice` 后:
- sema 拿 slice 的 len,desugar 到 index loop
- codegen 跟 `NODE_FOR` 标准路径 + 自动 index + elem load

**端改动**:

| 端 | 改动 |
|----|------|
| parser | `for IDENT in expr` 语法 (新分支,跟 `for i in 0..N` 区分) |
| sema | 检查 expr type = `[*]T` → desugar 到 `for i in 0..len { let x = arr[i]; }` |
| codegen | **同 NODE_FOR**, 加自动 index + elem load (i_local 自动重命名避免冲突) |

**Lang-spec 增量**:
- § 循环 — 加 `for x in slice` 描述 (跟 v3.x iterator 区分,本 sprint 仅 slice)

**Scope 限制**:
- 只支持 `[*]T` 上下文 (slice) — 不支持 `for x in [T; N]` 数组 (后者用 `for i in 0..N`)
- 不支持 `for x in iter` (v3.x 有 iterator trait 时再做)
- 不支持 `for (i, x) in slice.enumerate()` (v3.x)

**验证**:
- 反向测试:`for x in arr` 跟 `for i in 0..len { let x = arr[i]; }` emit 比较 (应当 byte-equal 或仅 `i` 临时变量名不同)
- 拒绝测试:`for x in i32` → SemaError "expected slice type"
- regress.py 50/50 + regress_v1.py 50/50 持平
- Stage 1 byte-equal 7/7 持 (sema desugar 0 IR 影响)
- Stage 2 N=3 7 行 cascade 持

**实施步骤**:
1. parser 区分 `for i in 0..N` 跟 `for x in expr` (e.g. `..` 关键字检测)
2. sema `for x in expr` 路径:求 expr type → 必须是 `[*]T` → desugar 到标准 for 形式
3. codegen 现有 NODE_FOR 路径复用 (加 `i_local` 自动 var rename 避免冲突)
4. 写 `for_in_slice.jhyy` 测试 (含 3 元素 slice + 累加)
5. 跑双 regress 50/50 + Stage 1 byte-equal 验证

**风险 / 守门**:
- `i_local` 命名冲突 — 用 `for_i_<unique_id>` 形式避免
- Stage 1 byte-equal 在 user 测试文件 byte-equal,src0/ 中 0 处现有用法所以 0 干扰 ✅
- Stage 2 跨 src0/ byte-equal 持 (sema desugar 0 IR 影响在 src0/ 上)

**不动**:
- NODE_FOR 实现 (复用)
- v3.x range iterator / enumerate — 留给 v3.x

**留给后续**:
- v1.3.8 lang-spec 增量章节

### v1.3.5 — `#[inline]` attribute

**目标**: 在 fn 节点加 `#[inline]` attribute,codegen 在 callsite 内联 emit 函数体。

**Why this matters**: jhyy 无 forward ref,小 helper 函数 (e.g. `qbe_type_of` / `cg_body_returns`) 必须定义在所有 callsite 之前。`#[inline]` 变相解决 forward ref 限制:
- callsite 内联 emit → 不需要 fn 完整定义 (只要 AST 节点可见)
- **未来**: v3.x 加 return type fixpoint 后可去掉 forward ref 限制

**端改动** (中等):

| 端 | 改动 |
|----|------|
| parser | 识别 `#[X]` attribute (function-level,fn 前一行) |
| AST | fn 节点加 `is_inline` flag (i32 bool) |
| codegen | 对 `#[inline]` 函数不 emit call → 在 callsite 内联 emit 函数体 (递归探测,emit 一次) |

**Lang-spec 增量**:
- § 函数 — 加 `#[inline]` attribute 描述

**Scope 限制**:
- 不内联递归函数 (codegen 探测 call graph 时跳过)
- inline 函数必须在使用前定义 (仍是 jhyy 限制 — `#[inline]` 不解决 forward ref,只让 codegen 在 callsite 展开)
- 不支持 `#[inline]` 在 `fn` 之外的 node (e.g. struct field / const)

**验证**:
- 反向测试:`#[inline] fn f(x) -> i32 { return x + 1; } /* ... */ f(5);` 跟手写 `5 + 1` emit byte-equal (或仅 callsite inlined 后 inline 函数本体不再 emit)
- 拒绝测试:递归 `#[inline]` → 编译期 warning "[inline] recursive fn X not inlined" + 退化为 call
- regress.py 50/50 + regress_v1.py 50/50 持平
- Stage 1 byte-equal 7/7 持 (不引入 `#[inline]` 现有 src0/ 函数)
- Stage 2 N=3 7 行 cascade 持

**实施步骤**:
1. parser 识别 `#[attribute]` (在 `fn` 定义前) — 加 `parse_attributes` helper
2. AST fn 节点加 `is_inline: i32` 字段 (`compiler/src/ast.c` + `compiler/src0/ast.jhyy`)
3. codegen `cg_expr` 遇到 `is_inline` 函数时:把函数体的 AST 节点 emit 到 callsite (不是 call fn_name)
4. codegen 探测递归 (call graph walk) → 递归的 `#[inline]` 退化为 call + warning
5. 写 `inline_basic.jhyy` 测试 + 1 个 `qbe_type_of` 候选验证
6. 跑双 regress 50/50 + Stage 1 byte-equal 验证

**风险 / 守门**:
- **Stage 1 byte-equal 抖动**: `#[inline]` 改 codegen emit,即使 src0/ 中 0 个现行 `#[inline]` ,emitter 路径可能跟现有 inline 手写代码 emission 不同
- **守门**: src0/ 0 处 `#[inline]` 现有用法,Stage 1 byte-equal 应当 0 抖动。但要 5/5 PASS W-005 触发面
- **递归探测**: call graph 可能在 codegen 阶段不完整 (jhyy 编译时不知道所有调用),退化为"允许 inline,emit 跟 call 一样,然后 v0 linker warning" — 保守策略

**不动**:
- v0 C-side codegen emit (不改)
- 不支持 `#[inline]` on recursive (退化为 call + warning)

### v1.3.6 — `defer` 语句

**目标**: `defer fncall();` 替代 `goto cleanup` 模式。

**Why this matters**: src0/main.jhyy 里 `goto cleanup` 模式到处都是 (e.g. file open 错误路径)。Go 的 `defer` 是零成本的 cleanup 方案。

**端改动** (中等-高):

| 端 | 改动 |
|----|------|
| parser | `defer expr;` → NODE_DEFER(expr) |
| sema | 收集函数内所有 defer, 注册到 Func.defer_stack (i32 array of Node* ids) |
| codegen | 每条 return 前 emit defer stack (LIFO, 倒序执行) |

**Lang-spec 增量**:
- § 控制流 — 加 `defer` 语句描述

**Scope 限制**:
- **只**支持 `defer fncall();`,不支持 `defer { block }` (更复杂,留给 v3.x)
- defer 在 fn 内**任意位置**声明 (不要求紧跟 resource acquisition)
- defer 顺序:LIFO (最后声明的先执行)
- defer 在 fn 异常路径 (panic / longjmp) **不**支持 (jhyy 无 longjmp)

**验证**:
- 反向测试:`defer fclose(f);` 跟手写 `fclose(f); goto cleanup;` 跟现有 `goto cleanup;` 模式 emit 比较 (LIFO 顺序敏感)
- 警告测试:多个 defer `defer fclose(f); defer free(p);` → 验证执行顺序 `free(p); fclose(f);` (LIFO)
- regress.py 50/50 + regress_v1.py 50/50 持平
- Stage 1 byte-equal 7/7 持 (src0/ 中 0 个现行 `defer` 用法)
- Stage 2 N=3 7 行 cascade 持

**实施步骤**:
1. parser 加 `defer` 关键字 + `parse_defer_stmt`
2. sema 收集函数内 defer → Func.defer_stack (Node* array)
3. codegen `cg_return`:每条 return 前 emit defer LIFO 调用
4. 写 `defer_basic.jhyy` 测试 (3 layer defer + 异常路径)
5. 跑双 regress 50/50 + Stage 1 byte-equal 验证
6. src0/main.jhyy 1 处 `goto cleanup` → `defer ...` 验证 (commit example)

**风险 / 守门**:
- **defer 顺序敏感**: LIFO 倒序执行,跟用户预期一致 (跟 Go 一致)
- **return 路径多**: `NODE_RETURN` 可能有多个路径 (sret / 值 / void),每条都需 emit defer LIFO
- **codegen 改 emit 路径**: 跟 v1.3.5 一样,Stage 1 byte-equal 抖动风险 — src0/ 0 处现行 `defer` 用法, 0 干扰 ✅
- **5/5 PASS** 触发面回归 (W-005 / W-003 minimal repro)

**不动**:
- 不支持 `defer { block }` (v3.x)
- 不支持 defer 在循环 (v3.x)
- 不支持 defer 在多个函数返回 (只有直接 caller defer)

**留给后续**:
- v1.3.8 lang-spec 增量章节
- v3.x `defer { block }` / `defer in loop` 扩展

### v1.3.7 — Pattern binding + OR pattern

**目标**: `Some(v) => v` codegen 提取 payload + `Some(x) | Some(y)` 一致性检查。

**Why this matters**: 这是 v1.0.0 后续未完成项 (per `docs/internal/status.md` line 208-209):
> Pattern binding codegen (`Some(v) => v` 提取 payload) — v1.x post-50-53 patch
> OR pattern 一致性检查 (`Some(x) | Some(y)` 两边必须绑同名) — v1.x post-50-53 patch

**端改动** (高):

| 端 | 改动 |
|----|------|
| parser | `Some(v) => v` 中 `v` binding 已经是合法解析,sema binding 收集是 sema 阶段 |
| sema | pattern binding 收集 (e.g. `Some(v)` 把 `v` 绑定到 `T` payload 类型) |
| sema | OR pattern 一致性检查 (`Some(x) \| Some(y)` 两边必须绑同名 + 同类型) |
| codegen | `Some(v)` 构造时已 emit variant_id, codegen 提取 payload field 时用 local var `v` (symtab find) |

**Lang-spec 增量**:
- § 模式匹配 — 加 Pattern binding + OR pattern 描述

**Scope 限制**:
- Pattern binding **只**在 enum variant 的 payload 上下文 (e.g. `Some(v)` / `None`(no binding) / `Pair(a, b)` 2 binding)
- OR pattern 仅支持 enum variant (不支持 tuple / struct pattern)
- OR pattern 一致性: 两边**必需**绑同名 + 同类型 (e.g. `Some(x) | Some(y)` **必须** 一边 `x` 另一边 `x`,不能 `x` / `y`)

**验证**:
- 反向测试:`Some(v) => v` 跟手写 `match x { Some => x.payload }` emit byte-equal
- 一致性测试:`Some(x) | Some(x)` OK; `Some(x) | Some(y)` SemaError "OR pattern bindings must match: x != y"
- 类型测试:pattern binding `v` 在 body 里 type = variant payload type (e.g. `Some(i32)` → `v: i32`)
- regress.py 50/50 + regress_v1.py 50/50 持平
- Stage 1 byte-equal 7/7 持 (src0/ 现有 match 0 处用 OR pattern)
- Stage 2 N=3 7 行 cascade 持

**实施步骤**:
1. sema `sema_match_pattern`: pattern binding 收集 (per-arm,变量名 → type)
2. sema OR pattern 检查:提取每 arm 的 binding 集,验证 N 个 arm 集一致
3. codegen `cg_match_pattern`: payload 提取时,symtab lookup binding var → emit field load
4. 写 `pattern_binding.jhyy` + `or_pattern.jhyy` 测试
5. 跑双 regress 50/50 + Stage 1 byte-equal 验证
6. src0/ 现有 `match` 3-5 处试用新 pattern binding (commit example)

**风险 / 守门**:
- **Pattern binding type 推断**: payload type 推断需 traverse enum variant decl,sema 阶段需要 Symbol 完全 loaded
- **OR pattern 一致性**:需要 N-arm 全部 bind 同一组 var,实现细节需考虑 "OR 整体作为 1 个 arm" vs "每个 OR 子模式是 1 个 arm"
- **codegen 改 emit 路径**: 跟 v1.3.5/v1.3.6 一样,Stage 1 byte-equal 抖动风险 — src0/ 0 处现行 OR pattern, 0 干扰 ✅
- **5/5 PASS** 触发面回归 (W-005 / W-006 / W-007 minimal repro)

**不动**:
- 不支持 tuple pattern (v3.x)
- 不支持 struct pattern (v3.x)
- 不支持 nested pattern (e.g. `Some(Some(v))` 一层嵌套以上)v1.3 不支持

**留给后续**:
- v1.3.8 lang-spec 增量章节
- v3.x struct pattern / nested pattern / guard pattern
