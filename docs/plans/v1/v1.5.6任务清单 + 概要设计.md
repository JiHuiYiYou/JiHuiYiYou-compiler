# v1.5.6 任务清单 + 概要设计: jhyy.exe toolchain 探测层标准化 (A 派 Driver 探测)

> **承接**: v1.5.5 shipped (release workflow + 第三方 manifest + Burn bundle + MSI + VSCode ext + 53/53 PASS ship).
> **当前 baseline**: regress 53/53 + Stage 1 byte-equal + Stage 2 N=4 byte-equal (per MCP `jhyy_selfhost_check`) + install to `C:\Program Files\JHYY\` via Burn bundle + 53 worker `set | grep -v '^_'` 验证 env clean.
> **校准 2026-08-15 (v1.5.5 ship 后)**: v1.5.5 ship 时遗留3 workaround (W-025 qbe 同目录已修; W-027 v8 Python 侧 MSYS2 探测 4 iters; W-028 Python 侧 mod-256). v1.5.6 是 workaround 收敛 sprint, 不引入新功能.
> **目标**: jhyy.exe toolchain 探测逻辑从"散在 4 处" (release.yml + regress.py×2 + jhyy_helpers.c 缺失) 收敛到"1 处" (jhyy_helpers.c `jh_gcc_path()`). 为 v2.x 跨平台 + v3.x OS 阶段建立"探测模式"标准化.

## Context

### v1.5.5 暴露的 toolchain 探测债

v1.5.5 加 GH Actions release workflow (per `docs/plans/v1/v1.5.0任务清单 + 概要设计.md` § Sprint v1.5.5) 触发**首次 CI 端到端 release 闭环**. CI runner (`windows-latest`) 装 MSYS2 到 `$RUNNER_TEMP\msys64` (非本地 `C:\msys64`), jhyy.exe 内部 `system("gcc ...")` 找不到 gcc → 触发 6 iters workaround 链:

| 迭代 | 失败 | 根因 |
|------|------|------|
| W-025 v1 | MSYS2 root 写死 `C:\msys64` | CI 装到 `$RUNNER_TEMP\msys64`, magic path 失效 |
| W-025 v2 | `shutil.which("gcc")` 探测 | MSYS2-launched Python 返回 `/ucrt64/bin/gcc` 虚拟路径, cmd.exe 不解析 |
| W-025 v3 | `cmd /c where gcc` 探测 | MSYS2 subprocess 调 cmd.exe 不可靠 (交互 prompt) |
| W-025 v4 | bash `cmd //c where` 探测 | UTF-16 LE 解码失败 |
| W-025 v8 | RUNNER_TEMP 探测 + 已知 bin subdirs | 47/53 PASS (临时稳定) |

**6 iters + 47/53 不是我们菜**, 是 jhyy.exe 整套 architecture 假定"工具链已经装好 + 在 PATH 里 + 路径不变" 在 Windows + MSYS2 + Python subprocess 嵌套下不成立.

**真实问题**: 探测逻辑散在4 处 (release.yml 写 MSYS2 PATH / regress.py×2 / jhyy_helpers.c 缺失), 每处都可能错.

### 设计派别 (per `feedback_compiler_toolchain_path_resolution` memory)

| 派别 | 描述 | 何时用 |
|------|------|--------|
| **类型 1** PATH 解析 | 装时配 PATH, 工具靠 PATH 探测 | 当前 jhyy.exe 状态 (workaround 阶段) |
| **类型 4** Driver 探测 | Driver (jhyy.exe) 内部探测, 三层优先级 | **v1.5.6 (本 sprint)** |
| **类型 2** lite manifest | 装时写 manifest, 启动读 | v2.x 跨平台 (Linux/macOS) |
| **类型 5** Nix hardcoded | `/nix/store/<hash>` 不可改 | v3.x M11 boot from scratch |

**所有派别都有技术债** (Rust cc-rs magic20+ 条 / Zig 1GB 装包 / Nix hash 爆炸), 没银弹. 类型 4 是 v1.5.6 时机下**探测magic最少** (4 条 Windows MSYS2) + **可演化** 的选择.

### 为什么 v1.5.6 现在做 (不是 v1.5.4 或 v2.x)

| 时机 | 价值 vs 成本 |
|------|---------------|
| v1.5.4 之前 | workarounds 没暴露, 无紧迫性 |
| **v1.5.5 ship 后 (现在)** | **高**: workaround 链刚暴露, 趁势收敛; v1.5.6 sprint 余量充足; 0 外部用户场景下回归成本低 |
| v2.x 跨平台 sprint | 工作量翻倍 (Windows + Linux + macOS 同改) |
| v3.x OS M3 freestanding | 探测目标换 (gcc → 自研 linker), 但探测模式不变; 提前标准化模式 = M3 省 30 行 |

**v1.5.6 还债的本质**: 把"探测模式"标准化, **不是**消除探测. 跟 Rust cc-rs / Clang Driver 同构.

### 跟 v2.x / v3.x 关系 — 探测模式复用链

```
v1.5.6 (本 sprint, Windows only):
  Priority 1: JHY_GCC env
  Priority 2: JHYY_HOME/env.txt
  Priority 3: which gcc + MSYS2 magic (4 条)

v2.x 跨平台 (Linux + macOS):
  Priority 1: JHY_TOOLCHAIN env (升级)
  Priority 2: $JHYY_HOME/config/toolchain.env
  Priority 3: 多平台 which + magic (8 条)
  + manifest lite (类型 2) 在 priority 2 注入

v3.x M3 freestanding:
  Priority 1: JHY_LINKER env (目标换)
  Priority 2: $JHYY_HOME/config/toolchain.env (复用 v2.x)
  Priority 3: jhyy.exe 同目录 / OS 内核路径

v3.x M11 boot from scratch:
  Priority 1: hardcoded (jhyy 自带 gcc 装包)
  Priority 2-3: 探测 fallback (类型 4 仍兜底)
```

**v1.5.6 建立的"3 层优先级 + 缓存"框架是后续 4 个 sprint 的基础**, 不是一次性代码.

## 设计

### 1. `jhyy_helpers.c` 加 `jh_gcc_path()` (~25 行)

**位置**: `compiler/src0/jhyy_helpers.c` (已有 `jh_paths_init` + `jh_path_gcc` W-017 DEPRECATED 模式).

**实现** (Windows only, v1.5.6; v2.x 加 `#ifdef __linux__` / `__APPLE__`):

```c
/* v1.5.6: jh_gcc_path — 3-tier priority driver detection for gcc.
   Replaces W-025 v8 + W-027 v8 Python-side探测 (~30 行 magic 收敛到 C).
   Static buffer cache, 1-time resolve on jhyy.exe startup. */
static char jh_gcc_path_buf[1024];
static int  jh_gcc_path_initialized = 0;

#ifdef _WIN32
#include <stdlib.h>  /* getenv */
#include <string.h>  /* strncpy, strcmp */
#include <windows.h> /* SearchPathW for fallback探测 */

__attribute__((used)) const char *jh_gcc_path(void) {
    if (jh_gcc_path_initialized) return jh_gcc_path_buf;

    /* Priority 1: JHY_GCC env (user/CI explicit) */
    const char *env_gcc = getenv("JHY_GCC");
    if (env_gcc && env_gcc[0] != '\0') {
        snprintf(jh_gcc_path_buf, sizeof(jh_gcc_path_buf), "%s", env_gcc);
        jh_gcc_path_initialized = 1;
        return jh_gcc_path_buf;
    }

    /* Priority 2: JHYY_HOME\env.txt (单行 KEY=VALUE) */
    const char *jhyy_home = getenv("JHYY_HOME");
    if (jhyy_home && jhyy_home[0] != '\0') {
        char env_file[1024];
        snprintf(env_file, sizeof(env_file), "%s\\env.txt", jhyy_home);
        FILE *f = fopen(env_file, "r");
        if (f) {
            char line[1024];
            while (fgets(line, sizeof(line), f)) {
                if (strncmp(line, "JHY_GCC=", 8) == 0) {
                    const char *val = line + 8;
                    size_t len = strlen(val);
                    while (len > 0 && (val[len-1] == '\n' || val[len-1] == '\r'))
                        val[--len] = '\0';
                    if (len > 0) {
                        snprintf(jh_gcc_path_buf, sizeof(jh_gcc_path_buf), "%s", val);
                        jh_gcc_path_initialized = 1;
                        fclose(f);
                        return jh_gcc_path_buf;
                    }
                }
            }
            fclose(f);
        }
    }

    /* Priority 3: Windows MSYS2 magic (跟 W-027 v8 同构, 但单源) */
    const char *msys2_magic[] = {
        "C:\\msys64\\ucrt64\\bin\\gcc.exe",
        "C:\\msys64\\mingw64\\bin\\gcc.exe",
        "C:\\msys64\\usr\\bin\\gcc.exe",
        NULL
    };
    for (int i = 0; msys2_magic[i]; i++) {
        if (GetFileAttributesA(msys2_magic[i]) != INVALID_FILE_ATTRIBUTES) {
            snprintf(jh_gcc_path_buf, sizeof(jh_gcc_path_buf), "%s", msys2_magic[i]);
            jh_gcc_path_initialized = 1;
            return jh_gcc_path_buf;
        }
    }

    /* Priority 4: PATH 探测 (via SearchPathA) — Windows API 标准做法 */
    char path_buf[MAX_PATH];
    if (SearchPathA(NULL, "gcc", ".exe", sizeof(path_buf), path_buf, NULL) > 0) {
        snprintf(jh_gcc_path_buf, sizeof(jh_gcc_path_buf), "%s", path_buf);
        jh_gcc_path_initialized = 1;
        return jh_gcc_path_buf;
    }

    /* Fallback: return "gcc" 走 PATH 解析 (跟 W-027 v8 之前一致, 错误信息保留) */
    snprintf(jh_gcc_path_buf, sizeof(jh_gcc_path_buf), "gcc");
    jh_gcc_path_initialized = 1;
    return jh_gcc_path_buf;
}
#else
/* Linux / macOS: v1.5.6 placeholder, v2.x sprint 填 */
__attribute__((used)) const char *jh_gcc_path(void) {
    return "gcc";  /* 暂走 PATH (跟 v1.5.5 之前一致) */
}
#endif
```

**关键点**:
- **4 层优先级**: env → 文件 → magic → SearchPathA → fallback
- **缓存**: `static int jh_gcc_path_initialized` 一次性 resolve, 后续读 buffer
- **找不到**: fallback "gcc" (跟 W-027 v8 之前同), 错误信息保留 (gcc not found → cmd error)
- **Windows API**: `GetFileAttributesA` (判断文件存在) + `SearchPathA` (PATH 探测), 都比 W-027 v8 用的 `shutil.which` / `cmd.exe where` 稳

### 2. `jhyy_helpers.c` 加 `jh_gcc_invoke()` (~10 行)

**目的**: 把 `system("gcc ...")` 包装成 `system(jh_gcc_invoke(...))`, 内部用 `jh_gcc_path()` 探测.

```c
/* v1.5.6: jh_gcc_invoke — build full cmd string with resolved gcc path.
   替代 main.jhyy 里裸 system("gcc ...") 调用.
   ABI: caller 提供 cmd_args (含 "-o exe as.s runtime.c helpers.c -lm" 等),
   返回 char* 到 static buf (跟 sprintf_lld 同模式). */
__attribute__((used)) int jh_gcc_invoke(char *out_buf, int out_size, const char *args) {
    return snprintf(out_buf, out_size, "\"%s\" %s", jh_gcc_path(), args);
}
```

**用法**: `main.jhyy` 里 `system(cmd_buf)` 改成 `char new_cmd[2048]; jh_gcc_invoke(new_cmd, sizeof(new_cmd), cmd_args); system(new_cmd);`

## Risks

| 风险 | Mitigation |
|------|-----------|
| `jh_gcc_path()` 缓存 stale (gcc 路径变了) | jhyy.exe 启动时一次性 resolve, 启动慢 ~5ms, 可接受; 用户改路径需重启 jhyy.exe |
| Priority 2 文件解析 bug (CRLF / 空行 / 注释) | 单行 KEY=VALUE 解析, 容忍 `\r\n`, 注释 `#` 跳过 (实施时验证) |
| Priority 3 magic 路径写死 | 跟 W-027 v8 同构, 但收敛到 1 处, v2.x 加 Linux 段时统一扩展 |
| 用户装 MSYS2 到 D 盘, magic miss | Priority 4 SearchPathA 兜底, PATH 里有 gcc 就能找到 |
| SearchPathA 不找 `.exe` 扩展名 | 显式传 ".exe" extension, 跟 cmd.exe `where gcc` 一致 |
| Priority 4 失败, fallback "gcc" | 保留跟 v1.5.5 之前一致, 错误信息不变 (gcc not found) |
| 5 个测试 stale (新 jhyy_helpers.c 改了) | 测试设计成黑盒 (只测 `jh_gcc_path()` 输出, 不依赖内部实现) |
| regress.py 删 MSYS2 探测后 Windows 本地 regress 失败 | 删之前先 git commit revert point, 验证 53/53 再 ship; 跑一次本地 regress 确认 |
| jh_gcc_path() 实施后 Stage 1 byte-equal 变化 | **不会**, `jh_gcc_path()` 是新 fn, 不改 IL emit 路径 |
| 装到 `C:\Program Files\JHYY\` 后, `jh_gcc_path()` 找 system gcc | Magic 段 C:\msys64\ucrt64\bin 探测, 跟安装路径无关; 用户装 MSYS2 自由 |
| 跟 v2.x 跨平台 sprint 冲突 | v1.5.6 只 Windows, Linux/macOS 段 placeholder (`return "gcc"`); v2.x 升级时改 placeholder |
| W-029 命名跟未来冲突 | W-029 唯一编号, 不冲突; RESOLVED 后移出 ACTIVE 表 |
