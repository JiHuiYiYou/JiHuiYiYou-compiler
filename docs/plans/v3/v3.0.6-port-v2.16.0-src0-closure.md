### W-086-fix — (b)+(c) one commit 真修 + Gate-0 灯转绿 📋 ⏳ critical

**Why (b) → (c) → (a) (one commit, NOT 顺序分步)** (per 用户 2026-09-23 反馈):
- (a) 原写法 "int_val/text_len 选一个" **根本不成立**。**binop 语义 = dst = op(lhs, rhs) 需要 3 个 operand slots**, 当前 ILToken (codegen_amd64_state.jhyy:81-88) 只有 `int_val` + `text_len` 两个 8B 字段 = 16B payload, **字段数根本不够**。emit_binop 拿 `int_val` 当 dst_id 之后, lhs/rhs 没地方放 → 塌缩成由 dst_id=0 推导出的固定偏移 (-32(%rbp)) — **所有 binop 写 -32(%rbp) 就是这个塌缩的实证**。
- **正确顺序 (用户反馈)**: (b) 先做 → (c) 做 → (a) 自然成立
  - **(b) lexer consume operand for ALL token kinds**: `'%'` LHS handler 写 dst_id 到 token.dst; next_token_binop consume lhs + rhs 写 token.lhs/token.rhs; next_token_copy consume src 写 token.src; next_token_conv consume src (existing partial); next_token_call args (existing partial)。**这是"从全 0 到有真值"的开关, 必须先做** — 单独做完 (c) token 扩字段, 但 lexer 仍不写 → 字段值仍 default 0 → 行为跟现状一样 (still broken)。
  - **(c) 扩展 ILToken 到 3-operand capacity**: 加 `dst: i64` + `lhs: i64` + `rhs: i64` 字段 (3 × 8B = 24B operand payload), 加 `op_flags: i32` 标记 IMM/TEMP 区分 (3 operand × 1 bit = 3 bits, pack 进 op_flags)。emit_* 全部按 dst/lhs/rhs 读 + 按 op_flags 决定 IMM vs TEMP 路径。**删 L4 § 4.3 1-to-1 简化** (假设单槽正是这个 bug 的 root cause — 1-to-1 简化允许只用 2 字段凑合)。**删 1-to-1 简化 = 同一个改动的另一面** (per 用户反馈), 所以 (c) 必须包含这俩 substep。
  - **(a) 字段约定统一作废 — 不需要单独 commit**: (b)+(c) 一起做完, emit_copy/binop/conv/call 全部按 dst/lhs/rhs 读, 冲突自然消解。先做 (a) 等于白做一遍。
