## 为什么单独立这份文档

jhyy_OS 的 capability-based 安全模型（独立 repo 设计中）需要在**两个层面**落地：

| 层 | 落地位置 | 作用 |
|----|----------|------|
| **OS 内核** | jhyy_OS 内核态代码 | capability 表（cnode）管理、revocation 协议、内核对象生命周期 |
| **语言类型系统** | jhyy 编译器（**本文档**）| `Cap<T>` 编译期保证：不可伪造、不可复制、不可类型混用 |

只有内核层 + 语言层双重保障，capability 安全才能在编译期 + 运行期都正确。如果只靠内核层（裸 `u32` 表示），用户代码一个 `as` 就绕过；如果只靠语言层（编译期检查但运行时无支持），运行时撤销做不到。

**v1.x 阶段锁定 spec，v3.x 实现**：
- v1.x 锁定 spec：~50 行 spec 文本，成本低（不写编译器代码，只写规范）
- v3.x sprint 3g 实现：跟 `&mut + lifetime` 联动，是大特性，单独 sprint

## 概念模型

### Capability 是什么

Capability = **对一个受保护对象的不可伪造引用**。传递 capability = 授权访问。

jhyy_OS 中：
- **物理页** = capability 持有 → 可读写该页
- **进程** = capability 持有 → 可控制该进程
- **I/O 端口** = capability 持有 → 可读 / 写该端口
- **设备** = capability 持有 → 可驱动该设备
- **IPC 端点** = capability 持有 → 可发送 / 接收消息

### 为什么需要语言层

裸 `u32` capability 索引：

```rust
let cap: u32 = kernel_alloc_page();   // 拿到物理页 capability
let evil: *u8 = cap as *u8;           // 绕过！裸指针 + 用户代码能伪造任意 capability
```

`Cap<T>` phantom type 在编译期阻止这种绕过：

```rust
let cap: Cap<Page> = kernel_alloc_page();
let evil: *u8 = cap as *u8;           // sema 拒绝！Cap<Page> 不能 as *u8
```

## 语法

```rust
// 类型定义
type Cap<T> = struct {
    cnode_idx: u32,    // cnode 表里的索引
    depth: u8,         // capability 在 cnode 树里的深度
    rights: u16,       // 权限位（读 / 写 / 授予 等）
    _phantom: *T,      // phantom type 字段（编译期存在，运行时 0 字节占用）
};

// 构造（特权操作）
#[cap_constructor]
fn kernel_alloc_page() -> Cap<Page>;   // 只有 #[cap_constructor] 函数能返回 Cap<T>

// 转移 / 克隆 / 撤销
fn give(c: Cap<Page>) -> Cap<Page> { c }       // move 语义（隐式转移 ownership）
fn clone_cap(c: &Cap<Page>) -> Cap<Page>;     // 显式 clone（走内核授权）
fn revoke(c: Cap<Page>);                       // 撤销（销毁底层对象）
fn into_raw(c: Cap<Page>) -> *u8;             // 降级为裸指针（**显式 + 编译器警告**）

// 使用
fn map_page(c: Cap<Page>) -> *Page {
    // 类型系统保证 c 是 Cap<Page>，不能是 Cap<Process> 假冒
    kernel_map(c)
}
```

## 8 条编译期规则

### 规则 1：不可伪造

**只有 `#[cap_constructor]` 函数能构造 `Cap<T>`**。用户代码不能写：

```rust
let c = Cap { cnode_idx: 0, depth: 0, rights: 0, _phantom: null };  // sema 拒绝！
```

`#[cap_constructor]` 函数本身只能由 `#[kernel_entry]` / `#[syscall]` 函数调用，用户态代码禁止直接调用。**双重保证**让伪造 capability 必须过编译器 + 内核两层。

### 规则 2：类型参数化

`Cap<Page>` ≠ `Cap<Process>` ≠ `Cap<IO>`。编译器强制：

```rust
let p: Cap<Page> = kernel_alloc_page();
let proc: Cap<Process> = p;            // sema 拒绝！类型不匹配
let io: Cap<IO> = p as Cap<IO>;        // sema 拒绝！类型不匹配
```

**实现**：sema 比较 `T` 类型参数是否相等；类型参数不同的 `Cap<T>` 视为不同类型。

### 规则 3：不可复制（默认 move）

```rust
let c1: Cap<Page> = kernel_alloc_page();
let c2 = c1;        // move（c1 失效）
// c1.read();       // sema 拒绝！c1 已 move
let c3 = c1.clone(); // 显式 clone（走内核授权，返回新 Cap<Page>）
```

**实现**：sema 给 `Cap<T>` 标记 `Move` trait（v3.x sprint 3i 实现 trait 系统后），自动拒绝隐式 copy。

### 规则 4：不可降级

```rust
let c: Cap<Page> = kernel_alloc_page();
let raw: *u8 = c as *u8;              // sema 拒绝！Cap<Page> 不能 as *u8
let raw2: u64 = c as u64;             // sema 拒绝！同因
```

显式降级用 `into_raw()`（编译器警告 + 必须 `unsafe` block）：

```rust
unsafe {
    let raw = c.into_raw();   // 显式降级，编译器发 warning
}
```

### 规则 5：可撤销（运行期，非编译期）

`Cap<T>` 的撤销由 jhyy_OS 内核负责，编译器不强制。**用户代码不需要关心**——内核 revoke 后，cnode 里相应 slot 被标记 invalid，下次 syscall 返回错误。

> **长期**：可考虑 effect system 追踪 revoke 边界（Rust 风格 dropck）；v3.x+ 研究

### 规则 6：空 capability = 无权限

`Cap<T>` 默认值是 `null` capability（cnode_idx = 0，rights = 0）：

```rust
let c: Cap<Page>;           // 默认 init 为 null
if c.is_valid() {
    c.read();              // 非空才操作
}
```

`is_valid()` 是标准库 trait 提供的 check。

### 规则 7：传参 = move ownership

```rust
fn consume(c: Cap<Page>) {
    // c 在这里 ownership，函数结束自动 drop（隐式 revoke 通知）
}

let c = kernel_alloc_page();
consume(c);
// c.read();                // sema 拒绝！c 已 move 进 consume
```

借用 cap（不转移 ownership）走 `&Cap<T>`：

```rust
fn peek(c: &Cap<Page>) -> u32 {
    c.cnode_idx
}

let c = kernel_alloc_page();
let idx = peek(&c);        // OK，借用完 c 还可用
c.read();                  // OK
```

### 规则 8：跟 `&mut` 借用规则一致

`Cap<T>` 的 `&mut Cap<T>` 借用约束同 Sprint 3g `&mut + lifetime`：

- 同一作用域内，`c` 要么有多个 `&Cap<T>`，要么有一个 `&mut Cap<T>`
- 借用期跨越 borrow expression 的使用范围（非词法作用域）

```rust
let mut c: Cap<Page> = kernel_alloc_page();
let r1 = &c;             // OK，共享借用
let r2 = &c;             // OK，多个共享借用
let m = &mut c;          // sema 拒绝！已有共享借用活跃
```

## 内存布局（abi § 12 草案）

```c
// C 端对齐参考（jhyy 端同）
typedef struct {
    uint32_t cnode_idx;   // 4 字节
    uint8_t  depth;       // 1 字节
    uint16_t rights;      // 2 字节
    // 1 字节 padding（自动）
} CapRepr;                // 8 字节（不包 _phantom）

// jhyy 端 layout
type Cap<T> = struct {
    cnode_idx: u32,       // offset 0
    depth: u8,            // offset 4
    rights: u16,          // offset 6
    _phantom: *T,         // 编译期字段，运行时 0 字节（phantom type）
};
// 总运行时大小：8 字节（cnode_idx + depth + rights = 7 字节 + 1 字节 padding，phantom 0 字节）
```

> **`_phantom` 是 jhyy 编译期字段，运行时大小 = 0**（phantom 类型惯用法）。codegen 看到 `Cap<T>` 时只 emit 8 字节，不带 `*T` 字段。Cap<T> 运行时总大小 = 8 字节（cnode_idx + depth + rights = 7 字节 + 1 字节 padding），跟 OS 端 cap 表布局 byte-equal（参见 [../../../../jhyy_OS/docs/coordination.md](../../../../jhyy_OS/docs/coordination.md) § 3 "Cap<T> phantom type 8 字节布局锁"）。

## 跟 jhyy_OS 的对应关系

| jhyy_OS 概念 | jhyy 语言层表达 | 备注 |
|--------------|----------------|------|
| Page capability（物理页授权）| `Cap<Page>` | `rights` 决定 R/W/X |
| Process capability（进程控制）| `Cap<Process>` | `rights` 决定 kill / debug / signal |
| IO port capability（端口 I/O 授权）| `Cap<IO>` | `rights` 决定 in / out |
| Device capability（设备控制）| `Cap<Device>` | `rights` 决定 read / write / ioctl |
| Endpoint capability（IPC 端点）| `Cap<Endpoint>` | `rights` 决定 send / recv |
| 内核构造 capability | `#[cap_constructor] fn kernel_alloc_page() -> Cap<Page>` | 编译器 + 内核双重门控 |
| 撤销 capability | `Cap::revoke(c)` | 内核调用，OS revocation 协议 |
| cnode 引用布局 | 8 字节（cnode_idx + depth + rights）| ABI § 12 锁定 |

## 跟 v3.x sprint 3g 联动

`Cap<T>` 跟 `&mut + lifetime` **必须同时实现**，因为：

- `&mut Cap<T>` 借用规则 = `&mut` 规则
- `Cap<T>` move 语义 = `Move` trait（trait 系统 sprint 3i 实现，但 v3.x sprint 3g 可能先用 hardcoded 路径）
- phantom type `_phantom: *T` 跟 `&mut` lifetime 标记共享 codegen 路径

**实施拆 sprint**(per coordination.md § 3 D27 锁 — **三段独立 sprint,顺序强制不可调换**):
- **v3.x sprint 3g(主体)**: `&mut + lifetime` + `Cap<T>` 8 条规则 + sema 实现 + 4 项 OS 联动 attribute/trait(`#[ipc_handler]` / `unsafe cap` / `Cap::provenance` / cap-offset 表 emit)— per D12/D13/D14/D15/D16/D18/D19/D20/D21
- **v3.x sprint 3g.5(独立 sprint,3g 后推)**: phantom type 0 字节布局保证(codegen + abi 锁定) — per D23/D27
- **v3.x sprint 3g.7(独立 sprint,3g.5 后推)**: 跟 jhyy_OS 内核实际 cap 表布局 byte-equal 联调 — per D27

**顺序强制理由**:
- 3g.5 依赖 3g codegen 路径(`_phantom` skip 路径在 3g codegen 之上)
- 3g.7 依赖 3g.5 phantom 0-byte 锁定(byte-equal 验证前提)
- 不可调换为 "3g.5 → 3g → 3g.7" 或 "3g.7 → 3g.5 → 3g"

**OS 对接**(per D9/D18):
- 3g/3g.5/3g.7 = **M4 启动硬前置**(不在 M1 之前)
- M1-M3 OS 代码用 `*mut T` raw pointer + 手动 discipline(per D11)
- M4 起 OS 代码用 `Cap<T>` + `&mut T`
