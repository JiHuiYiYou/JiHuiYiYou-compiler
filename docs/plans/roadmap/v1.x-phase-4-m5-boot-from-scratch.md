# v1.x Phase 4 / M5: boot-from-scratch — C 编译器最终丢弃

> **状态**: L1 roadmap — M5 backlog 推迟到 v2.x 末 + v3.x 末**之后**,等 C 依赖彻底清完再统一做。
> **生成原因**: 2026-08-14 user 决策 — M5 是**政治性里程碑** ("C 编译器最终丢弃"),不是技术阻塞。技术上**现在能做** (git rm + Makefile 改 default target),但 v2.x 砍 QBE 自写后端 + v3.x 砍 runtime.c 之前做 M5 等于"半吊子自举"。统一推迟到 v2/v3 后面,一次性删干净所有 C 依赖。
> **前置**: v1.0 M4 真闭环 ✅ + v1.5 installer ✅ + v2.x 全 ship (QBE 自写) + v3.x 全 ship (runtime 重写)
> **权威源**: [v1.0-self-hosting.md § "v1.0-self-hosting 的 5 个 milestone"](v1.0-self-hosting.md) (M5 原始定义) + [changelog-v1.0.0.md § "未达成 8" line 108](../logs/v1/changelog-v1.0.0.md) + [v2-v3-parallel-sprint-plan.md](v2-v3-parallel-sprint-plan.md) (M5 触发时点) + memory `project_m5_boot_from_scratch_decision.md`

## 0. TL;DR

**M5 不是"完全无 C 代码"**, 是 **"jhyy 编译器能完全靠 jhyy 编自己, 不需要 C 编译器"**。

技术上现在能 ship, 但用户决定**推迟**:
- v2.x 砍 QBE 自写后端 → M5 时机之一
- v3.x 砍 runtime.c → M5 时机之二
- v2/v3 都 ship 之后 → **一次性** git rm src/*.c + untrack QBE + untrack runtime → M5 真闭环

**触发时点**: **v2.x 末** (QBE 完全移除) **AND** **v3.x 末** (runtime 重写完) 都 ship 后。
**不是 "v2.x 末 OR v3.x 末"** — 要两个都完。

## 2. 自循环链 — 为什么 M5 跟 v1.0 M4 区分

### 2.1 当前链 (M4 hard 已 ship, v1.0.0 commit `eabee0d`)

```
compiler/src/*.c  ──(gcc)──>  jhyy_stage0.exe      [C 端产物]
                                          │
                                          ▼ 编 src0/main.jhyy
                          jhyy.exe                  [jhyy-side 产物]
                                          │
                                          ▼ 编 src0/main.jhyy
                          jhyy_v2.exe               [jhyy 编 jhyy]
                                          │
                                          ▼
                          jhyy_v3.exe               [jhyy_v2 编 jhyy]
                                          │
                                          ▼
                          jhyy_v4.exe               [jhyy_v3 编 jhyy]
sha256(v2.il) == sha256(v3.il) == sha256(v4.il) ✅ Stage 2 closure
```

**Stage 2 N=3 closure 已 ship** (M4 hard),但链起点 `jhyy_stage0.exe` 依赖 C 端。

### 2.2 M5 链 — 砍掉 C 端后

```
                  jhyy.exe (tracked seed, jhyy-side)   [唯一入口]
                                          │
                                          ▼ 编 src0/main.jhyy
                          jhyy_v2.exe                    [jhyy 编 jhyy]
                                          │
                                          ▼
                          jhyy_v3.exe                    [jhyy 编 jhyy 编 jhyy]
                                          │
                                          ▼
                          jhyy_v4.exe                    [jhyy 编 jhyy 编 jhyy 编 jhyy]
sha256(v2.il) == sha256(v3.il) == sha256(v4.il) ✅ Stage 2 closure (M4 维持)
```

**链起点 `jhyy.exe` 本身就是 jhyy-side 产物**, 不再需要 C 端 bootstrap。

### 2.3 关键观察

`jhyy.exe` 在 v1.4.4 ship (commit `9fb35c3`) 后**已经是 jhyy-side 产物**, 跟 C 端没运行时依赖。**M5 不需要重新实现任何东西**, 只是:

1. 承认 jhyy.exe 是种子, 不再需要从 C 端 rebuild 它
2. 物理删 src/*.c + jhyy_stage0.exe
3. 改 Makefile default target

**M5 = 30 行 git rm + 5 行 Makefile 改 + 验证 make selfhost 仍然 closure 维持**。

## 3. 推迟理由 (为什么不在 v1.0 ship 后立刻做)

### 3.1 "半吊子自举" 问题

| 时机 | C 依赖残留 | 自举质量 |
|------|----------|---------|
| **v1.0 末立刻做 M5** | QBE (C) + runtime.c (C) | 半吊子 — 编译器自举了, 但工具链和运行时仍 C |
| **v2.x 末做 M5**(QBE 自写后端后) | runtime.c (C) | 较好 — 编译器 + 后端都 jhyy |
| **v3.x 末做 M5**(runtime 重写后) | — | 完美 — 整个栈 0 C 依赖 |
| **v2/x/v3.x 都完做 M5** | — | 最佳 — 一次性删干净, 文档明确 |

### 3.2 v1.0 时还不敢的 3 个理由

1. **ACTIVE workaround 还在** (W-003/W-004/W-006/W-007) — v1.0 末仍有 C-side codegen 的"逃逸路径"在用, 删 src/ 万一 jhyy-side 改坏无 fallback (v1.4.6 ✅ 已清零)
2. **CI 守门不严** — v1.0 时无 GH Actions, 改 src/ 风险高 (v1.4.5 ✅ 已加 CI 三跑守门)
3. **installer 未 ship** — 用户拿 jhyy.exe 不依赖 MSYS2 的体验未验证 (v1.5 ⏳ 待 ship)

### 3.3 v1.5 ship 后仍然不做 M5 的理由

v1.5 installer 让用户能 "git clone → make → jhyy.exe 跑 hello.jhyy", 但 M5 让用户能 "git clone → make → jhyy.exe 编 jhyy.exe", **后者要求 jhyy.exe 是稳定的 seed**, 而 v1.5 时:
- jhyy.exe 还在 v1.x polish 阶段 (可能有 v1.6/v1.7 改动)
- ACTIVE workaround 数 = 0 ✅, 但**未来**改动还要进 src/ C 端吗? M5 后只能进 src0/

**M5 把 src/ 删了 = 锁死 jhyy-side 编译器为唯一开发路径**, 这是单向门, 不可逆。所以**等编译器功能稳定**再做, 不要在 v1.5 末这种"还可能改"的时点做。

### 3.4 真触发 M5 的时机

- ✅ v2.x 末 (QBE 移除, jhyy 自写后端) — 后端全 jhyy
- ✅ v3.x 末 (runtime 重写) — 运行时全 jhyy
- ✅ v1.x 再 ship 几个 polish 版本 (v1.6/v1.7 看实际需要) — jhyy-side 编译器 API 稳定

**三者都达成后, M5 一次性 ship**。

## 4. M5 sprint 设计 (推迟后, 实际启动时的步骤)

### 4.1 sprint 拆分建议 (3 个 sprint, 估 ~2 sprint 当量)

| 子 sprint | 内容 | 估时 | 风险 |
|----------|------|------|------|
| **M5-A 准备** | 验证 v2.x/v3.x 都 ship 完毕, jhyy.exe 在 v2.x/v3.x 任何 release 路径下都能 make selfhost closure 维持 | 0.3 | 低 |
| **M5-B 物理删 + Makefile 改** | `git rm compiler/src/*.c *.h` + `git rm jhyy_stage0.exe jhyy_v1.exe.exe` + `git rm -r qbe/` (v2.x 末 QBE 已 untrack 后) + Makefile 删 stage0 target, default all 直接编 jhyy.exe (从 tracked seed) | 0.3 | 中 (单向门, 不可逆) |
| **M5-C 验证 + 文档 ship** | (1) 新 clone 路径 `git clone → make → jhyy.exe 跑 hello.jhyy` → EXIT=42 (2) `make selfhost` Stage 2 N=3 仍然 closure (3) regress 持平 53/53 (4) docs/logs/v1/changelog-v1.X.Y.md 写 M5 ship section + memory `feedback_regress_baseline_binary_hash.md` 更新 ("v1 baseline 退役" 解释) + CLAUDE.md 改 "v1.x = jhyy 唯一入口" | 0.4 | 低 |
| **总计** | | **~1 sprint** | |

### 4.2 M5-B 详细步骤 (单向门, 必须小心)

```bash
# 1. 准备
git checkout -b v1.x-phase-4-m5-boot-from-scratch

# 2. 物理删 C 端源码
git rm compiler/src/*.c
git rm compiler/src/*.h

# 3. 物理删 C 端 binary + 历史 baseline
git rm compiler/build/bin/jhyy_stage0.exe
git rm compiler/build/bin/jhyy_v1.exe.exe

# 4. (假设 v2.x 末已 untrack QBE) 物理删 QBE 源码 + binary
git rm -r qbe/

# 5. 改 Makefile — 删 stage0 target, default all 改用 tracked jhyy.exe 当种子
#    原:
#      all: $(BIN_DIR)/jhyy.exe
#      $(BIN_DIR)/jhyy.exe: $(SRC0_DIR)/main.jhyy $(BIN_DIR)/jhyy_stage0.exe
#          $(BIN_DIR)/jhyy_stage0.exe compile ...
#    新:
#      all: $(BIN_DIR)/jhyy_v2.exe
#      $(BIN_DIR)/jhyy_v2.exe: $(SRC0_DIR)/main.jhyy $(BIN_DIR)/jhyy.exe
#          $(BIN_DIR)/jhyy.exe compile $(SRC0_DIR)/main.jhyy -o $(BIN_DIR)/jhyy_v2

# 6. 改 .gitignore — 删 jhyy_stage0.exe + jhyy_v1.exe.exe 例外 (已经 untrack)
#    注意: jhyy.exe 例外保留 (它是 seed)

# 7. CI workflow (.github/workflows/ci.yml) — 删 `make stage0` step + regress_stage0.py step (C 端没了)

# 8. mcp-jhyy — jhyy_compile / jhyy_run 工具不变, jhyy_selfhost_check 改 v1=v2=v3=v4 (jhyy.exe 是 v1)

# 9. docs 同步
#    - changelog-v1.X.Y.md: M5 ship section
#    - memory feedback_regress_baseline_binary_hash.md: 标 jhyy_v1.exe.exe "退役" (M5 删了, 不再是 invariant)
#    - CLAUDE.md: 改 "v1.x = jhyy 唯一入口, 无 C 端"

# 10. 验证 (per M5-C)
```

### 4.3 风险

| 风险 | 缓解 |
|------|------|
| 单向门 — src/ 删了不能再加回来 | git history 永远保留, 出问题可 `git checkout <M5 之前 sha> -- compiler/src/` 临时恢复;但**长期**是单向 |
| tracked jhyy.exe seed 漂移 | 跟 jhyy.exe 每次 release 一同发 binary, 用 SHA256 + GH Release asset 锁定 |
| 新人 clone → make 报错 | Makefile 报错信息明确: "jhyy.exe not found — run `git lfs pull` or check tracked binary" |
| CI 失去 stage0 验证 | regress_stage0.py 删, 但 regress.py (jhyy.exe) + make selfhost closure 已经够;真正守门是 v2=v3=v4 byte-equal |
| runtime.c 仍依赖 C | M5 时 runtime.c 仍在 (v3.x 末才会重写), 这是已知"M5 不完全"边界, 文档必须明示 |

### 4.4 M5-B 验证 (M5-C 必跑)

| # | 验证 | 命令 | 期望 |
|---|------|------|------|
| 1 | clone 路径无 C 工具链 | `git clone ... && cd ... && make` | jhyy_v2.exe 产出, 零 gcc 依赖 |
| 2 | jhyy.exe 跑 hello | `jhyy.exe run hello.jhyy` | EXIT=42 |
| 3 | selfhost closure | `make selfhost` | v2.il == v3.il == v4.il (sha256 比对) |
| 4 | regress 持平 | `python regress.py` | 53/53 PASS |
| 5 | CI 三跑只剩一跑 | GH Actions log | regress.py (jhyy.exe) ✅, regress_v1.py ❌ (已删), regress_stage0.py ❌ (已删) |
| 6 | `git grep` 找残留 | `git grep "src/.*\.c"` (从 src/ 视角) | 0 hit (除了 docs 里历史引用) |
