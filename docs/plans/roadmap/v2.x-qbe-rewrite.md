## § 2 自举定义（强自举，N 代 fixed point）

```
C 版 jhyy      编译 src0/*.jhyy → jhyy_0
jhyy_0         编译 src0/*.jhyy → jhyy_1
jhyy_1         编译 src0/*.jhyy → jhyy_2
jhyy_2         编译 src0/*.jhyy → jhyy_3
...
jhyy_N == jhyy_{N+1}  (编译器自身 fixed point)
```

### 验证对象

| 层 | 验证 | 工具 |
|---|---|---|
| QBE .il | jhyy_N 和 jhyy_{N+1} 编 fib.jhyy 产 .il byte-equal | `diff` 空 |
| 汇编 .s | jhyy_N 和 jhyy_{N+1} 编 fib.jhyy 产 .s byte-equal | `diff` 空 |
| 行为 .exe | regress.py 持平 baseline | regress.py |
| 性能 .exe | fib / ackermann / nqueens 等 benchmark 跑时间 ≤ 1.1x C 版 QBE 生成代码 | benchmark |

### 不验证

- 编译 wall time（自举编译慢可接受）
- .exe 字节 byte-equal（gcc ld 嵌 timestamp，**v2.x 末用 SOURCE_DATE_EPOCH 等兜底**,见 § 5 挑战 1）
- regress.py 47/47 全过（v1.0 baseline = 12 OK 持平即可，详见 [v1.0-self-hosting.md § 自举定义](v1.0-self-hosting.md)）

### "N 代" 的最低门槛

**jhyy_2 == jhyy_3**（编译器自身 fixed point，3 代内收敛）。**N ≥ 3** 是 v2.x 完成门槛。

> **N → ∞ 仍 fixed point** 是更强性质，目前**不要求**；是否纳入完成定义由 user 后续决定。

## § 5 关键技术挑战

### 挑战 1：byte-equal .s + 速度不退化的矛盾

传统编译器优化（peephole / 指令调度 / 寄存器分配启发式）会破坏 byte-equal：
- 不同 run 调度顺序不同 → .s 不一致
- 哈希表迭代顺序不稳定 → 寄存器编号不同

**应对**：
- **Deterministic optimization**：所有优化 pass 必须保输出稳定（输入不变 → 输出不变）
- 排序：所有数据结构用排序遍历（symtab 按名字 sorted）
- 寄存器分配：固定顺序启发式（如 local-first → global）而非贪心
- peephole：rule 应用按模式排序
- **LLVM 有等价做法（带 -g0 模式 + stable hash），可参考**

#### 扩展：deterministic binary byte-equal

v2.x 原计划只要求 **.il byte-equal + .s byte-equal**（不含 .exe）。**OS 启动 + 镜像部署**场景可能进一步要求 .exe byte-equal（确定性镜像）：

- **挑战**：gcc / ld 默认嵌 timestamp + 路径字符串 → .exe 每次 build 不同
- **应对**：
  - `gcc -g0`（无 debug）+ `strip` + `SOURCE_DATE_EPOCH=<fixed>` + `-Wl,--build-id=none`
  - 完全确定性：路径、命令、临时文件名都用 sorted canonical 形式
  - 链接器脚本定死 .text / .data 顺序
- **当前 v2.x 完成定义**：.il + .s byte-equal（**硬指标**）;.exe byte-equal **可选**（user 后续决定是否纳入完成定义）
- **关联**：jhyy_OS 启动镜像如果用 reproducible build 才需要这步；目前**仅作为 v2.x 扩展属性记录**

### 挑战 2：x86_64 指令集覆盖

C 版 QBE 生成的 .s 用到多少 x86_64 指令？需要先 inventory：
- 整数算术（add/sub/mul/div/neg）
- 内存（mov/lea/push/pop）
- 控制流（jmp/jcc/call/ret）
- 系统调用（syscall）
- struct pass-by-value sret 处理（v0.4 ABI 锁定）
- 浮点（**v2.x 不做**，等 v3.x 3h）

L3 任务清单启动后第一步：grep `codegen.c` 列出 emit 的所有 QBE IL 指令类型，反推 .s 指令集范围。

### 挑战 3：自举栈全栈验证

v1.x L1 计划只验证 `.il byte-equal`（单层）。v2.x 验证 `.il + .s` 双层 + 运行时性能：
- 验证脚本要重写：stage1.sh 加 .s diff 步骤 → 改名 stage2.sh
- benchmark 脚本：新写 `compiler/tests/bootstrap/bench.sh`，对比 jhyy_0 / jhyy_1 / C 版 QBE 三个编译器产 .exe 的运行时间

### 挑战 4：多目标 + freestanding（v0.8 末 + jhyy_OS 协调后重写）

jhyy_OS 需要 `amd64_win_freestanding` 目标（OS 走 UEFI + PE/COFF）：
- **多目标 codegen 拆分**:每个目标一份 emit 函数（`emit_amd64_win` / `emit_amd64_win_freestanding` / `emit_amd64_sysv` / `emit_amd64_sysv_freestanding`），共享 IL → 指令选择层
- **ABI 差异处理**:
  - Windows x64 ABI：4 寄存器传参（rcx/rdx/r8/r9），shadow space 32 字节
  - SysV x86-64 ABI：6 寄存器传参（rdi/rsi/rdx/rcx/r8/r9），无 shadow space
  - freestanding（amd64_win_freestanding）:**自定义 ABI**（OS 决定；建议优先 SysV 风格但具体由 jhyy_OS 决定；UEFI 调用约定走 EFI 规范）
- **链接器差异**:Windows → link.exe / lld-link.exe;SysV → ld.lld / ld.bfd;freestanding → 自定义 linker script
- **启动代码差异**:
  - hosted Windows:`_start` 由 ucrt 提供，main 被调
  - hosted SysV:`_start` 由 libc 提供
  - freestanding:**用户提供 `_start`**（jhyy 编 `_start` 进 `.text.boot`，bootloader 跳过去）
- **库差异**:
  - hosted Windows:link ucrt + vcruntime
  - hosted SysV:link libc（glibc / musl）
  - freestanding:**不 link 任何 libc**（jhyy runtime 跟 jhyy_OS 的 `core` 库同时存在）
- **codegen 隔离原则**:emitter 设计上严格按 target 隔离;选择哪个 emitter 由 `jhyy --target=<triple>` 决定
- **spec 增补**:jhyy-abi-v1.0.0.md 增 § 12（多 target ABI 表 + freestanding ABI 约定）
- **UEFI + PE/COFF 路径(v2.0 启动就位)**:
  - jhyy 编 `kernel.jhyy` → `kernel.s` → `kernel.o` (PE/COFF .obj)
  - 链接器(link.exe / lld-link)把 kernel.o + EFI runtime stub 链成 `kernel.efi`
  - QEMU -bios OVMF -kernel kernel.efi 启动
  - 不需要 ELF / multiboot2 路径
