## Context

**当前状态:零。**
lang-spec § 11.3 与附录 B 都明列 **const generic** 为不支持。

**这一版在 OS 线上的意义**:

| 用途 | 例 |
|---|---|
| 固定大小缓冲区 | `struct Buf<const N: usize> { data: [u8; N] }` |
| 寄存器组 / 位域宽度 | `struct Regs<const W: u32> { ... }` |
| 栈上界的静态上界 | `fn f<const N: usize>() -> [u8; N]` |

⚠️ **这一版与 capability rights 的设计直接相关** ——
[`docs/coordination/JHYY_编译器侧设计终版.md`](../../coordination/JHYY_编译器侧设计终版.md) § 5.1 明确说
**rights 走「8 个内置有限集合类型」路线,而不是 const generic 位集**,
理由是:
- const generic 位集与名义类型系统冲突(常量不是声明名)
- 单态化上界 2^16 失控(对比 8 种 rights ⇒ 11 类 type_tag × 8 = 88 种上界)

⇒ **本版引入 const generic 后,rights 的方案**要不要重新评估?
⇒ **建议:不评估** —— 88 种上界已可控,且 rights 走内置类型还有另一个好处:
**子集检查是编译期一条位运算,不需要常量表达式求值**。
⚠️ 但**这个前提要在本版开工时复核一次**(万一 const generic 做得足够好,方案可以更优雅)。

---

## Goal

1. **`const N` 泛型参数可用**
2. **单态化求值** —— `N` 在编译期算出具体值
3. **`[T; N]` 可用** —— 数组长度由 `N` 决定
4. **单态化上界可控** —— 不引入编译时间失控

---

## Scope

### 任务 1 —— 语法

```jhyy
struct Buf<const N: usize> { data: [u8; N] }
fn sum<const N: usize>(xs: [i32; N]) -> i32 { ... }
```

### 任务 2 —— 单态化求值

- `N` 必须是**编译期可求值的常量表达式**
- 求值 ⇒ 具体类型 ⇒ 单态化(每组 `N` 生成一份代码)

⚠️ **「编译期可求值」的边界要定清楚**:
允许字面量 / 算术 / 已知的 const 泛型参数组合?
⇒ **建议先只允许「字面量 + 算术」**,不做通用常量表达式。

### 任务 3 —— `[T; N]`

⚠️ **数组长度是 ABI 的一部分** ⇒ `[T; N]` 的布局要进 abi 文档 + abi-hash。

### 任务 4 —— mangling 与可复现

`const N` 参与类型 ⇒ mangling 必须编码 `N` 的值
⇒ **必须确定性**(W-121 教训:符号名不许取自堆地址)。

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| **单态化爆炸** ⇒ 编译时间失控 | 编译不可用 | 上界可控 + 编译时间预算 + 门要造一个「N 个不同取值」的用例量 |
| 常量表达式求值器做成通用引擎 ⇒ 成本高 | 版本做不完 | **先只允许字面量 + 算术** |
| `N` 参与类型 ⇒ mangling 破坏 | 产物不可复现 | 确定性编码 + 可复现门 |
| 引入 const generic 后 rights 方案被质疑 | 方案摇摆 | 启动时明确记录「不重估」的理由 |
