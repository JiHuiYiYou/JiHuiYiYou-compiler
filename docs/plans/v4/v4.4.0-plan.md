## Context

**这是本线第一个真正动 emit 层的版本** —— 风险比 v4.2.x 高一个量级(v4.2.x 只动一个公式 / 一个门)。

**为什么是寄存器分配** —— 2026-10-29 实测(不是判断):

| 事实 | 数字 | 来源 |
|---|---|---|
| 机器码里访存指令占比 | **49%** | `docs/perf/self-backend-baseline-2026-10-29.md` |
| 后端把**每个** SSA temp 物化成栈槽 | ⇒ 每个值都是「load 槽 → 算 → store 槽」 | 同上 |
| 只用一次的 temp | **52%** | 同上 |
| 紧接着下一条就被用的 temp | **30.5%** | 同上 |
| 4 条之内被用的 temp | **47.8%** | 同上 |

⇒ **一个带前瞻窗口的受限线性扫描就能覆盖 ~76% 的 temp**(实测 75.7%)，
而完整的 CFG + 活跃区间 + phi 并行移动是好几倍的工程量。**先拿 48%,再谈剩下的。**

**IR 层优化动不了它**(2026-10-29 逐项测量):

| 版本 | 声称价值 | **实测机会数** |
|---|---|---|
| v4.2.2 peephole | 折叠 no-op | 54 条 / 407386 行(0.002%) |
| v4.3.0 常量折叠 | `2+3` → `5` | 语料 A **0** / 语料 B **84** —— ⚠️ **前端本来就不折叠** |
| v4.3.0 代数化简 | `x+0` → `x` | 54 / 424 |
| v4.3.0 DCE | 删死指令 | 42(0.1%)/ 193 —— 前端产出的 SSA 本来就干净 |
| **v4.4 寄存器分配** | 消掉 load/store 往返 | **52% 的 temp 只用一次;47.8% 在 4 条之内** |

**阶段一(2026-10-30 已完成)只做基础设施 + 安全网,产物逐字节不变** ——
`codegen_amd64_rcache.jhyy` 已落地(受限线性扫描:同基本块 + 无 call + 整数类型;
5 个 callee-saved GPR;池满退化成栈槽)。
**阶段二才让 emit 层真的按 temp id 取位置。**

## Goal

1. **emit 层按 temp id 取位置**(`emit_mov_temp_to_reg` / `emit_mov_reg_to_temp` 改成按 temp 取位置,
   操作数读取改走 `emit_operand_temp`)⇒ 消除「load 槽 → 算 → store 槽」往返
2. **三条硬约束同期落地**(见下)⇒ 防止 volatile load 被缓存 / XMM 溢出 / 静默槽位访问
3. **`-O0` 的产物逐字节不变**(寄存器分配**默认关**,靠 flag 开)⇒ 现有门全绿

## Scope

### 任务 1 —— emit 层消费寄存器(核心)

改动面(实测 **48 个取槽位偏移的调用点**):

| 文件 | 调用点数 |
|---|---|
| `compiler/src0/codegen_amd64_emit_call.jhyy` | 16 |
| `compiler/src0/codegen_amd64_emit_sse.jhyy` | 17 |
| `compiler/src0/codegen_amd64_emit_mem.jhyy` | 10 |
| `compiler/src0/codegen_amd64_emit_ctrl.jhyy` | 5 |

⇒ 引入**两个收口 helper**(而不是在 48 处各写一遍判断):
- `emit_load_temp(state, temp, dest_reg, target_tag)` —— 从寄存器或槽位读进 dest_reg
- `emit_store_temp(state, temp, src_reg, target_tag)` —— 写进寄存器或槽位

### 任务 2 —— 三条硬约束(**必须同期**,见下)

### 任务 3 —— 序言 / 尾声

- `ret` 只在**一个地方** emit(`codegen_amd64_emit_ctrl.jhyy:321` 的 `emit_ret`)⇒ 尾声统一收口 ✓
- 序言在 `emit_func_header` ⇒ 加 `pushq %rbx` 等
  ⚠️ 必须在 `movq %rsp, %rbp` **之后**,否则 rbp 相对的槽位偏移全错
- ⚠️ **16 字节对齐**:序言 push 了 k 个寄存器 ⇒ `%rsp ≡ -8k (mod 16)`
  ⇒ `subq $N, %rsp` 的 N 必须 ≡ 8k (mod 16)⇒ **k 为奇数时 N 要 +8**
- ⚠️ `___chkstk_ms` 的探测量必须含 push 的那 8k 字节(否则跳过 guard page)

### 三条硬约束(与阶段二同期落地)

> ⚠️ **前两条来自 OS 线的审核**([`docs/coordination/JHYY_编译器侧设计终版.md`](../../coordination/JHYY_编译器侧设计终版.md)
> § 3.3);**这正是它们必须同期落地的原因** —— 约束晚一版落地,而那正是它开始发作的时刻。

| # | 约束 | 为什么必须同期 | 形状 |
|---|---|---|---|
| 1 | **排除 volatile temp** | `emit_volatile`(`codegen_amd64_emit_call.jhyy:2741`)**只发注释、什么都不做**;后端**能**识别 volatile(`tok.qbe_type == QBE_VOLATILE_MARKER()`)却**没有拒绝机制**;阶段一的资格判据(同基本块 + 无 call + 整数类型)**没有 volatile 这一维**(`codegen_amd64_rcache.jhyy` grep 零命中)⇒ 寄存器化会让 volatile load 被缓存 ⇒ **MMIO 读静默失效** | 显式排除 + 响亮失败 |
| 2 | **禁 XMM 溢出 / 禁 red zone** | 后端全 spill、寄存器池只有 5 个 GPR、**没有省略帧优化** ⇒ 当前恰好安全;**但正因如此**问题在阶段二这一刻诞生 | 持久断言(编译期上下文属性) |
| 3 | **槽位访问响亮失败** | 阶段一已有:分配了寄存器却走槽位路径 ⇒ 编译失败。阶段二要保证**所有**槽位访问点都走收口 helper ⇒ 漏改的调用点当场被抓 | 沿用阶段一 |

> ⚠️ **约束 1 与 `ptr<io>` 是同一件事**:`ptr<io>` 要求「默认 volatile、不合并访问、禁止推测读」
> ⇒ 语言的承诺要靠后端这条约束兑现 ⇒ **必须在 `ptr<io>` 落地之前做完**。

### ⚠️ 安全网的一个已踩过的坑(必须复现检查)

守卫**必须放在 `jh_write_file` 之前**:
第一版只把它放在 in-mem 路径,文件路径(`codegen_amd64_run_text`)漏了
⇒ 守卫**响了**,但**错的 .s 和 .exe 照样落地、exit code 还是 0** ⇒ 守卫形同虚设。
⇒ **两条路径都要查,而且都要在写盘之前。**

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| 漏改的槽位访问点 ⇒ **静默读到垃圾** | 产出错代码,不报错 | **响亮失败**(W-120 / W-130 的规矩:响亮失败远好过静默错代码)+ 收口 helper |
| volatile load 被缓存 ⇒ **MMIO 读静默失效** | 硬件级静默错误 | 显式排除 volatile temp + 响亮失败 |
| 序言 push 破坏 16B 对齐 ⇒ SysV SIMD 参数 fault | 运行期 fault | `subq $N` 的 N ≡ 8k (mod 16);k 奇数时 +8 |
| `___chkstk_ms` 探测量漏算 push 的 8k ⇒ 跳过 guard page | 栈溢出 | 探测量含 push 字节 |
| 「寄存器分配更快但栈仍不可知」的局部优化 | 白干 | 栈上界分析在 v4.7(OS-2),**依赖**本版把帧压下来才量得准 ⇒ 本版是 v4.7 的前置 |
| 只做前瞻窗口,收益不及预期 | 性能目标落空 | 阶段一已有独立实现 `scripts/dev/regalloc_reference.py` 可对拍 |
