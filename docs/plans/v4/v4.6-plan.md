## Context

**这一版是整条 OS 线的地基。** 它不做任何新特性,只做一件事:
**把「静默通过的错误程序」变成「编译失败」。**

**为什么这是最高优先** —— 2026-10-30 逐条回源码核过(§ 现状审计):

| P0 项 | 结论 | 证据 |
|---|---|---|
| 实参**类型**检查 | ❌ **未做** | `sema.jhyy:1773-1811`:期望形参类型只用于泛型 enum 变体解析(W-111 遗留),**从不与实参比对**。实测 `takes_i64(1 as i32)` / `takes_ptr(7 as i64)` 编译通过**并运行** |
| 实参**个数**检查 | ❌ **未做(规范里也没记)** | 实测 `takes_one(1, 2)` 编译通过并运行。lang-spec §118 与附录 B 只写了「类型不检查」 |
| `extern fn` 形状限制 | ❌ **未做** | `sema.jhyy:2984` 只跳过 body 检查,无任何形状约束 |
| CLI 多余输入文件报错 | ❌ **静默忽略** | `main.jhyy:1561-1563`:`if input == (0 as *u8) { input = arg; }` ⇒ 第二个输入文件被丢弃 |
| bool 归一化 | ⚠️ **宽度已一致,值未归一化** | 表达式层统一 `'w'`(`ir.jhyy:188`)、data 段用 `'b'`(`ir.jhyy:70`);但 `codegen.jhyy:3212` 的 `jnz` 判「非 0」⇒ **值为 2 的 bool 仍算真** |

**为什么「静默错误」是头号风险** —— 它比「像 C 一样不安全」更危险,
因为语法像 Rust 会制造**虚假安全感**。

## ⚠️ 硬前置:先统计,后改码

实参类型检查会让「整数实参传给指针形参」这类代码**编译失败**
⇒ **必须先统计 `src0` 自身有多少处实参类型不符**(自举是硬门),
再决定报错口径(**全拒** / **只拒不安全形态**)。

⇒ **第一步不是改 sema,是写统计脚本。**

---

## Goal

1. **实参类型 + 个数都检查** ⇒ `takes_i64(1 as i32)` / `takes_one(1, 2)` 编译失败
2. **`extern fn` 参数形状受限** ⇒ struct 传给 C ABI 不符的形参编译失败
3. **CLI 多余输入文件报错** ⇒ 不再静默忽略
4. **bool 值归一化** ⇒ 只有 0/1
5. **整数上下文转换规则落地并写进规范**
6. **`src0` 自身零实参不符**(统计先行)

---

## Scope

### 任务 1 —— 统计(第一步)

写脚本扫 `src0/` 全部调用点,产出:
- 类型不符的调用点清单(按类型分类)
- 个数不符的调用点清单
- 涉及 `extern fn` 的调用点清单

⇒ 产出决定后面的报错口径。**统计结果要写进本 plan。**

### 任务 2 —— `ParamTypeChecker`

在 `sema.jhyy` 的实参推断路径上加比对:
- 期望形参类型 vs 实参类型(**类型 + 个数**)
- 泛型实例化后仍需比对
- ⚠️ **不能破坏 W-111 的泛型 enum 变体解析**(那里期望形参类型是**唯一**线索)

### 任务 3 —— `extern fn` 形状限制

`extern fn` 的形参类型必须是 C ABI 可表达的形状
⇒ struct / 聚合类型作形参 ⇒ 编译期报错(除非显式标注)。
⚠️ abi §12.1(sret 无条件启用)与 §12.4(MEMORY class 混排)当前都是已知偏离 ⇒
报错口径要跟这两条的现状对齐,别声称支持。

### 任务 4 —— CLI 多余输入文件报错

`main.jhyy:1561-1563` 改成:第二个输入文件 ⇒ **报错退出**,不是丢弃。
⚠️ CLI 验收必须区分「未知参数」「多输入文件」「输入不存在」。

### 任务 5 —— bool 值归一化

`codegen.jhyy:3212` 的 `jnz` 判「非 0」⇒ 值为 2 的 bool 仍算真
⇒ 归一化成 0/1(在产生处,不在比较处)。
⚠️ **这与「u8 比较宽度」是不同的修法** —— 已在 2026-10-30 实测排除 u8 那条。

### 任务 6 —— 整数上下文转换

**建议:只在字面量位置提升 + 写进规范**(F3)。

- 痛点是**字面量**不是变量:`i64 + 1` 极常见;`i64 + some_i32_var` **是类型错误,应该报错**
  ⇒ 全面提升(F1,C 风格)会把后者也放过 ⇒ **反而丢掉类型检查**
- 改法:sema 里字面量 coerce 的逻辑**已经有**(let 位置),**复用到二元运算与实参位置**

**建议的规范条文**:

> 整数字面量在**期望类型已知**的位置(let / 赋值 / 函数实参 / 二元运算中另一侧为整型)
> 按期望类型解释;**两侧都是变量时不做隐式转换** ⇒ 类型不同即报错。
>
> `i64 + 1` ✅(1 按 i64 解释)· `let x: i64 = 10` ✅ · `takes_i64(1)` ✅
> `i64 + i32_var` ❌ · `i32_var + i64_var` ❌

⚠️ **与任务 2 的交互**:`takes_i64(1)` 会变合法 ⇒
**实参检查的报错口径必须区分「字面量可隐式转换」与「真的类型不符」** ⇒ 两者**同批落地**。

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| 实参检查让 `src0` 自己编译不过 | 自举断 | **先统计后改码**;必要时先修 src0 的调用点 |
| 破坏 W-111 泛型 enum 变体解析 | 泛型回归 | 该路径的期望形参类型是**唯一**线索 ⇒ 单独 case + 回归 |

| 报错口径过严 ⇒ 大量代码要改 | 成本 | 统计结果驱动;可分「先只拒不安全形态」 |
| bool 归一化改在比较处 ⇒ 漏改路径 | 静默 | 归一化放在**产生处**,一处改完 |
