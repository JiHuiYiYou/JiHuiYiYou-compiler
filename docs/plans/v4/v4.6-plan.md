## Context

**这一版是整条 OS 线的地基。** 它不做任何新特性,只做一件事:
**把「静默通过的错误程序」变成「编译失败」。**

**为什么这是最高优先** —— 2026-10-30 逐条回源码核过(§ 现状审计):

| P0 项 | 结论 | 证据 |
|---|---|---|
| 实参**类型**检查 | ❌ **未做** | `sema.jhyy:1773-1811`:期望形参类型只用于泛型 enum 变体解析(W-111 遗留),**从不与实参比对**。实测 `takes_i64(1 as i32)` / `takes_ptr(7 as i64)` 编译通过**并运行** |
| 实参**个数**检查 | ✅ **已做**(2026-11-21,任务 7 / **W-236**) | sema 在调用点比对 `nargs` 与 `nparams` ⇒ `takes_one(1, 2)` **编译失败**。⚠️ **`extern fn` 不查**(C 的可变参函数在 jhyy 里只能声明成定长签名,调用点却按 C 的习惯传任意多个实参) |
| `extern fn` 形状限制 | ❌ **未做** | `sema.jhyy:2984` 只跳过 body 检查,无任何形状约束 |

因为语法像 Rust 会制造**虚假安全感**。

## ⚠️ 硬前置:先统计,后改码

实参类型检查会让「整数实参传给指针形参」这类代码**编译失败**
⇒ **必须先统计 `src0` 自身有多少处实参类型不符**(自举是硬门),
再决定报错口径(**全拒** / **只拒不安全形态**)。

⇒ **第一步不是改 sema,是写统计脚本。**

---

## Goal

1. **实参类型 + 个数都检查** ⇒ `takes_i64(1 as i32)` / `takes_one(1, 2)` 编译失败
2. **`extern fn` 参数形状受限** ⇒ struct 传给 C ABI 不符的形参编译失败
3. **CLI 多余输入文件报错** ⇒ 不再静默忽略
4. **bool 值归一化** ⇒ 只有 0/1
5. **整数上下文转换规则落地并写进规范**
6. **`src0` 自身零实参不符**(统计先行)
7. **静默缺陷清零** —— 任务 7 的每一条都变成「一条编译期报错」或「一个正确结果」

## Scope

### 任务 1 —— 统计(第一步)

写脚本扫 `src0/` 全部调用点,产出:
- 类型不符的调用点清单(按类型分类)
- 个数不符的调用点清单
- 涉及 `extern fn` 的调用点清单

⇒ 产出决定后面的报错口径。**统计结果要写进本 plan。**

### 任务 2 —— `ParamTypeChecker`

在 `sema.jhyy` 的实参推断路径上加比对:
- 期望形参类型 vs 实参类型(**类型 + 个数**)
- 泛型实例化后仍需比对
- ⚠️ **不能破坏 W-111 的泛型 enum 变体解析**(那里期望形参类型是**唯一**线索)

### 任务 3 —— `extern fn` 形状限制

`extern fn` 的形参类型必须是 C ABI 可表达的形状
⇒ struct / 聚合类型作形参 ⇒ 编译期报错(除非显式标注)。
⚠️ abi §12.1(sret 无条件启用)与 §12.4(MEMORY class 混排)当前都是已知偏离 ⇒
报错口径要跟这两条的现状对齐,别声称支持。

### 任务 4 —— CLI 多余输入文件报错

`main.jhyy:1561-1563` 改成:第二个输入文件 ⇒ **报错退出**,不是丢弃。
⚠️ CLI 验收必须区分「未知参数」「多输入文件」「输入不存在」。

### 任务 5 —— bool 值归一化

`codegen.jhyy:3212` 的 `jnz` 判「非 0」⇒ 值为 2 的 bool 仍算真
⇒ 归一化成 0/1(在产生处,不在比较处)。
⚠️ **这与「u8 比较宽度」是不同的修法** —— 已在 2026-10-30 实测排除 u8 那条。

### 任务 6 —— 整数上下文转换

**建议:只在字面量位置提升 + 写进规范**(F3)。

- 痛点是**字面量**不是变量:`i64 + 1` 极常见;`i64 + some_i32_var` **是类型错误,应该报错**
  ⇒ 全面提升(F1,C 风格)会把后者也放过 ⇒ **反而丢掉类型检查**
- 改法:sema 里字面量 coerce 的逻辑**已经有**(let 位置),**复用到二元运算与实参位置**

**建议的规范条文**:

> 整数字面量在**期望类型已知**的位置(let / 赋值 / 函数实参 / 二元运算中另一侧为整型)
> 按期望类型解释;**两侧都是变量时不做隐式转换** ⇒ 类型不同即报错。
>
> `i64 + 1` ✅(1 按 i64 解释)· `let x: i64 = 10` ✅ · `takes_i64(1)` ✅
> `i64 + i32_var` ❌ · `i32_var + i64_var` ❌

⚠️ **与任务 2 的交互**:`takes_i64(1)` 会变合法 ⇒
**实参检查的报错口径必须区分「字面量可隐式转换」与「真的类型不符」** ⇒ 两者**同批落地**。

### 任务 7 —— 静默缺陷清零(台账 2026-11 新登记)

台账在 2026-11-14 ~ 11-20 之间又登记了一批**同一类**的缺陷:不报错 / 报错不指真因 /
**静默给错值**。它们全部并进本版 —— 本版总目标本来就是「把静默通过的错误程序变成
编译失败」,而 OS 线后续各格(v4.7 起)的主线是**能力建设**,不是止血。

| ID | 一句话 | 根因位置 | 关掉条件(= 台账的「失效条件」) |
|---|---|---|---|
| **W-228** | 整数字面量**装不下**声明类型时被静默接受 ⇒ 常量折叠与运行时**两种解释** | `sema.jhyy` `NODE_INT` 分支只读 `(*d).prim`,**不按声明类型窄化** | 窄化发生在 **sema 定类型那一步** ⇒ 字面量与运行时**只有一种解释** |
| **W-229** | 把**函数名当值**用 ⇒ sema 放行、IR 坏 ⇒ **codegen 崩 + 产物爆栈** | `sema.jhyy` 表达式位置的标识符解析到 `SYM_FN` 时直接放行 | sema 拦一条「函数值未实装」的干净报错 + IR 不再产出空实参槽 |
| **W-230** | 栈位置实参传 `null` 字面量 ⇒ caller 只写 4 字节、callee 按 8 字节读 ⇒ **指针带残渣** | `NODE_NULL` 的类型靠「caller 上下文」填充,**调用实参路径没实现** | 调用实参路径给 `null` 填形参类型(⇒ IR 发成 `l`),或 codegen 按 8 字节槽写零扩展值 |
| **W-231** | struct 字面量里的 `null` 字段 ⇒ 误报 `field type mismatch` | 同一根因,**struct 字段路径**也没实现 | struct 字面量字段路径也给 `null` 填类型 |
| **W-232** | 顶层 `const` 标量 ⇒ 报错文案指向「语法」而不是「顶层 const 只支持数组」 | `parser.jhyy` `parse_const_decl` 只按数组语法解析 | 诊断改成明确的「顶层 const 只支持数组」 |
| **W-233** | `"x" as [*]u8` ⇒ 切片的 **len 没填**(=0)⇒ 读元素**越界 ⇒ 访问违例** | `codegen.jhyy` `NODE_CAST` 只特判 array→slice | 给 `*u8 → [*]u8` **填上字面量的长度**,或**明确拒绝**这个转换 |
| **W-234** | 顶层 `const` 数组的元素写成 `1 as i32` ⇒ **静默读出 0** | 顶层 `const` 数组的初值**没走常量表达式求值** | 顶层 `const` 数组初值也走常量表达式求值(⚠️ **求不出来的元素仍落 0** —— 那是规范 § 12 明写的「编译器不做 const 表达式检查」) |
| **W-235** | 窄类型(`i8`/`u8`/`i16`/`u16`)**局部变量**既不截断也不回绕(实际按 32 位算)⇒ 与 lang-spec § 4.2 / § 4.3 **冲突** | `ir.jhyy` `qbe_type_of` 把四个窄整型都映成 `QBE_W()` | **可观测语义**对齐:`as` 显式截断 + 算术按窄宽度回绕 ⇒ 与内存路径逐位一致(⚠️ **机制与原条件写的不同** —— 见下面的「怎么修的」) |
| **W-236** | 调用**不检查实参个数** ⇒ 少传/多传 ⇒ 编译通过 ⇒ 参数**全是垃圾** | `sema.jhyy` 调用点只推实参类型,**从不比对 `nargs` 与 `nparams`** | sema 在调用点比对实参个数与形参个数,不等就报一条错 |

**与已有任务的合流**(不是新增工作量,只是归位):

- **W-230 + W-231** ⇒ **同一个根因**(`NODE_NULL` 的类型填充点不全)⇒ 一处改动收两条。

### 任务 7 的落地记录(2026-11-21)

> **9 条全部修完**(W-228 … W-236)⇒ 台账 ACTIVE 8 → **0**、DEFERRED 2 → **1**。
> 复现件全部搬进 `compiler/tests/examples/`(`w228_…` … `w236_…`,**9 条新用例**)。

**W-235 的机制与原条件不同** —— 原条件写的是「窄整型返回真正的
`QBE_B_LOCAL()` / `QBE_H_LOCAL()`,且算术按操作数宽度发射」,**没按那条做**:
QBE 的 IL **没有** sub-word 临时量(`'b'`/`'h'` 只在**内存寻址**那层有意义)
⇒ 真给窄类型发 `addb`,得把整个后端的寄存器分配 / 比较 / 传参 / phi 全改成
sub-word 宽度 ⇒ 那是一次**重写后端**。
**改成「值语义对齐」**:位宽在**值**上正确(**槽宽**仍是 32 位)⇒
`as` 发一次 `extsb`/`extub`/`extsh`/`extuh`、窄类型的算术结果再截断一次
⇒ **可观测语义**与内存路径(`storeb`/`loadub`)**逐位一致**
⇒ 台账按**可观测行为**关闭。

⚠️ **代价**:窄类型转换在每道题上都摊在静态指标里 ⇒ 加了两处省成本的措施
(**常量折叠** + **复用源槽**)⇒ 实测用到窄类型的 3 道题
(nbody / revcomp / spectral)**指令 +3、访存 +3、帧中位数 +16 字节**,
其余 6 道题**一字未变** ⇒ 按 METHODOLOGY § 7「改后端后必须重取基线」
重取了 `bench/baseline/static.json`(只改这 3 道题)。

**W-234 的边界** —— 「求不出来的元素仍落 0」是**规范 § 12 明写**的行为
(「编译器不做 const 表达式检查」)⇒ 编译器**刻意不加**那条诊断
(加了会打死 `spec_const_nonconst_elem.jhyy` 那条一致性用例)
⇒ 本条修的是「**能求出来却没求**」的那一半(`1 as i32` 那种)。

**W-236 的口径** —— **`extern fn` 不查个数**:C 的可变参函数在 jhyy 里只能
声明成**定长**签名,但调用点按 C 的习惯传**任意多个**实参
⇒ 这条检查当场抓出了编译器**自身**的 2 个真缺陷
(⇒ 另开 **W-237 / W-238**,同一批修好)。
