## Context

**M5 是「0-C 闭环」项 —— 编译器自己不再依赖 C 代码。**

| Part | 内容 | 状态 |
|---|---|---|
| Part 1 | 删 `compiler/src/*.c` | ✅ v4.0.21 已做 |
| Part 2 | untrack QBE | ✅ v3.1.0 已做 |
| **Part 3** | **删 `compiler/runtime/runtime.c` + `compiler/src0/jhyy_helpers.c` 的用户侧 runtime** | ⬜ **唯一剩余** |
| Part 4 | 工具链自含闭环验证 | 部分 |

**为什么排在性能线之后**(2026-10-29 论证):

1. **M5 Part 3 是把成熟的 C runtime 换成新写的 jhyy 代码。**
   `runtime.c` + `jhyy_helpers.c` 现在给每个用户程序提供 malloc / memcpy / printf / exit。
   删掉它们 ⇒ 这些改走 **jhyy 侧的实现**
   (`std/arena.jhyy` / `std/mem.jhyy` / `std/fmt.jhyy` / `std/os.jhyy` 已存在)
   ⇒ **在一个已经比 gcc -O0 慢 3.4~4.7x 的后端上,再叠一层新写的、同样慢的代码。**
2. **先修后端,M5 Part 3 的成本才可控** —— 而且只有先有性能门,
   才能写出「0-C 闭环后程序不得比 0-C 前慢 > X%」这条**真正有意义**的门。
3. **寄存器分配器直接受益** —— std lib 的热路径(arena 分配、memcpy)拿到寄存器分配后,
   M5 Part 3 的性能代价会小得多。

⚠️ **注意方向张力**:W-103 往 `jhyy_helpers.c` 加了 **5 个 libc bridge**
(`std_os_open/close/read/write/exit`),M5 Part 3 要删 C runtime。
**取舍**:真的 0-C 时换掉的是 **bridge 的实现**(改 syscall),
`std/os.jhyy` 的 `std_os_*` **一行不动**(台账 W-103 已记)。

### ⚠️ 阶段 0 的起因(2026-11-02 新增)

> **起因**:一次 std ergonomics 专项复核发现**版本轴上的空缺** ——
> **在本版之前，23 份 plan 里没有一份把「让 std 好用」当目标**;std 只在 v4.5 出现,
> 还是作为「替换 C runtime」的**载体**,不是作为「让用户好写」的目标。
> ⇒ **阶段 0 补这个空缺**(范围见下面「Scope」⇒ 阶段 0)。

#### 为什么是「阶段 0」而不是独立一格

| 理由 | 说明 |
|---|---|
| **形状先定,实现后填** | 本版任务 1 要**改 std 真身**(删 C runtime ⇒ jhyy 侧接管)。形状若在改真身时才定 ⇒ 一次 break;**先定 ⇒ 本版只填实现,第二次 break 被省掉** |
| **不依赖 v4.4** | 阶段 0 只碰 `compiler/src0/std/*.jhyy` + 文档 + 测试 ⇒ **不碰 codegen / 不碰 ABI** ⇒ **可与性能线并行** |
| **窗口期** | 「现在用的人少」⇒ 改名 / 去重的迁移成本最低 —— 这正是 § 15 这份锁版规范里 std 的真实处境 |

#### 阶段 0 的范围(2026-11-02 **实测**基线,不是判断)

| 事实 | 实测结果 |
|---|---|
| `ptr_add` 的**公开**副本 | **5 份**(`mem` / `fmt` / `arena` / `string` / `vec`) |
| arena API 的整份副本 | **2 份**(`arena_init` / `align_up` / `arena_alloc` / `arena_reset` / `arena_free`,`arena` 与 `string` 各一份) |
| `math` 的公开 API | **只有 `sin` / `cos` / `sqrt` / `pow`**(libm `extern fn`)—— **没有 `abs` / `min` / `max`** |
| `fmt` 的公开 API | **只有 `i32` / `i64` / `str` / `hex_u32`** —— 没有 `u32` / `u64` / `f64` / `bool` / `char` / `ptr` |
| `io` 的公开 API | **全是字符串级** —— 打一个整数要自己 `fmt_i32` 进缓冲区 + `std_io_print` |
| 输入侧 | **只有裸 fd 读**(`os::std_os_read`)—— 没有 `read_line` / 读整数 / EOF 判定 |
| `[0; N]` 重复数组字面量 | **parse error**(实测 `expected ], got ;`)⇒ 用户开 scratch buffer **只能手写 N 个 0** |
| 模块可见性 | **jhyy 没有 `pub`**(`pub` 在规范与源码里零命中)⇒ **模块内无法声明私有 helper** ⇒ 上面的副本**全是公开的** |
| `strlen_local` vs `str_len` | ⚠️ **语义不同,不是重复** —— 前者扫 **NUL 结尾的 C 串**,后者读 **自描述串**(`StringHeader`:`data @0` + `len @8`)的长度 ⇒ **两个都留** |
| 编译器自己用 std 吗 | ❌ **一个都不用** —— `import arena;` / `import util;` 命中的是**编译器自己的** `compiler/src0/arena.jhyy` + `compiler/src0/util.jhyy`（两级查找的「同目录优先」），**不是** `std/` 下那 8 个 ⇒ **`std/` 的 8 个模块编译器自己一行不用** |
| 同名跨模块的语义 | `mem::ptr_add` 与 `fmt::ptr_add` **可同时存在且不报错** ⇒ 不限定调用时**静默取其一** —— ⚠️ 但 **5 份 `ptr_add` 的实现逐字节相同** ⇒ 静默取其**行为一致** ⇒ **不是正确性 bug**,是整洁度问题 |

⇒ **最刺痛的一条**:`fmt_i32(out_buf, val)` 要一个 **≥32 字节**的缓冲区,
而 `[0; N]` 不存在 ⇒ 用户今天写「打印一个整数」是 **5 行 + 32 个手写的 0**。

## Goal

**阶段 0(新增)**

0.1 **std 的缺口补齐(纯增量,零 API break)** —— `[0; N]` 可用;`math` 有
   `abs`/`min`/`max`;`fmt` 有 `u32`/`u64`/`bool`/`char`/`ptr`;`io` 有输入侧 +
   三个标准流句柄
0.2 **「打印一个整数」的 buffer 声明从 318 字符降到 ≤ 40 字符**(句数 3 不变)——
   阶段 0 的用户可感知验收点
0.3 **std 的公开面收口(带 API break)** —— `ptr_add` 只剩 1 份、arena API 只剩 1 份、
   § 15 拆出独立规范 ⇒ **本版只填实现,不再重塑 API**
   ⇒ **顺序有意为之**:先给全部纯增量收益,再一次性付 break 的代价(见 Scope ⇒ 排序)

**任务 1–4(原有)**

1. **用户程序不再链接任何 C runtime** ⇒ 真正的 0-C 闭环
2. **`std/` 八个模块成为唯一的 runtime 提供者** —— 且它们**真的可被用户代码 import**
   (W-103 已落地「两级查找:main 文件旁边 → std lib 目录」)
3. **性能不退化**:0-C 闭环后同一组用例的运行时不得比 0-C 前慢 > 阈值
4. **自举闭环仍 PASS**

## Scope

### 阶段 0 —— std API 收口 + 缺口补齐(2026-11-02 新增)

> **本阶段在任务 1–4 之前执行** —— 理由见上面 Context ⇒「为什么是『阶段 0』而不是独立一格」。

#### 阶段 0 内部的排序(2026-11-02 重排)

**排在前面的三个是纯增量(无 API break),排在最后的那一个带 break。**

| 序 | 任务 | 性质 | 用户可感知收益 | 代价 |
|---|---|---|---|---|
| 0.1 | `[0; N]` 重复数组字面量 | 纯增量(唯一语言改动) | **极大** —— 解开所有 scratch buffer | 小(只碰 parser) |
| 0.2 | `math` 补齐(`abs`/`min`/`max`) | 纯增量 | 中(常用) | 小(纯 jhyy 实现) |
| 0.3 | `fmt` 补齐 + `io` 的输入侧 | 纯增量 | **大** | 中 |
| 0.4 | 命名去重 + § 15 拆出独立 std 规范 | **API break** | 小(整洁度) | 中 |

**为什么是这个顺序(三条理由):**

1. **先兑现全部纯增量收益,再一次性付 break 的代价。**
   反过来排(break 在第二位)⇒ 用户先承受 API 迁移,却还没拿到任何新能力 ⇒
   迁移是「纯损失」。⇒ break 挪到最后。
2. **`fmt` 补齐(0.3)在 `ptr_add` 收敛(0.4)之前做** ⇒ `fmt` 继续用**自己那份**
   `ptr_add` ⇒ **不引入跨模块 `import` 依赖边**(§ 13 的两级查找对 std 目录是否
   成不成立**至今未验** —— 见复核清单)⇒ 0.4 的方案选择不被提前污染。
3. **「打印一个整数」这个用户可感知验收点在 0.3 之后达成**
   (buffer 声明 318 字符 → 32 字符)⇒ 阶段 0 的价值**先兑现**,迁移成本后付。

#### 任务 0.1 —— `[0; N]` 重复数组字面量(parser 小改;0.3 的前置)

- 形状:`[expr; N]` —— `expr` 只求值一次,`N` 必须是编译期常量
- 位置:**`let` / 局部**。§ 12 的顶层 `const` 数组**不在本版范围** ——
  那里的元素编译器本来就不检查(§ 12),加 `[0; N]` 会让「`N` 是不是常量」变成新的静默面
- ⚠️ **本版唯一的语言改动** —— 刻意挑了最小那个:它解开 scratch buffer,
  且不牵动 ABI / codegen / 规范语义
- **为什么它排第一(ROI 最高的单点):** `fmt_i32(out_buf, val)` 要一个 **≥32 字节**
  的缓冲区,而今天用户只能**手写 32 个 `0 as u8`**(实测 `[0; N]` 是 parse error:
  `expected ], got ;`)⇒ **「打印一个整数」的 buffer 声明是 318 个字符**。
  ⇒ 这一条把那段噪声从 **318 字符压到 32 字符**(`[0; 32]`),**10×**。
  ⚠️ **它不减句数** —— 句数是 3(不含 import),要再降到 2 需要「格式化 + 打印」的
  组合 helper,而那会引入 `fmt` ↔ `io` 的**跨模块 import 依赖边** ——
  std 模块之间能否 import **至今未验**(复核清单第 2 条)⇒
  **不为了凑一个句数引入一条未验证的依赖边** ⇒ 见下面的验收门。

#### 任务 0.2 —— `math` 补齐(`abs` / `min` / `max`)

⚠️ **无 trait ⇒ 无泛型约束**(§ 11.3)⇒ **只能是 per-type 的家族**:

```
std_math_abs_i32 / std_math_abs_i64 / std_math_abs_f64
std_math_min_i32 / std_math_min_i64 / std_math_min_f64
std_math_max_i32 / std_math_max_i64 / std_math_max_f64
```

- `abs` / `min` / `max` **不需要 libm** ⇒ 纯 jhyy 实现(比现有 4 个 FFI 函数更独立)
- ⚠️ **不追求「一份代码覆盖所有类型」** —— 那要 trait(v4.12)⇒ 本版承认 per-type,
  **并在 § 15 的表里写清楚**,免得用户以为漏了

#### 任务 0.3 —— `fmt` 补齐 + `io` 的输入侧

**`fmt` 补 5 个**:`fmt_u32` / `fmt_u64` / `fmt_bool` / `fmt_char` / `fmt_ptr`
- ⚠️ **`fmt_f64` 本版不做** —— 见下面的「`fmt_f64` 决策」
- `fmt_bool` 的显示规则:**非零即 true**(与 § 2.1「bool 不归一化」对齐)
- ⚠️ **`fmt` 补齐在 `ptr_add` 收敛(0.4)之前做** —— `fmt` 继续用自己那份
  `ptr_add` ⇒ 不引入跨模块 `import` 依赖边(见上面「排序」理由 2)

**`io` 补输入侧**:`std_io_read_line(buf, cap) -> i64` / `std_io_read_i32() -> i32` /
`std_io_read_i64() -> i64` / `std_io_eof() -> bool`
- ⚠️ **缓冲区归调用方**(`read_line(buf, cap)`)⇒ **不引入隐藏的全局状态**
  (⚠️ 顶层非整数全局变量的初始化器是坏的,§ 3 ⇒ std **持有不了**全局状态)
- ⇒ 这条依赖任务 0.1 的 `[0; N]`(用户得能开缓冲区)

**`io` 补标准流句柄**:`std_io_stdin()` / `std_io_stdout()` / `std_io_stderr()` → `*u8`(FILE*)
- ⚠️ **放在 `io` 不放 `os`** —— `os` 走裸 POSIX/Win32 fd,`io` 走 libc FILE*,
  两边缓冲策略不同(§ 15 已记「依赖 libc 的 stdout/stderr 句柄」)⇒ **混用会乱序**
  ⇒ 句柄只从 `io` 出,`os` 保持纯 raw fd

#### 任务 0.4 —— 命名去重 + § 15 拆出独立的 std 规范(同版落地,一次迁移)

⚠️ **jhyy 没有 `pub`** ⇒ 模块内无法私有 ⇒ 去重只有两条路:

| 方案 | 做法 | 代价 |
|---|---|---|
| **(b) 默认** | `ptr_add` 的**公开面只留 `mem` 一处**;另 4 个模块不再定义同名公开符号 | 需 std 模块之间能互相 import ⇒ **启动时先验**(复核清单第 2 条) |
| (a) 备选 | 跨模块 `import mem;` 后用 `mem::ptr_add` | `fmt.jhyy` 现在**刻意不 import 任何模块**(注释:「避免 mangle 复杂度」)⇒ 引入依赖边 |

⇒ **本版默认做 (b)**:**把 5 份 `ptr_add` 收敛成 1 份实现**,
其余模块不再各自定义同名符号。**具体形态(改实现 / 改 import)由复核清单第 2 条拍板**,
判据 = std 模块之间的 `import` 能否解析(§ 13 的两级查找规则对 std 目录成不成立)。

- 同批:`string.jhyy` 里那份 arena 副本 ⇒ **收进 `string` 内部,不再以 `arena_*` 公开名出现**
- 同批:**§ 15 拆出独立 std 规范**(见下)
- ⚠️ **本次是公开 API break** ⇒ § 15 的表 + 迁移说明必须同步更新

**§ 15 拆出独立的 std 规范**(与命名去重**同版落地** —— API break 与「std 独立成规范」
**合成一次迁移**,不做两次):
- 新文件 `jhyy-std-v4.0.0.md`(**落点待定** —— 复核清单第 7 条;倾向与三份锁定规范同目录)
- 规格与三份锁定规范同档:锁版 + 稳定性承诺章节 + 每个模块的测试门清单
- 内容 = 现有 § 15 的表 + **本次收口后的 API**
- 登记进文档地图(`docs/internal/README.md`)

#### ⚠️ 两条**实测纠错**(2026-11-02 重排时核出来的 —— 原草案有误)

| 原草案的说法 | 实测 | 纠正 |
|---|---|---|
| 「`strlen_local` 与 `str_len` 语义重复 ⇒ **留一个**」 | ❌ **语义不同**:`strlen_local(s)` 扫 **NUL 结尾的 C 串**长度;`str_len(s)` 读 `*(s + 8)` = **自描述串**(`StringHeader`:`data @0` + `len @8`)的长度。`str_from_cstr` 靠 `strlen_local` 测 C 串长度 | ⇒ **两个都留**。照「留一个」做会**破坏 `str_from_cstr` / `str_from_bytes` 的语义** |
| 「同名跨模块 ⇒ 不限定调用时**静默取其一**」是隐患 | ⚠️ 5 份 `ptr_add` 的实现**逐字节相同**(`(p as i64 + off) as *u8`)⇒ 静默取其**行为完全一致** | ⇒ **不是正确性 bug**,是 API 整洁度问题 ⇒ 本条的优先级因此下降(排到最后) |

#### ⚠️ `fmt_f64` 决策 —— 本版**不做**,归属写明

「打印一个浮点数」有两种做法,**本版都不做**:

| 方案 | 为什么不做 |
|---|---|
| **C bridge 包装 `snprintf`** | ⚠️ **与本版方向相反** —— 任务 1 的目标是「用户程序不再链接任何 C runtime」⇒ 转换逻辑放 C ⇒ 任务 1 要再搬一遍 |
| 纯 jhyy 写十进制最短往返 | 「最短往返」要 Grisu/Ryu 级算法 ⇒ 纯 jhyy 写不出精确版;近似版又与「正确」冲突 |

⇒ **归属:任务 1(= 0-C 闭环那一版)**。那一版本来就要把 `printf` 搬进 jhyy
⇒ **f64 格式化跟它同批做,一件事不做两遍。**
⚠️ 阶段 0 的 § 15 表里**必须写明「`fmt_f64` 未实装」**,不要让用户以为漏了。

#### 阶段 0 明确不做(记录在案,免得下一轮重复讨论)

| 不做 | 为什么 | 归属 |
|---|---|---|
| **`Vec<T>` 泛型化 / `Option<T>` / `Result<T,E>`** | 技术上**今天就能做**(实测:`sizeof(T)` / `alignof(T)` 在泛型函数里可用;泛型 struct 持 `*T` 字段可用)⇒ **但它们是「容器语义」**:① 无 `Drop` ⇒ 仍要手写 `free`;② `defer` 不覆盖末表达式(§ 6.1)⇒ 隐式返回路径会漏释放;③ 无 trait ⇒ 泛型容器零防护 | 等 **v4.10**(`defer` 覆盖末表达式 + `fn(...)`)+ **v4.12**(trait)定形状 |
| **前缀统一**(`std_io_` → `io_` 等) | 那是 **60+ 个公开名的 break**,收益纯审美;而任务 1 本来就要动这些文件的真身 ⇒ **合并到那一版做,两次 break 合成一次** | 任务 1 |
| **C bridge 版 `printf` 家族** | 与 0-C 闭环方向相反(见上) | ❌ 永久不做 |
| **`print<T>` / `Display` 派发** | 要 trait | v4.12 |
| **`sort_by` / `map` / `filter`** | 要 `fn(...)` 类型 | v4.10 |
| **`println!` 编译期格式化宏** | 要前端宏设施(不是「无前置的小改动」) | **v4.10 任务 6** |

### 任务 1 —— 用户侧 runtime 的 jhyy 化

| 原 C 实现 | jhyy 侧对应 | 状态 |
|---|---|---|
| `malloc` / `free` | `std/arena.jhyy` | 已存在 |
| `memcpy` / `memset` | `std/mem.jhyy` | 已存在 |
| `printf` / 格式化 | `std/fmt.jhyy` | 已存在 |
| `open` / `read` / `write` / `exit` | `std/os.jhyy` | 已存在(W-103 接真 libc bridge) |

⚠️ **std lib 的已知历史**:v4.0.22 挖出三处真缺陷
(字节循环写穿 4n 字节 / `import string;` 编译失败 / arena 把分配互相踩 ⇒ AV)
—— **已全部真修**(W-139 / W-140 / W-141)。
根因是「**std 模块的测试全是 inline 副本**」⇒ 改真身零覆盖、副本给错误实现背书。
⇒ **本版动 std lib 时,必须改真身 + 跑 import 真身的测试**(6 个 `std_*_import.jhyy`)。

### 任务 2 —— 5 个 libc bridge 的 syscall 化

`std_os_open/close/read/write/exit` 现在是 `jhyy_helpers.c` 里的 libc bridge
⇒ 0-C 时改成直接调 syscall。
⚠️ **Windows 与 POSIX 的 `O_*` flag 差异要在这层翻译掉** ——
Windows 的 `_O_CREAT` = **0x100**,不是 POSIX 的 **0x40**(W-103 已记)。

### 任务 3 —— 链接行改造

删掉 `runtime.c` / `jhyy_helpers.c` ⇒ 链接行要跟着改
⇒ ⚠️ **注意 `--no-link` 与 side-file 的交互**(W-122 已修:每次编译开头清干净)。

### 任务 4 —— 性能门

**「0-C 闭环后,同一组用例的运行时不得比 0-C 前慢 > 阈值」** ——
阈值在启动时定(基线来自 v4.4.3 之后的 perf 序列)。

## Risks

**阶段 0**

| Risk | Impact | Mitigation |
|---|---|---|
| **公开 API break ⇒ 已有用户程序编不过** | 用户侧破坏 | 阶段 0 就在 break ⇒ **一次迁移**(break + 独立规范同版);§ 15 的表同步更新 |
| **顺序排错 ⇒ 用户先付 break 的代价却还没拿到新能力** | 迁移是「纯损失」 | 纯增量(0.1–0.3)**全部在前**,break(0.4)**在后**;「打印一个整数」的 buffer 声明在 0.1 之后即从 318 字符降到 32 字符 |
| **去重走错路**(把 `fmt` 的 `ptr_add` 删了但 `fmt` 又不能用 `mem::ptr_add`) | 编不过 | 复核清单第 2 条先验「std 模块之间能否 import」⇒ 验不过就退回「保留副本但 § 15 表只列一处」 |
| **`[0; N]` 的 `N` 不是编译期常量** ⇒ 新的静默面 | 静默错值 | 只在 `let`/局部做;`N` 必须常量否则报错;顶层 `const` 数组**不做** |
| **`io` 输入侧的缓冲区约定没写清** ⇒ 用户踩坑 | 体验差 | § 15 / 新 std 规范里写明「缓冲区归调用方 + 最小 256 字节」 |
| **阶段 0 与任务 1 改同一批文件** ⇒ 回归难定位 | 定位难 | 阶段 0 先合、跑一次绿;任务 1 后改 ⇒ **两个可单独回滚的点** |

**任务 1–4**

| Risk | Impact | Mitigation |
|---|---|---|
| std lib 覆盖不全 ⇒ 某些用户程序跑不了 | 功能回归 | 逐项盘点 `runtime.c` 提供的符号 |
| **改 std lib 真身却只跑 inline 副本测试** | 错误实现被背书 | ⚠️ 这正是 W-139/140/141 的根因 ⇒ **必须跑 import 真身的 6 个测试** |
