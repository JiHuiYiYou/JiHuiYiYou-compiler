## Context

**M5 是「0-C 闭环」项 —— 编译器自己不再依赖 C 代码。**

| Part | 内容 | 状态 |
|---|---|---|
| Part 1 | 删 `compiler/src/*.c` | ✅ v4.0.21 已做 |
| Part 2 | untrack QBE | ✅ v3.1.0 已做 |
| **Part 3** | **删 `compiler/runtime/runtime.c` + `compiler/src0/jhyy_helpers.c` 的用户侧 runtime** | ⬜ **唯一剩余** |
| Part 4 | 工具链自含闭环验证 | 部分 |

**为什么排在性能线之后**(2026-10-29 论证):

1. **M5 Part 3 是把成熟的 C runtime 换成新写的 jhyy 代码。**
   `runtime.c` + `jhyy_helpers.c` 现在给每个用户程序提供 malloc / memcpy / printf / exit。
   删掉它们 ⇒ 这些改走 **jhyy 侧的实现**
   (`std/arena.jhyy` / `std/mem.jhyy` / `std/fmt.jhyy` / `std/os.jhyy` 已存在)
   ⇒ **在一个已经比 gcc -O0 慢 3.4~4.7x 的后端上,再叠一层新写的、同样慢的代码。**
2. **先修后端,M5 Part 3 的成本才可控** —— 而且只有先有性能门,
   才能写出「0-C 闭环后程序不得比 0-C 前慢 > X%」这条**真正有意义**的门。
3. **寄存器分配器直接受益** —— std lib 的热路径(arena 分配、memcpy)拿到寄存器分配后,
   M5 Part 3 的性能代价会小得多。

⚠️ **注意方向张力**:W-103 往 `jhyy_helpers.c` 加了 **5 个 libc bridge**
(`std_os_open/close/read/write/exit`),M5 Part 3 要删 C runtime。
**取舍**:真的 0-C 时换掉的是 **bridge 的实现**(改 syscall),
`std/os.jhyy` 的 `std_os_*` **一行不动**(台账 W-103 已记)。

---

## Goal

1. **用户程序不再链接任何 C runtime** ⇒ 真正的 0-C 闭环
2. **`std/` 六个模块成为唯一的 runtime 提供者** —— 且它们**真的可被用户代码 import**
   (W-103 已落地「两级查找:main 文件旁边 → std lib 目录」)
3. **性能不退化**:0-C 闭环后同一组用例的运行时不得比 0-C 前慢 > 阈值
4. **自举闭环仍 PASS**

## Scope

### 任务 1 —— 用户侧 runtime 的 jhyy 化

| 原 C 实现 | jhyy 侧对应 | 状态 |
|---|---|---|
| `malloc` / `free` | `std/arena.jhyy` | 已存在 |
| `memcpy` / `memset` | `std/mem.jhyy` | 已存在 |
| `printf` / 格式化 | `std/fmt.jhyy` | 已存在 |
| `open` / `read` / `write` / `exit` | `std/os.jhyy` | 已存在(W-103 接真 libc bridge) |

⚠️ **std lib 的已知历史**:v4.0.22 挖出三处真缺陷
(字节循环写穿 4n 字节 / `import string;` 编译失败 / arena 把分配互相踩 ⇒ AV)
—— **已全部真修**(W-139 / W-140 / W-141)。
根因是「**6 个 std 模块的测试全是 inline 副本**」⇒ 改真身零覆盖、副本给错误实现背书。
⇒ **本版动 std lib 时,必须改真身 + 跑 import 真身的测试**(6 个 `std_*_import.jhyy`)。

### 任务 2 —— 5 个 libc bridge 的 syscall 化

`std_os_open/close/read/write/exit` 现在是 `jhyy_helpers.c` 里的 libc bridge
⇒ 0-C 时改成直接调 syscall。
⚠️ **Windows 与 POSIX 的 `O_*` flag 差异要在这层翻译掉** ——
Windows 的 `_O_CREAT` = **0x100**,不是 POSIX 的 **0x40**(W-103 已记)。

### 任务 3 —— 链接行改造

删掉 `runtime.c` / `jhyy_helpers.c` ⇒ 链接行要跟着改
⇒ ⚠️ **注意 `--no-link` 与 side-file 的交互**(W-122 已修:每次编译开头清干净)。

### 任务 4 —— 性能门

**「0-C 闭环后,同一组用例的运行时不得比 0-C 前慢 > 阈值」** ——
阈值在启动时定(基线来自 v4.4.3 之后的 perf 序列)。

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| std lib 覆盖不全 ⇒ 某些用户程序跑不了 | 功能回归 | 逐项盘点 `runtime.c` 提供的符号 |
| **改 std lib 真身却只跑 inline 副本测试** | 错误实现被背书 | ⚠️ 这正是 W-139/140/141 的根因 ⇒ **必须跑 import 真身的 6 个测试** |
| Windows/POSIX flag 差异漏翻译 | 打开/创建行为错 | `O_*` 差异在 bridge 这一层统一翻译 |
| 0-C 后性能显著退化 | 目标落空 | 性能门 + 阈值;必要时先补 std lib |
| 删 C runtime 影响自举 | 自举断 | 自举闭环门常驻 |
