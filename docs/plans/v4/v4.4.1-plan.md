## Context

**v4.4.0 的保守子集靠「期间无 call」这个限制换来的。**
一个 temp 只有在 def 与**所有** use 落在同一基本块、且期间没有 call 时才进寄存器。
⇒ 覆盖率封顶在 **75.7%**(实测 56719 / 74950)。

**这一版拆掉「无 call」这个限制** —— 它需要三样东西:
① 真正的**活跃区间分析**(跨越 call 时,值要么进 callee-saved,要么落槽)
② **寄存器类**(GPR vs XMM)—— 否则浮点值会被塞进整数寄存器
③ **`MAX_TEMPS=64` 动态化** —— 真实 temp 空间到 **60656**

⚠️ **这一版同时是「禁 XMM 溢出 / 禁 red zone」约束真正开始承压的版本** ——
v4.4.0 阶段二已加了持久断言,但那时还没有跨 call 的值需要分配;
本版开始,「XMM 能不能当溢出目标」变成一个**真实的调度问题**,而不只是一条断言。

---

## Goal

1. **跨 call 的值有明确归属** —— callee-saved 寄存器或落槽,**没有第三种**
2. **寄存器类正确** —— GPR 与 XMM 不混用
3. **temp 空间不再被 64 卡住** —— 真实 temp id 到 60656
4. 覆盖率从 75.7% 往上走(**具体目标在启动时按 v4.4.0 实测基线定**)

---

## Scope

### 任务 1 —— 活跃区间分析

跨 call 的值需要知道「从 def 到最后一个 use 之间,有没有 call」。
- 纯寄存器持有 ⇒ 必须是 **callee-saved**
- 否则 ⇒ **落槽**(等价于今天的行为,不是错误)

⚠️ 寄存器池现状:**5 个全是 callee-saved**(`%rbx` `%r12` `%r13` `%r14` `%r15`),
且后端一个都没用过(真实产物里各出现 1 次,在注释里)
⇒ callee-saved 天然是跨 call 安全的,这是 v4.4.0 选它们的原因。

⚠️ **不能用** `%rsi` / `%rdi`:它们在 **SysV** 是第 1/2 个参数寄存器(后端要用)。

### 任务 2 —— 寄存器类(GPR vs XMM)

浮点类型在语料 A 里只占 **9 条** ⇒ 可忽略(2026-10-29 实测)。
⇒ 本任务的现实规模很小,但**必须做对**,否则将来浮点变多时是静默错误。

### 任务 3 —— `MAX_TEMPS=64` 动态化

真实 temp 空间到 **60656**(vs 当前固定 64)。
⚠️ 这与台账 **W-120**(temp 表越界 → 静默算错值)是同一族问题:
W-120 的教训是「**响亮失败远好过静默错代码**」⇒ 动态化后必须保留越界响亮失败。

### 任务 4 —— 「禁 XMM 溢出 / 禁 red zone」从断言升级为**调度规则**

v4.4.0 的持久断言是「检测到违规就失败」;
本版开始,XMM 与 red zone 变成**分配器要考虑的事** ⇒ 断言升级为「分配时就不选它」。

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| 跨 call 的值被 clobber ⇒ **静默错值** | 极难查 | callee-saved 白名单 + 落槽兜底 + 响亮失败 |
| 浮点值进 GPR ⇒ 静默位模式错 | 难查 | 寄存器类显式建模;浮点走 XMM 或落槽 |
| `MAX_TEMPS` 扩容踩 W-120 同款坑 | 静默算错值 | 越界响亮失败(沿用 W-120 修法) |
| 活跃区间分析写错 ⇒ 大范围回归 | 高 | 分步 ship,每步 `-O0` 逐字节不变 |
| 覆盖率提升不明显 | 性能目标落空 | 启动时先量(v4.4.0 基线),不够则停下重新评估 |
