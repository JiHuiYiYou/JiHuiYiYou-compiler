# 自研后端性能线 —— v4.2 及以后的排期

**状态:** 🔄 **2026-10-29 立线**。v4.2 起的主线 = **自研后端性能线**
(2026-10-29 user 拍板:「自研后端性能线为主线」,语言特性链整体后移)。

**定位:** 自研后端**就是编译器本身** —— `compiler/src/*.c` 已于 v4.0.21 删光,
`jhyy.exe` 由它自己编 `src0/main.jhyy`(自举)。所以后端性能不是「锦上添花」,
它直接乘在两件事上:① 项目自己的迭代速度(自举编译 **12.5s**);
② 用户写的每一个 jhyy 程序。

**起点:** [`docs/perf/self-backend-baseline-2026-10-29.md`](../../perf/self-backend-baseline-2026-10-29.md)
—— 第一份**可信**的运行时基线(旧 `bench.sh` 的计时器是坏的)。

2. **CLI 根本没有 `-O` 开关**(只有 `-o` / `--target=`)

## 一、基线(2026-10-29 实测)

| 程序 | gcc -O0 | gcc -O2 | **jhyy** | jhyy/gcc-O0 | 访存指令占比 |
|---|---|---|---|---|---|
| fib | 89.7ms | 55.5ms | **307.9ms** | **3.43x** | 49% |
| ack | 28.5ms | 22.9ms | **134.7ms** | **4.73x** | 53% |
| nq  | 20.4ms | 19.1ms | **32.0ms**  | 1.57x | 69% |

**参照系 = gcc -O0**,不是 gcc -O2 —— 这三个程序 gcc -O0 ≈ gcc -O2
(递归调用开销主导),所以差距几乎全在 codegen 质量而非优化 pass。
`bench.sh` 那个 `1.1x` 对 gcc -O2 的门槛**不可达**(gcc 自己都达不到)。

⚠️ 但 **-O0 只是下限**:真实用户程序(循环/数组/浮点)上 gcc -O2 ≫ gcc -O0。
**v4.2 的目标是把 3.4x 拉到 2x 以内;v4.4 的目标是让 1x 成为可达的长期目标。**

### v4.2.1 —— 帧尺寸公式修复 ⭐

**改动**(`codegen_amd64_emit_ctrl.jhyy:565`):

```
现状:  alloc_pool_size = 8192 + per_fn_alloc
改为:  alloc_pool_size = 32 + (local_max+1)*8 + per_fn_alloc
```

`local_max` 是该函数**精确已知**的 local temp 上限(`emit_ctrl.jhyy:544`);
8192 是「公式池最深 -32792」的**旧 4096-temp 时代**遗留常量
(`codegen_amd64_state.jhyy:1153` 自陈)。

**预期收益**:fib **-41%**(实测消融:8384 帧 + chkstk = 335ms → 128 帧无 chkstk = 197ms);
自举产物 **1045 个函数全部**从 ≥8352 字节降到几百字节 ⇒ **`___chkstk_ms` 归零**。

**风险与对策**:

| 风险 | 对策 |
|---|---|
| pre-scan `per_fn_alloc` 低估 ⇒ 池长出帧外 ⇒ 静默踩坏栈 | 该估算**自带余量**(`total_a + max(total_a/2, 8, 64-bit binop 数)*8`,`state.jhyy:2148`);**再加响亮失败**:函数体 emit 完检查池底未越过预留边界,越了直接编译失败(沿用 W-120 / W-130 的规矩) |
| 帧变小后暴露原本被大帧意外撑住的越界 | 全量 regress + 自举闭环 + `artifact_checks.sh` 14 条门全绿 |
| `per_fn_frame` 门(f500 vs f1099 帧比 < 4)语义变化 | 重新验 + 造红灯 |

**新增常驻门** `artifact_checks.sh frame_bloat`:断言「真实函数帧中位数 < 1KB」
且「`___chkstk_ms` 调用数 == 0」—— **直接锁死本轮收益,防回退**。

**gate**: 全量 regress 绿 + 自举闭环绿 + `artifact_checks` 绿 + **perf 数字改善 ≥ 30%**
+ `make` 后 `git add compiler/build/bin/jhyy.exe`(CI 的 artifact-fresh 步会比对它)。

#### ✅ 完成记录(2026-10-29,台账 W-167)

**改法**(`codegen_amd64_emit_ctrl.jhyy`):
```
alloc_pool_size = 8192 + per_fn_alloc
⇒ alloc_pool_size = 32 + (local_max+1)*8 + per_fn_alloc
```
`local_max` 是**该函数精确已知**的 local temp 上限(`per_fn_max[cur] - per_fn_max[cur-1]`)
⇒ 帧终于按函数实际需要算。

**实测(自举产物 1045 个真实函数)**:

| | 修前 | 修后 |
|---|---|---|
| 帧 min / 中位 | 8352 / 8368 | **208 / 288** |
| 总预留栈 | 9.1 MB | **1.5 MB** (-84%) |
| 帧 >4096 / chkstk 调用 | 1045 / 1045(100%) | **46 / 46(4.4%)** |
| 最紧函数的余量 | 2664 B | **14584 B** |
| fib / ack jhyy/gcc-O0 | 3.46x / 4.65x | **2.14x / 2.13x** |
| 自举编译耗时 | 6676ms | **5605ms** (-16%) |

⚠️ **帧 max 变大(237680 → 349232)但不是变紧** —— 旧公式用 `max(...)`,
在公式池主导时**把 `per_fn_alloc` 丢掉了** ⇒ 值池向下生长不受帧保护
(`parser__parse_expr` 只剩 2664 字节余量)。新公式把两项**相加**
⇒ **顺手修掉一个潜在下溢**,大函数现在余量更足。

**门(新增两条,都验过红灯)**:
- `artifact_checks.sh frame_bloat` —— 修之前**必然红**(报「小函数的帧 8384B > 1024B」)
- `artifact_checks.sh frame_slots` —— 每个 rbp 相对槽位必须落在该函数的帧内
  (修之前就该是绿的 —— 已验;它是「帧算小的安全网」)

**验收(全绿)**:

### v4.2.2 —— peephole 4096 限制真修

**为什么**:`.s` 超过 4096 字节就整段跳过 peephole(`peephole.jhyy:545`)。
真实程序(自举产物 10.4MB)永远跳过 ⇒ **peephole 只在 hello-world 级输入上跑过**。
不修这条,v4.4 之后任何 .s 级 pass 的验证都缺一个可信的 .s 级工具。

**根因**: `peephole_concat_loop` 静默崩(W-074.6.1 PARTIAL)。
**gate**: 自举产物的 `.s` 上 peephole 真的跑了(可观测:fold 计数 > 0),且回归不退步。

### v4.3 —— IR 层优化框架 + `-O` 开关

**为什么是 IR 层而不是 .s 层**:IR 已经是 SSA(前端产的);在 IR 层做 pass
⇒ temp 数下降 ⇒ **帧进一步变小**(与 v4.2.1 叠加),而且是「少算」而不是
「算得更巧」—— 对一个 3.4x 的差距,少算比算巧更值钱。

**内容**:

- `-O0`(默认) / `-O1` 开关 —— **CLI 现在完全没有 `-O`**。
  默认保持 `-O0` ⇒ 现有 byte-equal 门全部保持绿,零风险。
- IR pass 框架 + 常量折叠 / 代数化简 / DCE / 不可达代码消除
  = 原 backlog 第 8 项按新设计重做(原 backlog 文档已删,见 § 四)(原设计假设「后端已有 peephole 兜底」,已过时)

**gate**: `-O1` 与 `-O0` 语义等价(同一组用例输出逐字相同);
优化后 `.s` 长度 ≤ 不优化 +5%;**`-O0` 必须仍 byte-equal**。

### v4.3.1 —— `artifact_checks.sh` 去文本耦合

**为什么现在做**:这 14 条门里有 4 条是**汇编文本断言**
(`holds_bitmap` 认死 `%r8` + `%tN` 注释格式;`sysv_memory_class` 认死
`movq %r10, 0(%rsp)`;`sysv_arg_spill` 认死 `r8d`/`r9d`/`16(%rbp)`;
`per_fn_frame` 认死 `subq $N, %rsp` 的形状)。

v4.4 的寄存器分配器会**同时**改寄存器名、栈槽编号、帧布局 ⇒ 这 4 条会红
⇒ 需要手工改门 ⇒ 改门和改后端混在一起会掩盖真实回归。

**做法**:能改成语义判定的改语义判定(例如「base temp id > 65536」
而不是「某一行含 `, %r8`」);改不动的登记成 expected-FAIL 风格。

### v4.4 —— 真寄存器分配器

**这是本线的重头戏,也是旧报告估得最不准的一项。**
`regalloc.jhyy` 的 972 行里,真正可复用的是 **~375 行算法**
(区间构造 + 确定性贪心分配);另外 ~400 行是常量表 / 结构体访问器 / 寄存器名表。
**hard 90% 未实现**:

| 子版本 | 内容 |
|---|---|
| **v4.4.0** | 后端加「temp → 寄存器 / 槽位」的**位置映射** + 一个**前瞻窗口**的寄存器缓存(受限线性扫描):定义 temp 时放进空闲寄存器,使用时从寄存器读(而不是从栈槽)。**保守子集** —— 只在「该 temp 的使用点落在窗口内」时启用 |
| **v4.4.1** | **call-clobber**:跨调用的值必须 callee-saved 或落槽(⇒ 这一步才需要真正的活跃区间分析)+ 寄存器类(GPR vs XMM)+ `MAX_TEMPS=64` 动态化(真实 temp 空间到 60656) |
| **v4.4.2** | 跨基本块 / **phi 解析改成并行移动**(现在是 slot-based 顺序 copy,`emit_call.jhyy:1167`,寄存器化后必须做并行赋值 + 环打破) |
| **v4.4.3** | 门 + perf 验证 + 把 `artifact_checks.sh` 的 4 条汇编文本断言去文本耦合 |

**为什么从「前瞻窗口」起步而不是直接做完整分配器** —— 2026-10-29 测量:
**52% 的 temp 只用一次;30.5% 紧接着下一条就被用;47.8% 在 4 条之内用**。
⇒ 一个带前瞻窗口的受限线性扫描就能覆盖 **~76% 的 temp**(实测 75.7%),
而完整的 CFG + 活跃区间 + phi 并行移动是好几倍的工程量。
**先拿 48%,再谈剩下的。**

⚠️ **v4.4.0 是本线第一个真正动 emit 层的版本** —— 风险比 v4.2.x 高一个量级
(v4.2.x 只动一个公式 / 一个门)。**必须**:
- **`-O0` 的产物逐字节不变**(现有门全绿)⇒ 寄存器分配**默认关**,靠 flag 开
- 新门:「`-O0` 产物 sha 与基线一致」+「`-O1` 产物访存指令数显著下降」
- 分步 ship,每步能单独回滚

**gate**: 每子版本独立可 ship;`artifact_checks` 的 4 条文本耦合门在 v4.3.1
之后不再拦路;全量 regress + 自举闭环 + perf 数字每版记录。

#### v4.4.0 实施要点(2026-10-29 测量 + 源码勘察得出)

**可寄存器化的比例(语料 A = 编译器自己的 142763 行 IL):**

| 约束 | 覆盖(def 数) |
|---|---|
| 同基本块 + 期间无 call + 整数类型(**保守子集**) | **58070 / 74950 = 77.5%** |
| 实际分配到寄存器(5 个寄存器池;池满的 1345 个退化成栈槽) | **56719 = 75.7%** |
| 浮点类型 | 只占 9 条 ⇒ 可忽略 |

**⇒ 保守子集就够,不需要一上来就做完整的 CFG 活跃区间分析。**

**寄存器池:** `%rbx` `%r12` `%r13` `%r14` `%r15`
—— 扫遍 `codegen_amd64_emit_*.jhyy` + `abi_*.jhyy`,这 5 个**一个都没被用过**
(真实产物里各出现 1 次,在注释里)⇒ 纯空闲。
- 全是 **callee-saved** ⇒ 跨 call 安全 ⇒ 保守子集的「期间无 call」限制
  将来可以放宽(那是 v4.4.1)
- ⚠️ 不能用 `%rsi` / `%rdi`:它们在 **SysV** 是第 1/2 个参数寄存器(后端要用)
- **保守子集下同时活跃数最多 15**(全模块极值)⇒ 5 个寄存器会让 **1345** 个 def
  退化成落槽(= 今天的行为,不是错误);池大小 vs 覆盖率实测:
  3 → 68.2% · **5 → 75.7%** · 6 → 77.0% · **7 → 77.5%(饱和)**

**序言 / 尾声:**
- `ret` 只在**一个地方** emit(`emit_ctrl.jhyy:314` 的 `emit_ret`)⇒ 尾声统一收口 ✓
- 序言在 `emit_func_header` ⇒ 加 `pushq %rbx` 等(必须在 `movq %rsp, %rbp` **之后**,
  否则 rbp 相对的槽位偏移全错)
- ⚠️ **16 字节对齐**:序言 push 了 k 个寄存器 ⇒ `%rsp ≡ -8k (mod 16)`
  ⇒ `subq $N, %rsp` 的 N 必须 ≡ 8k (mod 16)⇒ **k 为奇数时 N 要 +8**
- ⚠️ `___chkstk_ms` 的探测量必须含 push 的那 8k 字节(否则跳过 guard page)

**改动面(实测:48 个取槽位偏移的调用点):**

| 文件 | 调用点数 |
|---|---|
| `codegen_amd64_emit_call.jhyy` | 16 |
| `codegen_amd64_emit_sse.jhyy` | 17 |
| `codegen_amd64_emit_mem.jhyy` | 10 |
| `codegen_amd64_emit_ctrl.jhyy` | 5 |

⇒ 引入**两个收口 helper**(而不是在 48 处各写一遍判断):
- `emit_load_temp(state, temp, dest_reg, target_tag)` —— 从寄存器或槽位读进 dest_reg
- `emit_store_temp(state, temp, src_reg, target_tag)` —— 写进寄存器或槽位

**⚠️ 安全网(本版最关键的一条):** 如果某个 temp 被分配了寄存器,
但仍有一条路径**按槽位**读/写它 ⇒ **静默读到垃圾**。
⇒ 在**所有**按槽位访问 temp 的路径上加**响亮失败**
(沿用 W-120 / W-130 的「响亮失败远好过静默错代码」规矩):
分配了寄存器的 temp 一旦走槽位路径 ⇒ **编译直接失败**。
⇒ 这样「漏改的调用点」会被全量回归当场抓住,而不是产出错代码。

⚠️ **守卫必须放在 `jh_write_file` 之前**(2026-10-30 实测踩过):
第一版只把它放在 in-mem 路径,文件路径(`codegen_amd64_run`)漏了
⇒ 守卫**响了**,但**错的 .s 和 .exe 照样落地、exit code 还是 0**
⇒ 守卫形同虚设(它只是打印了一行字)。
⇒ **两条路径都要查,而且都要在写盘之前**。

**门:**
- `-O0` 产物**逐字节不变**(寄存器分配**默认关**,靠 flag 开)⇒ 现有门全绿
- 新门:「开了寄存器分配后,产物里的访存指令数显著下降」
  (用 `runtime_perf.py` 已有的静态指标 `mem` 计数)
- 分配了寄存器但走槽位路径 ⇒ 编译失败(上面那条)

#### v4.4.0 阶段二 —— emit 层消费寄存器(**下一个动作**)

阶段一(2026-10-30 完成)只做**基础设施 + 安全网**,产物逐字节不变;
**阶段二才让 emit 层真的按 temp id 取位置**(`emit_mov_temp_to_reg` /
`emit_mov_reg_to_temp` 改成按 temp 取位置,操作数读取改走 `emit_operand_temp`)。
**默认仍关**,靠 flag 开。

**三条硬约束必须与阶段二同期落地** —— 前两条来自 OS 线的审核(见
[`docs/archive/plans/v4/version-schedule.md`](../../archive/plans/v4/version-schedule.md) § 五.5),第三条是阶段一的延续:

| # | 约束 | 为什么必须同期 | 形状 |
|---|---|---|---|
| 1 | **排除 volatile temp** | `emit_volatile`(`codegen_amd64_emit_call.jhyy:2742`)**只发注释、什么都不做**;后端**能**识别 volatile(`qbe_type == -1`)却**没有拒绝机制**;阶段一的资格判据**没有 volatile 这一维** ⇒ 寄存器化会让 volatile load 被缓存 ⇒ **MMIO 读静默失效** | 显式排除 + 响亮失败 |
| 2 | **禁 XMM 溢出 / 禁 red zone** | `docs/coordination/JHYY_编译器侧设计终版.md §3.3 接口 B` 判定这两个约束「必须与寄存器分配**同一期**落地」(原载于已合并的 `设计自审 §3.1`) | 持久断言(编译期上下文属性) |
| 3 | **槽位访问响亮失败** | 阶段一已有:分配了寄存器却走槽位路径 ⇒ 编译失败。阶段二要保证**所有**槽位访问点都走收口 helper ⇒ 漏改的调用点当场被抓 | 沿用阶段一 |

> ⚠️ **约束 1 与 `Cap` 草案的 `ptr<io>` 是同一件事**:`ptr<io>` 要求
> 「默认 volatile、不合并访问、禁止推测读」⇒ 语言的承诺要靠后端这条约束兑现
> ⇒ **必须在 `ptr<io>` 落地之前做完**,否则语言层写了承诺、后端给不了。

### v4.5 —— M5 Part 3(0-C 闭环)

**M5 的现状**:Part 1(删 `compiler/src/*.c`)✅ v4.0.21 已做;
Part 2(untrack QBE)✅ v3.1.0 已做;
**Part 3(删 `compiler/runtime/runtime.c` + `compiler/src0/jhyy_helpers.c` 的
用户侧 runtime)⬜ 唯一剩余**;Part 4(工具链自含闭环验证)部分。

**为什么排在性能线之后**(2026-10-29 论证):

1. **M5 Part 3 是把成熟的 C runtime 换成新写的 jhyy 代码。**
   `runtime.c` + `jhyy_helpers.c` 现在给每个用户程序提供 malloc / memcpy /
   printf / exit。删掉它们 ⇒ 这些改走 **jhyy 侧的实现**
   (`std/arena.jhyy`、`std/mem.jhyy`、`std/fmt.jhyy`、`std/os.jhyy` 已存在)。
   ⇒ **在一个已经比 gcc -O0 慢 3.4~4.7x 的后端上,再叠一层新写的、同样慢的代码。**
2. **先修后端,M5 Part 3 的成本才可控** —— 而且只有先有性能门,
   才能写出「0-C 闭环后程序不得比 0-C 前慢 > X%」这条真正有意义的门。
3. **寄存器分配器直接受益** —— std lib 的热路径(arena 分配、memcpy)
   拿到寄存器分配后,M5 Part 3 的性能代价会小得多。

**新增门**:「0-C 闭环后,同一组用例的运行时不得比 0-C 前慢 > 阈值」。

⚠️ **注意方向张力**:W-103 往 `jhyy_helpers.c` 加了 5 个 libc bridge,
M5 Part 3 要删 C runtime。**取舍**:真的 0-C 时换掉的是**bridge 的实现**
(改 syscall),`std/os.jhyy` 的 `std_os_*` 一行不动(台账 W-103 已记)。

`lifetime → closure → dyn Trait → HKT`(强串行链)+ async / const generic /

## 三之二、2026-10-29 测量驱动的重排:**v4.2.2 与 v4.3.0 的性能价值 ≈ 0**

上面两版(v4.2.2 peephole / v4.3.0 IR 优化)是**照着「缺什么补什么」的直觉**排的。
v4.2.1 落地后做了逐项测量,结论是**它们的性能价值远小于预期** —— 这条必须写下来,
否则下一轮又会照着原顺序去啃两个不值得的版本。

### 测量方法

- **语料 A**:编译器自己的 `src0/main.jhyy`(142763 行 IL,73473 条 IL 指令)——
  本仓最大的真实代码库
- **语料 B**:`compiler/tests/examples/` 的 235 个能编译的测试程序(38453 行 IL)
- 工具:直接扫 IL 文本(不依赖编译器行为)

### 逐项测量

| 版本 | 声称的价值 | **实测机会数** | 结论 |
|---|---|---|---|
| **v4.2.2** peephole | 3 条规则折叠 no-op | 语料 A:**54**(全是 `addq $0, %rax`);Rule 2 / Rule 4 各 **0** | 2.5M 条机器指令里的 **0.002%** |
| **v4.3.0** 常量折叠 | `2 + 3` → `5` | 语料 A:**0**;语料 B:**84** | ⚠️ **前端本来就不折叠**(`%t2 = copy 2; %t3 = copy 3; %t4 = add %t2, %t3`)⇒ 折叠**确实缺失**,但真实代码里字面量算术本来就少 |
| **v4.3.0** 代数化简 | `x + 0` → `x` | 语料 A:**54**;语料 B:**424** | 小 |
| **v4.3.0** DCE | 删死指令 | 语料 A:**42**(0.1%);语料 B:**193** | 前端产出的 SSA **本来就干净** |
| **v4.4** 寄存器分配 | 消掉 load/store 往返 | **75.7% 的 def 能拿到寄存器**(实测 56719 / 74950)⇒ 少 **113438 条访存指令**,占机器码的 **36%** | ⭐ **唯一的数量级杠杆** |

⇒ **IR 层优化三项加起来 ≈ 语料 B 的 1.8% 的 IL 指令**(84 + 424 + 193 / 38453)。

⚠️ **2026-10-30 更正:本节原先写的「v4.4 覆盖 38.3% 的 IL 指令」是错的。**
那版 Python 参考实现**只扫 def 行来找 use** ⇒ 漏掉了 `store` / `ret` / `jnz` 等
**非 def 指令里的 use** ⇒ 活跃区间被低估 ⇒ 覆盖率被低估。
修正后的参考实现(扫全部行)与 jhyy 侧的实现**逐项对上**:
eligible **58070 = 58070**、池满 **1345 = 1345**、分配 56725 vs 56719(差 6 = 同 last_use 的定序细节)。

⇒ **两套独立实现逐项对上**(参考实现:`scripts/dev/regalloc_reference.py`)。
⚠️ **对拍当场抓出了参考实现自己的两个 bug** —— 这正是它存在的意义:
① 「哪些 op 定义 temp」被写成白名单 ⇒ 漏了 498 条 ⇒ 合格候选少算 ~3000
② **call 计数在 append 之前自增** ⇒ 「call 定义的 temp」与「下一个 call 用的 temp」
   的 def_call / use_call 差 1 ⇒ 合格的被误判成不合格
② **就是当初「38.3%」那个错数的根因** —— 一次测量错误,差点据此否掉整个方案。

| | 修正前(错) | 修正后(对) |
|---|---|---|
| 合格(def+use 同块 + 期间无 call + 整数) | 「38.3% 的 IL 指令」 | **57976 / 74798 = 77.5% 的 def** |
| 实际分配到寄存器(5 个寄存器池) | — | **56625 = 75.7% 的 def** |
| 单块内最大同时活跃数 | 6 | **15** |
| 机器码里访存指令占比 | 49% | **68.2%**(317543 条指令里 216619 条访存) |

### 为什么会这样(根因)

前端**已经把常量表达式在源码层算掉了**(所以 IL 里几乎没有 const+const 的 binop),
也**已经把死代码清掉了**(SSA 产出干净)。剩下没被折叠的,全都是
「一个操作数是变量」—— 那本来就**不该**被常量折叠。

⇒ **「缺常量折叠」这个前提是错的。** 真正缺的是**寄存器分配**:
后端把**每个** SSA temp 物化成一个栈槽,于是每个值都是
「load 槽 → 算 → store 槽」。语料 A 里 `copy` 指令 17414 条(每个 SSA 值一次物化),
机器码里 **49% 的指令是访存**。

### v4.4 的设计要点(由上面的测量定的,不是拍脑袋)

测量说:**52% 的 temp 只用一次,30.5% 紧接着下一条就被用,47.8% 在 4 条之内**。

⇒ **不需要一上来就做完整的 CFG + 活跃区间 + phi 并行移动**。
一个**带前瞻窗口的寄存器缓存**(受限线性扫描)就能覆盖 **~76% 的 temp**(实测 75.7%):

| 子版本 | 内容 |
|---|---|
| **v4.4.0** | 后端加「temp → 寄存器 / 槽位」的位置映射;一个**前瞻窗口**的寄存器缓存:定义 temp 时放进空闲寄存器,使用时从寄存器读(而非槽位);**保守子集** —— 只在「该 temp 的使用点在窗口内」时启用 |
| **v4.4.1** | call-clobber 处理:跨调用的值必须 callee-saved 或落槽(⇒ 这一步才需要真正的活跃区间分析) |
| **v4.4.2** | 跨基本块 / phi(并行移动 + 环打破) |
| **v4.4.3** | 门 + perf 验证 + 把 `artifact_checks.sh` 的 4 条汇编文本断言去耦合 |

⚠️ **v4.4.0 是本线第一个真正动 emit 层的版本** —— 风险比前两版高一个量级
(前两版只动一个公式 / 一个门)。**必须**:
- `-O0` 的产物**逐字节不变**(现有门全绿)⇒ 寄存器分配**默认关**,靠 flag 开
- 新门:「`-O0` 产物 sha 与基线一致」+「`-O1` 产物访存指令数显著下降」
- 分步 ship,每步都能单独回滚
