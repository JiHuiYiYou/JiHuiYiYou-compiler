## Context

**为什么在发版前做测评。** 仓库要发一个稳定版本。发之前要把"跑得对不对"和
"跑得快不快"两条线补齐，产出**对外可发布**的一组数字。

**现状不是"没有测量"，而是"测得太窄"**（2026-11-03 实测）：

| 维度 | 已有 | 缺什么 |
|---|---|---|
| 性能 | `scripts/dev/bench/runtime_perf.py`：3 道题（fib/ack/nq），stdout 逐字比对，静态指标当 CI 硬门 | 题量少；**3 道题全是递归主导**（gcc -O0 ≈ gcc -O2）⇒ **参照系偏袒 jhyy**；只有 min-of-7；没有编译耗时 / 二进制体积 / 测量地板 |
| 正确性 | 285 条回归 + 47 份 golden AST + 30 条编译器变异测试 + jhyy↔gcc 的 SysV ABI 对拍 | **没有随机程序生成 / 差分测试**（v4.3.3） |
| 工程性 | **零数据** | 全缺 |

⇒ **要补的不是"再写几道题"，而是「一个可复现的测评套件 + 一条差分测试通道 + 一份写死的口径」。**

**⚠️ 一个必须先认清的现实**（关系到"对外发布"这个决定）：
现有 3 道题上 jhyy 是 gcc `-O0` 的 2.14x / 2.13x / 1.40x，但那 3 道题
**全是递归调用开销主导** ⇒ 这个数字偏袒 jhyy。
新题刻意选 **gcc `-O2` 明显优于 `-O0`** 的场景（循环 / 数组 / 浮点密集），
而 jhyy **没有任何优化器、寄存器分配未接线**（49%~68% 的机器指令是访存）
⇒ **新题上的倍数很可能明显更差**。
⇒ 这不是本线能解决的问题（要等 v4.4.x 的寄存器分配 + v4.4.5 的 IR 优化）。
⇒ **但发出去的表必须是诚实的** —— 宁可一张难看但口径写死的表。

## Goal（可度量）

1. `bench/` 目录落地，`bench/tasks/` 成为**基准题目的唯一真源**。
2. 新门 `bench-perf` 进 CI：正确性 + 二进制体积 + 静态指标硬门，**墙钟只报告**。
3. **二进制体积此前没有任何门在管** ⇒ 本格新增这道约束。
4. 口径写死：`bench/METHODOLOGY.md`（参照系 / 维度定义 / **16 条已知偏差**）。
5. **搬迁零影响**：fib/ack/nq 从 `runtime_perf.py` 的内联字符串搬到 `bench/tasks/`
   ⇒ `runtime_perf.baseline.json` **一个字节都不用改**。

## Scope

### ① `bench/` 目录

| 路径 | 内容 |
|---|---|
| `bench/README.md` | 怎么跑（中文，仓内文档） |
| `bench/METHODOLOGY.md` | 口径 / 参照系 / 维度 / 已知偏差 ⭐（中文，仓内文档） |
| `bench/bench.py` | 驱动：正确性 + 墙钟分布 + 静态指标 + 工程性指标 + 可发布输出 |
| `bench/tasks/<name>/` | `task.c` + `task.jhyy` + `task.meta`（key = value 元数据） |
| `bench/baseline/static.json` | 静态指标 + 二进制体积基线 |

### ② `scripts/dev/bench/runtime_perf.py` 的加法式改造

- 加 `timeit_samples(cmd, n) -> list[float]`（返回全部样本）；
  `timeit()` 改成 `min(timeit_samples(...))` ⇒ **行为不变**。
- 源码从 `bench/tasks/<name>/task.{c,jhyy}` 读，不再内联。
- 加 `LEGACY_TASKS = ("fib", "ack", "nq")` —— **本门（`perf`）拥有的题目**。

⚠️ **为什么是固定列表而不是"目录里有什么就跑什么"**：
`bench/tasks/` 会随新题增长。若本脚本也跟着跑，新题目的基线就得写进本文件
⇒ 两道门的基线混在一起。固定列表 ⇒ **两份基线管的任务不重叠**
⇒ 没有"改了 A 忘了改 B"的漂移。

### ③ 门 `bench-perf`

- `.github/workflows/ci.yml`：新 step，`# gate: bench-perf`，
  命令 `python bench/bench.py --ci`，`if: always()`，排在 `perf` 门之后。
- `docs/internal/FACTS.md` § 2.2：登记同一行（**两处必须同时改**，
  `docs_facts_check.py` 的 `check_gate_registry()` 双向对拍）。
- 同一个 step 里跑 `bench/bench.py --selftest`
  （同 `artifact_checks.sh --selftest` 的做法：一道从没被见过红的门不算门）。

### ④ 门禁边界

| 项 | CI | 理由 |
|---|---|---|
| stdout 与 gcc（**`-O0` 产物**）逐字相同 | **硬门** | 确定性 |
| 静态指标不回归 | **硬门** | 「源码 × 编译器」的确定性函数 |
| **二进制体积**不回归 | **硬门** | 同上。**此前没有任何门在管它** |
| 墙钟 / 编译耗时 / 测量地板 | **只报告** | 共享 runner 宿主负载不可控 |

## Risks

| # | 风险 | 缓解 |
|---|---|---|
| 1 | **两份基线各管一半 ⇒ 漂移** | 固定 `LEGACY_TASKS` ⇒ 任务集不重叠；`bench.py` 只对**非** legacy 题目判静态指标 |
| 2 | **门登记漏改一边** | `docs_facts_check.py` 的 `check_gate_registry()` 双向对拍 + 脚本集合**精确相等** |
| 3 | **墙钟被误加进硬门** | `--selftest` 断言"只改墙钟不会让门变红" |
| 4 | **搬迁改坏了基线** | 判据 1 + 2（基线文件逐字节未变 + 静态指标逐项相同）—— 两条都过才算搬成功 |
| 5 | **`jhyy compile -o` 的产物位置不符预期** | 一律用**绝对路径** `-o`；**计时前断言产物存在** |
| 6 | **机器负载让数字乱跳** | 比值用 min；median / p95 一并列出；**测量地板**单独公布 |

## Out of scope

- **跨语言对比**（只对 C）。
- **IO 题** —— jhyy 的 stdout 是无缓冲的 ⇒ 大量输出会退化成 syscall 瓶颈。
- **测标准库** —— 本套件测的是**代码生成**。
- **hyperfine / BenchExec / Docker 隔离** —— 本仓的计时路径在 MSYS2 下已被实测证明更可靠；
  BenchExec 是 Linux-only。
- **改编译器本体** —— 本格零 `compiler/src0/*.jhyy` 改动 ⇒ 零自举漂移风险。

> ⚠️ **原定的 `fannkuch` 换成了 `partial_sums`**（2026-11-03）：fannkuch 的"翻转"定义
> 有多种变体，**实测还原出来的三种都得不到 CLBG 的经典值（n=7 ⇒ 3492）**
> ⇒ 与其用一道"数字对不上出处"的题，不如换一道**定义无歧义**的纯整数题
> （`partial_sums`：20 000 × 1 000 次整数迭代，CLBG 同名题，改成输出单一 checksum）。
> ⇒ 覆盖轴不变（整数 + 嵌套循环），而**纯整数那一列反而更干净**（不碰浮点、不碰堆）。

⚠️ **v4.3.3 的差分门很可能第一天就挖出真实存在的编译器 bug** ⇒ 门一到就是红的
⇒ 全盘皆红 ⇒ 团队学会忽略红。⇒ **先 report-only 一个版本**，
挖到的缺陷分诊完、已知反例登记进 `bench/regress-cases/` 后再升硬门。

### ⚠️ 实际发生了什么（2026-11-03）

⇒ **它确实第一天就挖出了两个真缺陷** —— 计划里的担心成真了：

| 台账 | 症状 | 状态 |
|---|---|---|
| [W-185](../../internal/workarounds.md) | `u32 → i64` 的加宽用**符号扩展**(`extsw`)而不是零扩展 ⇒ `u32 as i64` 出负数;`u32 / u32` 按有符号语义算 | ACTIVE（根因**已定位**到 `compiler/src0/codegen.jhyy:2046`） |
| [W-186](../../internal/workarounds.md) | `u64` 的 `\| & ^ + - *` 在**任一操作数高位为 1**时结果错误 | ACTIVE（根因**未定位**） |

⇒ ⇒ 因此门**没有**按"先 report-only 再升硬门"走，而是换了个设计：
**两个模式 + 金标准** ——
① **规避模式**（避开已知缺陷的触发面）⇒ 门红 ⇔ 有**新**缺陷；
② **全量模式**（不规避）⇒ 盯住"已知缺陷的行为有没有变"；
③ **金标准**（`bench/seeds/golden.json`）⇒ 差分测试器只看"两侧是否一致"，
**一致 ≠ 正确** ⇒ 金标准补上这一维 ⇒ 任何行为变化都红。

⇒ ⇒ 顺带把 **FACTS § 3 的 ACTIVE 从 0 改成 2**（两个 README 的对应数字同步）。

⚠️ **静态指标基线绑定编译器版本** ⇒ v4.4.x 的寄存器分配落地后必须**重取一次**。
