## RCA re-verify (2026-09-17)

### Sub-bug 1: big_array SEGV at element ~93 init

**v2.11.21 RCA claim**: 2-pass slot alloc (~80-120 LOC) — 单 pass can't safely separate elements from region。

**v2.11.22 RCA re-verify** (per `feedback_audit_single_commit_diff` + `feedback_rca_first_root_cause`):

Read `.s` comparison QBE vs self-backend:
- QBE: `subq $408, %rsp` (400 region + 8 pointer-slot below); `movl $X, -Y(%rbp)` 直接写 region (e.g. `movl $1, -400(%rbp)` for arr[0])
- Self: `subq $1816, %rsp` (region 400 + 222 formula slots); 公式 `-(32+t*8)` 给每个临时变量分配 slot

**RCA 真因** (sub-bug 1 actual mechanism):
1. `cg_alloc_slot(state, 400)` 把 region 放在 `next_offset = -400` (region 占 -400..-1)
2. t1 (alloc result) 的 pointer-slot 走公式 `-(32+1*8) = -40` (跟 region 物理分离,这条本身 OK)
3. 后续 derived temps (e.g. `t21 = t1 + 200`) 的 slot 也走公式 `-(32+21*8) = -200`
4. **collision**: t21 的 slot (-200) == arr[50] 的 region 地址 (-400 + 4*50 = -200) — 8-byte pointer 写到 -200..-193 会覆盖 arr[50] + arr[51] 的 4-byte 值
5. `storew $91, %t21` indirect dispatch (`movq -200(%rbp), %r8; movl %eax, (%r8)`) 写 91 到 -200..-197 — 覆盖 arr[50]
6. 后续 `add %t21, 4` 重读 t21 slot (-200) 拿到的是 91 + garbage 当 ptr → bogus address → SEGV

**v2.11.22 真修 (per incremental allocation,NOT 2-pass)**: When recording address-holder flag, ALSO allocate dedicated slot via `cg_alloc_slot(state, 8)` + `cg_record_temp_slot(state, dst, allocated_offset)`. This pushes address-holder slots BELOW deepest region (next_offset 不断 advance),避免公式碰撞。

**LOC 收敛**:
- `emit_alloc` (codegen_amd64_emit_mem.jhyy:299-349): 加 5 LOC (call `cg_record_temp_slot(state, dst, region_offset - 8)` + advance next_offset + total_alloc)
- `emit_binop` (codegen_amd64_emit_call.jhyy:1681-1685): 加 4 LOC (call `cg_alloc_slot(state, 8)` + `cg_record_temp_slot(state, dst_id, slot)`)
- **Total: ~9 LOC** (vs v2.11.21 DEFER 估 ~80-120 LOC — incremental allocation 比 2-pass pre-scan 简单 10x)

### Sub-bug 4: for_in_slice_nested inner loop SEGV

**v2.11.21 RCA claim**: REVERT v2.11.20 RC-1 + retighten (~5 LOC net,REGRESSION fix)。

**v2.11.22 RCA re-verify** (per `feedback_audit_single_commit_diff`):

Read IL pattern (for_in_slice_nested.il inner loop):
```
%t40 =l mul %t39, 16          # idx * 16
%t41 =l add %t38, %t40        # base_ptr + idx*16 → t41 = derived addr
%t42 =l loadl %t41            # loadl reads 8 bytes from *t41 → t42 = data_ptr VALUE
%t44 =l add %t42, 8           # add VALUE 8 → t44 = data_ptr + 8 (derived on VALUE)
%t45 =l loadl %t44            # loadl reads 8 bytes from *t44 → SEGV
```

**RCA 真因** (sub-bug 4 actual mechanism):
1. v2.11.20 RC-1 fix (commit `56be6cf`) added `emit_load` flag propagation block at codegen_amd64_emit_mem.jhyy:704-710:
   ```jhyy
   if (*t).qbe_type == QBE_L_LOCAL() {
       let _lp = cg_record_temp_holds_address(state, dst);
   }
   ```
   When `t42 = loadl t41` runs (t41 IS address-holder), t42 marked as address-holder。**但 t42 是 VALUE not address** (load dereferences src)。
2. `t44 = add t42, 8` — t44 marked as address-holder (via emit_binop propagation at L1681)。
3. `t45 = loadl t44` — emit_load sees t44 is address-holder → indirect dispatch `movq (%r8), %rax`。但 %r8 = t44 slot VALUE = t42+8 = data_ptr+8 = 实际 runtime 地址 (e.g. heap-allocated region)。`(%r8)` 读这个 runtime 地址 → SEGV (内核内存 access)。

**v2.11.22 真修** (per v2.11.21 RCA plan Phase 2 + retighten):
1. **REMOVE L704-710** in `emit_mem.jhyy` (load propagation block, ~7 LOC delete)
2. **TIGHTEN emit_binop propagation at L1653-1685**:
   - Set `is_add_or_sub = 1` for BOTH `add` and `sub` ops (currently only sub fires; add coverage missing)
   - Tighten L1681 condition to `&& is_add_or_sub != 0` (so mul/div/mod/cmp don't propagate flag — they're value ops not derived-address)

**LOC 收敛**:
- `emit_load` L704-710: delete 7 LOC
- `emit_binop` L1653-1685: 5 LOC edit (add `is_add_or_sub = 1` for add + tighten L1681)
- **Total: ~7 LOC net** (vs v2.11.21-fix plan 估 ~5 LOC,实际 5 LOC 加上 is_add_or_sub 调整共 ~7 LOC)

## Phase plan

### Phase 1 — big_array fix ❌ DEFERRED to v2.12.x

**Deferral Evidence (2026-09-17)**:
v2.11.22 attempt 1 applied Edit 1a alone (emit_alloc: record pointer-slot at region_offset - 8). big_array STILL SEGV. Root cause deeper than just t1's pointer-slot — **derived temps (`t21 = t1 + 200`) still go through formula `-(32+t*8) = -200` which collides with arr[50] region address `-400 + 4*50 = -200`**.

Edit 1b attempted (emit_binop: cg_alloc_slot + record derived slot) → REVERTED because `cg_alloc_slot(8)` advanced next_offset into formula territory and broke test_array (formula t2 = -48 collided with cg_alloc_slot t3 = -48).

**Real root cause** (per attempt 1 investigation): **slot-vs-region overlap** — t2 = alloc16 16, region is at rbp-0x30 (= 0x5ffda0), t2's slot is at rbp-0x30 (SAME memory). Writing to "address t2+0" via indirect dispatch writes to t2's slot → corruption cascade.

This is an **architectural** issue in `emit_alloc` slot allocation: it doesn't separate the temp's "address-holder slot" from the "region" memory. Fix requires 2-pass slot allocation or per-alloc slot pre-allocation — both > 100 LOC + cross-cutting impact on `mem_temp_offset`, `cg_offset_for_temp_with_target`, `emit_alloc`, frame size calc, etc.

**Decision (per `feedback_rca_first_root_cause` + `feedback_memory_selectivity`)**: DEFER to v2.12.x. Document evidence here. Do NOT ship a partial fix that introduces subtle slot corruption.

### Phase 2 — for_in_slice_nested fix ❌ DEFERRED to v2.12.x

**Deferral Evidence (2026-09-17)**:
v2.11.22 attempt 2 applied Edit 2a (REMOVE L704-710 load propagation) + Edit 2b (extend is_add_or_sub to add) + Edit 2c (TIGHTEN L1681 to `is_add_or_sub != 0` AND `cg_is_address_holder(src1) != 0`). for_in_slice_nested STILL SEGV at runtime (first indirect store of `storew 1, %t4` where t4 = `add t2, 0` corrupted t2's slot).

gdb backtrace pinpointed: rbp-0x30 (t2's slot/region overlap) → 0x1 (corrupted from 0x5ffda0 stack address). t2's slot value (the stack address) was overwritten by indirect store because slot and region share memory.

Simplified Edit 2c to drop the `cg_is_address_holder(src1) != 0` gate (fire on ANY add/sub on QBE_L_LOCAL) — STILL SEGV (more broadly, all `t4 = add t2, 0` patterns now SEGV).

**Real root cause** (per attempt 2 investigation): same slot-vs-region overlap as Phase 1. The v2.11.20 RC-1 load propagation was actually CORRECT for the 5/6 slice tests (slice_index / slice_iterate / slice_literal / slice_subrange / mixed_struct_slice_match) — the propagation was tracking "this is a derived address" so emit_load does indirect dispatch. The propagation chains (`load → add → load`) work in the architectural sense, but for_in_slice_nested has an extra nesting layer that exposes a different downstream bug.

**Decision (per `feedback_rca_first_root_cause`)**: DEFER to v2.12.x. The Phase 2 fix sketch was correct in principle but incomplete — actually fixing requires addressing the slot-vs-region overlap (Phase 1's architectural issue) FIRST, then re-attempting the load propagation analysis.
