## Scope (~150 LOC, 2 commits ship)

### A. W-074 真修 — `codegen_amd64_run` silent no-op 根因定位 + 修 (~60 行改)

**目的**: 定位 `parse_and_emit` dispatch loop 内 emit 函数体为何 silent-no-op (sb.len = 0 输出),真修 emit 路径。

**实现**:

#### A.1 Trace 路径 (定位根因)
在 `compiler/src0/codegen_amd64.jhyy` `codegen_amd64_run` (L196-283) 加 stderr instrumentation:
```jhyy
fn codegen_amd64_run(il_path: *u8, asm_path: *u8, t: i32) -> i32 {
    // ... 现有 read_file + arena_init + lex_il + cg_state_init ...

    // NEW: trace per-iteration
    let mut sb_before: i64 = state_buf.sb.count;
    let r: i32 = parse_and_emit(state_buf, tokens, n, target_tag);
    let sb_after: i64 = state_buf.sb.count;

    jh_fputs_stderr("[codegen_amd64_run] parse_and_emit returned " as *u8);
    jh_print_int(r);
    jh_fputs_stderr(", sb.count: " as *u8);
    jh_print_int(sb_after);
    jh_fputs_stderr(" (delta " as *u8);
    jh_print_int(sb_after - sb_before);
    jh_fputs_stderr(")\n" as *u8);

    if sb_after == (0 as i64) {
        jh_fputs_stderr("warning: self-backend produced 0-byte .s, source module likely emits no body for this pattern\n" as *u8);
    }

    // ... 现有 peephole_fold + jh_write_file ...
}
```

**期望发现 (嫌疑)**: `parse_and_emit` 的某个 emit_X 函数体内有条件分支在 `target_tag == TARGET_AMD64_SYSV()` (or SYSVFS) 下走 silent return,不是 sb_append。看 `codegen_amd64_emit_call.jhyy` / `codegen_amd64_emit_mem.jhyy` / `codegen_amd64_emit_ctrl.jhyy` 的 target_tag dispatch chain。

#### A.2 修候选 1 — emit 函数体 target_tag dispatch silent-return
如果 trace 出"sb.count delta = 0 但 parse_and_emit 没报错",查 emit_call / emit_mem / emit_ctrl 的 `if t == TAG_X { ... } else { return; }` 模式,补全 target 分支。

#### A.3 修候选 2 — codegen_amd64_lexer.jhyy lex_il 末尾哨兵吞 token
`codegen_amd64_lexer.jhyy:936-974` lex_il 的 increment-after-EOF pattern 可能让 n=0 (lex 完整 IL 但 n 没算 token 数)。**不删此 branch**(per `feedback_jhyy_brace_nesting_trap` 类似的注释引用陷阱),加 `n = lex_il_count(tokens); if n == 0 { jh_fputs_stderr("warning: lex_il produced 0 tokens\n" as *u8); }` 探测。

#### A.4 修候选 3 — sb_append 调用点签名不匹配
检查 `codegen_amd64_emit_*.jhyy` 是否所有 sb_append 调用都过 `state.sb.count` (非 `state_buf.sb.count` 直接 deref) — jhyy struct literal field access 可能漏链。

## Risk + rollback

**Risk 1**: A.1 trace instrumentation 改变 emit 行为 (unlikely 但可能 — 加 stderr 调 jh_fputs_stderr 可能影响 inlining)
- **Mitigation**: trace 在 parse_and_emit 之外,只读 state_buf.sb.count 不写
- **Rollback**: revert Commit 1 的 trace 加法;保留真修的 emit 函数体改动

**Risk 2**: A.2/A.3/A.4 真修候选命中 emit_call / emit_mem / emit_ctrl 之一,引入新 codegen 路径 bug (新 emit 函数体在不同 target_tag 行为不一致)
- **Mitigation**: dual-path 验证 (QBE fallback + self-backend) 双 5/5 PASS;D43 closure hold (不动 codegen 主路径);regress 全部 (115+20 SKIP) PASS
- **Rollback**: revert Commit 1 的 emit 函数体改动;回归 W-074 ACTIVE 状态 (codegen_amd64_run 仍 0-byte)

**Risk 3**: regress.py `--self-backend` flag 在 docker cross-compile 链路下,JHY_SELF_BACKEND=1 在 docker container 内不可见 (env 传递问题)
- **Mitigation**: regress.py docker branch 显式 set env in subprocess.run;test 提前验证
- **Rollback**: revert Commit 1 的 regress.py 改动;flag 不 ship,改用 `regress.py --tests=...` shell prefix `JHY_SELF_BACKEND=1` 替代

**Risk 4**: D43 closure sha drift (codegen 主路径行为意外变 → v1→v2 .il sha 不再 = `6a2f2277...`)
- **Mitigation**: 真修只动 emit 函数体 silent no-op 部分,不动 codegen 主路径;.il 生成应 bit-identical (W-074 bug 在 .s 阶段不是 .il 阶段)
- **Rollback**: revert Commit 1;回归 v2.9.0 baseline 状态 (D43 closure `6a2f2277...` 持 hold)
