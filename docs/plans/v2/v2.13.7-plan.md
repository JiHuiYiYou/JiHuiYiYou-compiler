# v2.13.7 — W-057 lexer 放宽 + codegen emit i32 codepoint fold 真修

## Context

v2.13.5 workarounds.md refactor 后真 ACTIVE workaround count = 0,剩 3 条真未修推后续真修 sprint: W-057 / W-058 / W-081。W-057 v1.7.0 Stage 3 ship 时显式 lex reject 3/4-byte UTF-8 codepoint (per spec §4.4 BMP-only 限制),v1.7.3 patch C2 补登 W-057 (workarounds.md 缺归档)。v2.13.6 mini 修 MCP 后,W-057 真修可单独 sprint 推完。

**W-057 范围** (per `docs/internal/workarounds.md:4001-4043`):
- spec §4.4 字符字面量族 3-byte (U+0800-U+FFFF, e.g. `'你'` U+4F60) + 4-byte (U+10000+, e.g. `'🎉'` U+1F389) UTF-8 codepoint 在 v1.7.0 Stage 3 显式 lex reject
- 症状: `test.jhyy:2:9: error: 3/4-byte UTF-8 codepoint not supported`
- 根因: vendor QBE (2026-08-15 build) 编译期 fold 3/4-byte codepoint 到 IL 时,数据 section `b 0xE4 b 0xBD b 0xA0` 不被 vendor QBE 当作单个 codepoint 折叠,emit 错误 IL 字节序
- 影响: user-space `char_literal.jhyy` 只测 1/2-byte; OS debug 输出含 CJK 字符时 fail

## 真修 path (scope 限定)

**Lexer 放宽** (主 fix):
- `src0/lexer.jhyy` ~555-562 reject 分支: 当 char literal 是 3/4-byte UTF-8 codepoint 时,不再 emit "3/4-byte UTF-8 codepoint not supported" 错误,改成 emit codepoint integer literal (i32) + 标注 type = CHAR_W (新 type tag 区别 1/2-byte BMP CHAR)
- 新增 `CGState.cur_char_qt = W` (4 bytes) 但 codegen 仍 emit `movl` (per QBE `w` class semantics)
- 跟踪 lexer stage: char literal lex 阶段走 codepoint-decode logic,emit IR temp = codepoint int + qt = W

**Codegen emit path**:
- `src0/codegen.jhyy` char literal emit 路径: emit `data $ch = { w 0x4F60 }` (单 codepoint `w` 类,字节序 4 bytes little-endian); 然后 emit `movl $ch, %t<N>` load 进临时
- vendor QBE 现在需要支持 codepoint fold — 但 v2.13.7 不升级 vendor QBE,改成 codegen emit `data` + `movl` 2-instruction pattern,QBE 不用 fold
- Test 加: `compiler/tests/examples/char_literal_3byte.jhyy` (CJK `'你'` U+4F60) + `char_literal_4byte.jhyy` (emoji `'🎉'` U+1F389)

**Spec §4.4 修订** (per W-057 entry "实现路径 3"):
- `docs/abis/jhyy-lang-spec-v1.3.0.md` §4.4 加段: "v2.13.7+ codegen emit codepoint 直接走 `data $X = { w 0xCODE }` + `movl`,bypass vendor QBE codepoint fold gap. 3/4-byte BMP 在 user-space + OS debug 都可 ship"
