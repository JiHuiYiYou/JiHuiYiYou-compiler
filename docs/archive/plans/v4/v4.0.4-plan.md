**新根因 evidence (2026-10-11 v4.0.4 prep RCA, 1-iter):**

gdb 实地取证 (per `feedback_il_s_debugging_pattern` + `feedback_qbe_crlf_root_cause` + `feedback_jhyy_dbgfile_cwd_sensitive`):

```
$ cd $JHYY_ROOT && gdb -batch \
  -ex "file compiler/build/bin/jhyy_v1_new.exe.exe" \
  -ex "set args compile compiler/src0/main.jhyy" \
  -ex "run" -ex "info registers rbp r8" \
  -ex "x/16gx \$rbp-16528"

rbp            0x5f05b0            0x5f05b0
r8             0x0                 0

0x5ec520 = rbp-16528:    0x0000000000000000
0x5ec528 = rbp-16520:    0x0000000000000000
0x5ec530 = rbp-16512:    0x0000000000000000  ← %t9191 holder slot (NULL!)
0x5ec538 = rbp-16504:    0x0000000000000000
0x5ec540 = rbp-16496:    0x00000000005ec548  ← %t9189 holder = rbp-16488 (正确)
0x5ec548 = rbp-16488:    0x0000000000000000
```

**Smoking gun:** `compiler/build/bin/jhyy_v1_new.exe.s:70100` emit `movq %rax, -16512(%rbp)		# -> %t9191` (rax = rbp-16504, 装 holder pointer),但 runtime `-16512(%rbp)` 是 **0**。

-16512 是 `-(32 + 2060*8)` = local_t 2060 formula slot,**不是** alloc pool slot (`alloc pool start = -8192`)。说明 `cg_offset_for_temp_with_target(%t9191, ...)` **没走** temp_slot_for_id recorded path,而 fall through 到 formula path `-(32 + local_t2 * 8)` = -16512。

**对比** `%t9189` (line 70094 同 pattern, alloc4 4): -16496(%rbp) = 0x5ec548 = rbp-16488 (correct),说明 `cg_offset_for_temp_with_target(%t9189, ...)` 正确走 temp_slot_for_id recorded path。

**区别:** `%t9189` 和 `%t9191` 是相邻同 pattern 的两个 alloc,**为什么一个对、一个错**?

进一步取证 `compiler/build/bin/jhyy_v1_new.exe.s`:
- `%t9189`: alloc at line 70091-70095, region -16488, holder -16496 (`(allocated: 4, aligned: 8)`)
- `%t9191`: alloc at line 70097-70101, region -16504, holder -16512 (`(allocated: 4, aligned: 8)`)

两个 alloc 完全相同的 size (4 → aligned 8)。两者 alloc 距离: 16 bytes (8 region + 8 holder per alloc)。

**RCA 推测 (1-iter, 需 1-iter verify in v4.0.4):**

`%t9191` 的 holder slot 被 formula path 计算的 `-16512` 覆盖,**说明**:
- Option A: `cg_record_temp_slot(state, %t9191, -16512)` 没真写入(temp_slot_for_id 表 entry 没 update)
- Option B: `cg_record_temp_slot` 写对了 entry,但 `cg_offset_for_temp_with_target` lookup 时读 entry = 0
- Option C: entry 写入和读取之间被 clobber (reset_for_function zeroing)

**最可能 Option B 或 C** — 因为 reset_for_function zero temp_slot_for_id per-fn (line 549-556 `cg_state_reset_for_function`),如果 `emit_func_header` 调 reset_for_function 时序跟 `cg_local_t_from_global` 的 `cur_fn_idx` bump 时序有 race / reentry,可能 lookup 走 cur_fn_idx 错 → per_fn_base_t[idx] 读 garbage → local_t2 错 → formula 返回 wrong offset。

但**真正的 fix scope** 不在 frame_size 公式 (4 attempts 已 ship 失败证明),而需要深挖:
1. `cg_record_temp_slot` write 是否对 high temp_id 真的成功?
2. `cg_offset_for_temp_with_target` lookup 是否对 high temp_id 真的读到?
3. emit_func_header 跟 reset_for_function 调序是否在 parser__parse_expr (28-th fn) 时正确?

**Per audit attempt #4 ledger 显式指引:**
- 修复 scope = `src0/codegen_amd64_emit_call.jhyy:2189-2191` (emit_binop final store) + `src0/codegen_amd64_emit_load.jhyy` (dst temp record path)
- NOT frame_size 公式 (per audit Fix 1+2 错方向)
