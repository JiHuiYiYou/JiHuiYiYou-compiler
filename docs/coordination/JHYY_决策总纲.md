## §0 一句话结论

**JHYY 的方向已经收敛，剩下的是排序问题。** 内核形态锁定**能力微内核（首版物理结构按特权分层）**；语言的核心价值是**把 capability 授权、地址空间归属、执行上下文这三类 OS 不变量从"文档 + review"上推到"编译不过"**；当前最大的风险不是缺特性，而是**静默错误**与**没有裸金属反馈环**。

三项必须现在就动手的：**实参类型检查、最小 freestanding 镜像、栈深度可测量**。

## §1 已确立、无需再论证的结论

A 与 B 独立收敛，且都锚在规范具体章节上，以下八条视为定论：

| # | 结论 | 依据 |
|---|---|---|
| 1 | 内核形态 = **能力微内核**（长期）；首版 Tier 0/1 集中在特权区，属工程形态而非形态妥协 | B§2；type_tag + cnode_idx/depth/rights + cap_offsets + region_table 已构成完整授权链 |

| 3 | **静默错误是头号敌人**。它比"像 C 一样不安全"更危险，因为语法像 Rust 会制造虚假安全感 | A+P0；实参不检查（lang §2.4）、bool 不归一化、顶层非整数初始化错、`extern fn` struct 参数静默不符 C ABI |

## §2 一等公民模型总纲

### 2.1 判定标准（六项测试）

「一等公民」不是语法漂亮，而是**编译器无需读注释即可推理**。六项测试：

1. **参数化**：能否作为类型参数/const 参数出现且不被擦除
2. **类型检查**：是否参与类型等价、子集关系，能否阻止非法组合
3. **推导**：不写注释时能否从合法来源推导
4. **拒绝**：非法组合是否必然报错，而非延迟到运行时
5. **传递**：能否跨函数签名、IL、后端、二进制契约保持同一语义
6. **事实输出**：能否输出可被 loader/kernel 独立验证的机器可读事实

### 2.2 判定结果

| 对象 | 结论 | 承担角色 |
|---|---|---|
| `Cap<T>` | **一等** | 对象身份 + 权限 |
| rights 集合 | **一等** | 权限子集 |
| `ptr<space>`（user/kernel/phys/io） | **一等** | 解引用上下文 |
| 效果 `may_sleep`/`irq_ctx`/`preempt_disabled`/`may_alloc` | **一等（effect row，附在函数签名上）** | 执行上下文 |
| `holds(L)` | **一等（effect 参数）** | 锁序 |
| BootState | **一等，但封闭状态枚举** | 启动阶段不可倒退 |
| 错误类型 | 普通一等类型 | error as value |
| layout | **一等 metadata** | 生成期事实 |
| ABI 契约 | **一等编译对象，不是类型** | 编译器内部 |
| region | 运行时一等 + 类型轻量索引 | 内核对象 |
| WCET 上界 | **二等（分析结论，不是类型）** | contract |
| panic 可达性 | **二等事实** | contract |
| BootPhase 枚举值 | 普通类型即可 | — |
| IR 字母 `m`（MEMORY class） | 实现类型，不是语言一等 | 后端内部 |

### 2.3 明确不做（同等重要）

- **WCET 不参与泛型单态化**——只能是函数属性 + 常量上限
- **锁名不全量泛化**为 `Lock<order>`——用显式 `lock_class!` 编号，由 lockdep pass 消费
- **region 生命周期不复制为完整线性类型**——内核对象跨线程/RCU/引用计数，语言只持 token
- **运行时 ABI 细节不暴露为语言类型**——只提供 layout 查询
- **panic category 不是每层签名必写的类型参数**

### 2.4 总纲：三个层级 + 一条事实链

```
语言层   capability / address space / rights / state token / error / 普通类型
签名层   effect row（may_sleep / irq_ctx / holds(L) / may_alloc）
事实层   layout / ABI / 栈 / 锁序 / WCET / panic / cap_offsets（分析生成）
```

**事实链**：AST/sema 附 source span → IL 保留 → codegen 约束 sret/寄存器类/naked 栈/clobber → 链接期全程序断言 → `.jhyynb` 成为内核可验证契约。

> **纪律**：任何"不变量"必须落在三个层级之一，否则不得进入语言规范。

## §3 三处真实分歧及裁决

### 分歧 1：`Cap<T>` 真实 T 的落地时机

| | 主张 |
|---|---|
| B §14 | 第一阶段就加真实 T + rights 编译期参数 |
| A §八 | 反对。对象生命周期与 revoke 未冻结就改 `Cap<T>`，未来加 version/provenance 会迫使**第二次 ABI break** |

**裁决：采纳 A，但补一个前置动作。**

拆成两步：
- **P4a（先）**：冻结 **capability objects manifest**——type_tag 白名单、每类的初始 rights 集、生命周期 owner、cap init phase、version/provenance 规则
- **P4b（后）**：才改 `Cap<T>` 的类型参数

理由：wire 是 8 字节且不解析 T，改类型本身不难，难的是**对象语义未定时改了还要再改一次**。manifest 是纸面工作，成本极低但能消除返工。

### 分歧 2：`.jhyynb` 的编译事实放哪

| | 主张 |
|---|---|
| B §6 | 新增 `contract` section，或扩展 `debug_group` |
| A §八 | 反对塞进 `debug_group`——**安全位必须不同**，否则旧 loader 会把能力栈预算当可选调试信息忽略 |

**裁决：采纳 A，新增独立 section。**

```
kind = 9  contract    loader 必须验证，验证失败拒绝加载
kind = 6  debug_group 可选，可剥离
```

承载：栈上界（`frame_local_max` / `call_path_max`）、`may_sleep`/`irq_ctx`/`preempt_disabled`/`may_alloc`、`holds(L)` 锁序图、IPC handler version、panic category、WCET class、cap_offsets 位图与 type_tag allowlist。

**关键设计约束**：不能用 "debug" 命名承载安全契约，否则语义等级会被下游误解。

### 分歧 3：反馈环（P1）的位置

| | 主张 |
|---|---|
| 原排序 | P1 在 P2（栈与分配）之后 |
| A §八 | 上移到 P0 之后 |

**裁决：采纳 A。** 理由不是"能跑更重要"，而是**没有执行路径时，能力语法会在真空里演进**——你无法判断 P2 的 16 KiB 目标是否适配 trivial program，也无法验证 IPC 契约能不能被 loader 解释。

**但验收要收紧**：P1 的成功标志是"最小 UEFI 镜像输出 UTF-8 后停机"，**不是完整 boot**。过早写完整 UEFI 代码会把现有 ABI 偏离固化。

### 补充修正（对前一轮我的判断）

我原先说"栈深度编译期断言"。**不完整**——需要两个上界：

- `frame_local_max`：单函数本地需求（341 KiB 是这个值）
- `call_path_max`：入口到叶节点的最坏路径

**只做线性扫描能降单帧，但递归与深调用图仍可能超限。** 链接器必须约束后者。

## §4 分期路线图与硬验收门

两条链：**稳定链**（P0→P0.5→P1→P2→P2.5）与**能力链**（P3→P3.5→P4→P4.5），在 P2.5/P3 与 P4 处汇合。

| 阶段 | 目标 | 关键任务 | 前置 | 验收门（硬指标） | 不做会怎样 |
|---|---|---|---|---|---|
| **P0 止血** | 消除静默错误与不可重复编译 | 实参类型检查；`extern fn` 参数形状限制；CLI 多余输入文件改报错；旁路文件改唯一临时路径；bool 归一化；顶层非整数初始化；数字字面量规则冻结；**整数隐式提升**（新增，见 §6.4）；错误可定位（span） | 无 | ① 多余 `.jhyy` 输入报错（不静默忽略）② 并发 8 进程编译无旁路文件竞争 ③ `false && side()` 中 `side` 不执行 ④ 传 `i32` 给 struct 形参编译失败 | 后续自举无法区分真错误与旧 bug；Windows 上无法并行构建 |
| **P0.5 观测** | 编译器知道自己的最坏行为 | 输出 per-function `frame_local_max`；构建调用图算 `call_path_max`；递归/动态调用显式标记；链接器支持栈断言 | P0 | ① 所有函数两个上界可打印 ② CI 保存基线 CSV ③ 链接期可断言线程栈保留量 ≥ 最坏链 + redzone | 栈问题只能靠运行时溢出发现，内核栈大小无从配置 |
| **P1 反馈环** | 最小镜像真跑在裸金属 | UEFI entry 钩子实装；**按 `--target` 分支链接**（而非按源文件的 `#[no_std]`）；移除无条件 Windows 系统库；`SetConsoleOutputCP(65001)` | P0 | ① 最小 `kernel.efi` 在 QEMU/OVMF 输出 UTF-8 后停机 ② 编译期可选 8 KiB / 16 KiB 栈并触发断言 ③ `#[no_std]` 不再自动加 `-lkernel32 -luser32 -lshell32 -ladvapi32 -lm` | 编译器长期寄生 Windows；能力/IPC 是否可执行永远未知 |
| **P2 栈与分配** | 先证明栈，再压栈 | 栈深度全程序分析 + 链接断言；栈槽 16B 对齐；linear scan 寄存器分配；**禁 XMM 溢出 + 禁 red zone（上下文属性）** | P0.5 | ① **最大单帧 ≤ 16 KiB**（基线 **341 KiB** —— 229 KiB 已被 v4.2.1 作废，见 §6.5）② `call_path_max` 受链接期断言 ③ SysV SIMD 参数不产生 8B 对齐 fault | 中断/IPC 破坏相邻栈；线程栈被迫无谓增大 |
| **P2.5 ABI 收敛** | 关闭已知偏离，形成兼容基线 | 修 sret 阈值/整数预算、SysV eightbyte（§12.11）、MEMORY class 混排守门（§12.4）；统一 `alignof(enum)`；`asm!`/fence 进 IL 节点；**容器格式由 `--target` 决定** | P2 | ① 14 条已知偏离降至 **≤ 3 条**且均为显式兼容性例外 ② abi-hash CI 不回归 ③ hosted + freestanding 两套 smoke 全绿 | 新能力代码会在现有调用约定下悄悄错传 cap |
| **P3 语言自洽** | 让内核 API 能用普通语言写 | 块表达式；`fn(...)` 类型位置；闭包捕获；`()` 类型位置；`defer` 覆盖末表达式 | P2.5 | ① BootState 迁移可写在块内 ② 函数指针可跨模块传递 ③ hot helper 可写成 1–5 行闭包并被 `#[inline]` 展开 | BootState、热路径内联、回调契约都无法自然表达 |
| **P3.5 效果骨架** | 先拦最高危上下文错误 | `with { ... }` 语法；效果传播；irq/preempt/sleep/alloc 禁止规则；lock class 与有序 acquire/release | P3 | ① `irq_ctx` 内调用 `may_sleep`/`may_alloc` 被拒 ② 锁序图无环 ③ 误用给出确定错误码 | 持锁睡眠、PF 路径分配继续靠 review |
| **P4a 对象模型冻结** | 纸面冻结 capability 语义 | capability objects manifest：type_tag 白名单、初始 rights、生命周期 owner、cap init phase、version/provenance | P2.5 | ① 11 个 type_tag 逐个有 owner 与 rights 初集 ② revoke 语义（是否同步、是否传播）写明 ③ slot version 方案确定 | `Cap<T>` 改完还要再改一次（第二次 ABI break） |
| **P4b 能力类型化** | 授权链从 wire 提升为类型 | `Cap<T>` 真 T；rights 参数化与子集收缩；`ptr<phys>`/`ptr<io>`；derive API；`#[ipc_handler]` 全契约；cap_offsets 位图 | P4a、P3.5 | ① `Cap<i32>` ≠ `Cap<i64>` ② **整数不能 `as` 成 `ptr<phys>`** ③ IPC tag/layout/slot 全检查 ④ 最小 cap init + frame map + IPC demo 闭环 | 语言无法阻止 frame/endpoint/file 混用与物理地址越权 |
| **P4.5 可信工具链** | 输出可审计事实 | 插桩 pass 族（KASAN/KMSAN/KCFI/shadow stack 对应物）；WCET class；panic 分类；layout 差分测试 | P4b | ① 注入 ≥20 个 bug 被插桩捕获 ② KCFI 对类型不匹配的间接调用报错 ③ 所有契约有 schema + producer version | 无栈展开下故障与越界更难恢复 |

### 可并行项

- **P0 内部各任务互不依赖**，可全并行
- **P0.5 与 P1 可并行**（栈测量不阻塞 UEFI 钩子）
- **P3 与 P2.5 部分并行**（前端语法改造不依赖 ABI 收敛，但合流点需回归）
- **P4a 是纯纸面工作**，可与 P2.5–P3.5 完全并行，建议尽早启动

### 排序是否最优——三点评审

1. **P1 上移是对的**，但别把它做成"完整 boot"。最小停机镜像即可。
2. **P3 在 P4b 之前是对的**，且理由比"语法美化"更硬：块表达式是 BootState 的**硬前置**（typestate 本质是带顺序的语句序列）；`fn(...)` 类型是 IPC 回调与中断入口的前置；闭包捕获 + `#[inline]` 只认单条 `return` ⇒ 热路径小 helper 当前**一个都内联不了**。
3. **P4a/P4b 拆分是本次新增的**，目的是消除"改了又改"的返工风险。这是纯收益，成本只是先写一份文档。

## §5 语言—内核边界契约

### 5.1 分工公式

> **编译器证明 shape，内核强制执行 authority。**

| 不变量 | 检查阶段 |
|---|---|
| `Cap<T>` 的 T 与 type_tag 相容 | 编译期 |
| `Cap<T, W>` 传入需要 W 的接口 | 编译期 |
| rights 单调收缩 | **编译期生成证明 + 运行期内核强制** |
| IPC `msg_tag` 唯一、handler 签名一致 | 编译期 |
| cap_offsets 合法性与位图 | 编译期布局验证 + **内核必须重查**（消息可能来自不可信进程） |
| message struct 字段 size/align 一致 | 编译期（D41 无 packed、显式 `_pad` 下可完整检查） |
| region 内访问不越界 | 运行期为主 |
| 跨进程 cap 派生/拷贝/revoke | 运行期 |
| 页表/TLB/ASID/中断屏蔽 | 运行期 |
| 栈上界、irq_ctx、锁序 | 编译期分析 + 链接期断言 |

### 5.2 `.jhyynb` 的五个语义层

| kind | section | 语义 | 可剥离 |
|---|---|---|---|
| 0–3 | text / rodata / data / bss | 常规 | 否 |
| 4 | cap_init | 拥有什么 | 否 |
| 5 | ipc_dispatch | 接收什么 | 否 |
| 6 | debug_group | 调试信息 | **是** |
| 7 | region_table | 访问哪里 | 否 |
| **9（新增）** | **contract** | **执行时允许做什么** | **否** |

前三个 jhyy 专属 section 回答"拥有/接收/访问"，**contract 回答"执行"**——这是目前缺的第四问。

### 5.3 原则 5「Kernel 不解决语言问题」的边界条件

原则成立，但四种情况**内核必须破例**：

1. **内存安全依赖全局内核状态时**（页表、RCU grace period、PerCpu 偏移、中断屏蔽）→ 内核输出稳定 unsafe primitive，语言只检查 token 持有
2. **错误语义必须由内核恢复时**（oops/double fault/page fault/cap fault/IPC timeout）→ 语言可给 `#[panic_handler]` 与分类，但线程终止/namespace revoke 由内核决定
3. **wire format 跨版本时** → loader 必须理解最低版本与 cap wire 扩展，不能交给服务进程
4. **证明本身会改变系统状态时** → 运行期检查点是安全状态机的组成部分，不是语言失败

### 6.3 一个必须自己验证的技术事实

**`u8` 组合比较的 codegen 缺陷**：目前唯一证据是 `game.jhyy` 里的一句注释。**非归一化的 bool 在 `&&` 中做 32 位比较，症状可能完全相同**——两者修法不同（一个是 codegen 宽度，一个是归一化）。

> **动手前先写十行复现，确定是哪一类。别信任何人的转述，包括 AI 报告。**

✅ **2026-10-30 已按此要求复现并裁决:在当前自举后端上「u8 组合比较」不成立。**
探针(`eq_u8(200,200)` / `ne_u8(200,201)` / `u8 == 255` / `bool && (…)`)全部正确,exit 0。
⇒ **`game.jhyy` 那句注释指向的缺陷要么已被后续修复消掉,要么当时描述的不是这一类。**
但**另一半仍然成立**:**bool 的值未归一化** —— `codegen.jhyy:3213` 的 `jnz` 判「非 0」,
值为 2 的 bool 仍算真 ⇒ 这才是**归一化**问题,与 codegen 宽度无关。

### 6.4 2026-10-30 新发现:整数之间**没有**隐式提升(且规范未记)

实测(`jhyy` 自举后端):

| 写法 | 结果 |
|---|---|
| `i64 + (1 as i64)` | ✅ 通过 |
| `let x: i64 = 10;` | ✅ 通过(字面量在 let/赋值处有 coerce,`sema.jhyy:2169`) |
| **`i64 + 1`** | ❌ **报 "type mismatch in binary"** |
| `i64 < i64`(变量比变量) | ✅ 通过 —— **不是比较运算符的问题** |

⇒ **同一套整数字面量,在 `let`/赋值处被 coerce,在二元运算处不。**
lang-spec §117 只写了「整数与浮点之间不允许隐式转换」,**整数之间既没写允许也没写禁止**
⇒ 这是一条**规范缺口**,不是实现 bug ⇒ 需要拍板(见 §6.1 第 6 条)。

> ⚠️ 它不是纯纸面问题:写 `while i < N { i = i + 1; }` 时 `i` 是 i64 ⇒ **直接编译失败**,
> 迫使每个整数循环都写成 `i + (1 as i64)`。这是**可用性**问题,不只是语义问题。

### 6.5 「229 KiB 单帧」已作废

`ABI §12.7` 的 **234080 B ≈ 229 KiB** 取自 v4.2.1 **之前**的产物。
v4.2.1(2026-10-29)把帧公式从写死的 `8192 + per_fn_alloc` 改成按函数实际需要算:

| | v4.2.1 之前 | v4.2.1 之后 |
|---|---|---|
| 中位帧 | 8368 B | **288 B** |
| **最大帧** | 237680 B(229 KiB) | **349232 B(341 KiB)** —— **反而变大** |

⇒ **最大帧变大不是变紧**:旧公式用 `max(...)`,在公式池主导时把 `per_fn_alloc` 丢掉了。
⇒ **降帧的真正杠杆是寄存器分配(v4.4 阶段二),不是再调公式。**
⇒ **P2 的「≤ 16 KiB」目标要按 341 KiB 重算**;且寄存器分配理论只给到 ~85 KiB
⇒ **单靠寄存器分配到不了 16 KiB**,还需要别的杠杆。
