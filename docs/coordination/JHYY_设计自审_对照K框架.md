**判据守住了，框架瘸了。**

## §1 逐条对照

### 1.1 判据与四个层次

| 框架条目 | 覆盖 | 说明 |
|---|---|---|
| **判据**：规则 → 编译不过 | ✅ **守住** | 决策总纲 §7 把它写成可度量问句；A §一 同 |
| 表达层（语法描述硬件与约束） | ⚠️ 部分 | `#[naked]`/`#[link_section]`/`asm!` 有；**register block 缺** |
| 语义层（类型/效果编码不变量） | ✅ | 效果系统 + 地址空间 + Cap rights，P3.5–P4b |
| 实现层（内核专属优化与验证） | ❌ **最弱** | 栈深度有；**禁 FPU/SIMD、禁 red zone、别名分析全缺** |
| 工具层（外挂工具内置） | ⚠️ 部分 | objtool/lockdep/sparse/pahole 有对应；**Coccinelle 无对应**（但可能不需要，见 §2.2） |

### 1.2 前端六项「非分要求」

| # | 要求 | 判定 | 说明 |
|---|---|---|---|
| 1 | 消灭 Lexer Hack | ✅ **天然满足** | JHYY 无 C 式 typedef 歧义；`import` 驱动的模块图本就可增量 |
| 2 | **硬件描述一等语法**（register block、位域、write-1-to-clear） | ❌ **真遗漏** | 只在 Cap 草案里给了 `ptr<io>`，但**没有寄存器块声明语法** |
| 3 | 链接与内存布局进入语言 | ⚠️ 部分 | `#[link_section]` 有；`__init`/`.data..percpu` 式的**段语义与丢弃规则**缺 |
| 4 | **Kconfig 配置空间可分析** | ⚠️ **框架错配** | JHYY 无 Kconfig。等价物是「target × 属性 × flag 组合矩阵」，未做 |
| 5 | **ABI 单一真源**（syscall 一处声明 → 多处生成） | ❌ **真遗漏** | 这是能力微内核下**价值极高**的一条：endpoint 声明应同时生成内核侧 + client stub + IPC dispatch 表 + 契约元数据。四份文档都没系统做 |
| 6 | **结构化内联汇编**（类型化操作数、显式 clobber、效果签名） | ❌ **真遗漏** | `asm!` 仍是字符串（ABI §8）；只修了"内联位置"这个正确性 bug，没做结构化改造 |

### 1.3 后端八项 pass

| # | pass | 判定 | 说明 |
|---|---|---|---|
| 1 | 强制栈深度分析 | ✅ | P0.5 + P2，且**修正为两个上界**（比原框架更准） |
| 2 | **寄存器文件按上下文限制**（禁 FPU/SIMD 溢出、禁 red zone） | ❌ **真遗漏，且有时序风险** | 见 §3.1 |
| 3 | **地址空间感知别名分析** | ❌ **真遗漏** | 只做了安全侧（ptr<phys> 派生）；**优化侧零覆盖** |
| 4 | 锁秩静态验证 | ✅ | P3.5，含显式 lock class + 环检测 |
| 5 | 代码自修改（static keys） | ⚠️ 框架错配 | 无历史包袱，早期不需要；可降级 |
| 6 | 插桩 pass 族 | ✅ | P4.5（KASAN/KMSAN/KCFI/shadow stack） |
| 7 | 事实数据库输出 | ✅ | `.jhyynb` contract section（kind=9） |
| 8 | **目标形态**（bare-metal、per-function section、冷热分离、frame pointer/ORC） | ❌ **真遗漏** | 只有"能出 EFI"；段级布局与 unwind 表全缺 |

### 1.4 语言特性八项

| # | 特性 | 判定 | 说明 |
|---|---|---|---|
| 1 | **效果系统** | ⚠️ **做到了但排期偏后** | 原框架称"最高价值项"，我排到 P3.5。见 §3.3 |
| 2 | 地址空间类型 | ⚠️ 部分 | 只做 `ptr<phys>`/`ptr<io>`；**`ptr<user>`/`ptr<kernel>`/`ptr<percpu>` 无排期** |
| 3 | 启动阶段 typestate | ✅ | BootState，且识别出块表达式是硬前置 |
| 4 | 资源静态边界 | ⚠️ 部分 | 无 unwinding ✅；**递归**：`#[unsafe(recursive, max_depth=N)]` ✅ 且比原框架更具体；**`&Allocator` 无全局隐式分配器** ❌ 只在对标里提了一句 |
| 5 | 布局契约 | ✅ | D41 已锁（无 packed、显式 `_pad`）+ ABI 哈希在 P2.5 |
| 6 | 算术语义显式化 | ⚠️ 部分 | 干掉了整型提升与隐式转换 ✅；**但只有 wrapping 一种**，没有 checked/saturating 三选一 |
| 7 | **内核数据结构一等支持**（Rcu/PerCpu/侵入式容器） | ❌ **最严重遗漏** | 需求清单第 11/12 项有，**路线图无排期**。见 §3.2 |
| 8 | 一等 C 互操作 | ✅ | `extern fn`；增量迁移路径明确 |

### 1.5 明确不做五项

| # | 不做 | 判定 |
|---|---|---|
| 1 | GC | ✅ 无 |
| 2 | 异常栈展开 | ✅ 无 unwinding |
| 3 | 默认 async | ✅ 未引入 |
| 4 | **重度单态化** | ⚠️ 部分回应：Cap 草案算了 88 种组合上界，**但无全局编译时间预算** |

## §2 缺口分两类：真遗漏 vs 框架错配

这个区分很重要——**不是所有"0 次"都要补**。

### 2.1 真遗漏（普适内核约束，不因"从零开始"而消失）

- 禁 FPU/SIMD 溢出、禁 red zone
- register block / 位域语法
- 地址空间别名分析（优化侧）
- per-function section / 冷热分离 / frame pointer / ORC unwind
- `Rcu<T>` / `PerCpu<T>` / 侵入式容器
- `ptr<user>` / `ptr<kernel>` / `ptr<percpu>`
- ABI 单一真源（endpoint 一处声明多处生成）
- 结构化内联汇编
- `&Allocator` 无全局隐式分配器

### 2.2 框架错配（第一轮拿 Linux 痛点清单套自研 OS，部分条目天然不适用）

| 条目 | 为什么不适用 | 处置 |
|---|---|---|
| **Kconfig 配置空间** | JHYY 无 Kconfig，无 3000 万行历史配置 | 降级为「target × 属性 × flag 组合矩阵可达性」，**放入 P2.5 而非独立项** |
| **static keys / alternatives** | 是 Linux 应对多硬件变体的历史包袱，jhyy_OS 早期无此需求 | **明确推迟到 P5+**，写进"不做"清单 |
| **Coccinelle 语义补丁** | 用于批量改写历史代码，JHYY 没有历史代码 | **明确不移植**，写进"不做"清单并说明理由 |
| 一等 C 互操作的"逐文件增量迁移" | jhyy_OS 不从 C 迁移 | 降级：只需 FFI 边界可用，不需要大规模迁移工具 |

> **这一条本身是个结论**：第一轮的框架是以 Linux 为隐含参照系写的。JHYY 不是 Linux，没有那些历史包袱——**有些"缺失"是优势而非缺陷**。但 FPU/red zone/RCU/PerCpu/侵入式容器是硬件与内核惯用法的硬约束，跟有没有历史包袱无关。

## §3 三处最严重的问题

### 3.1 禁 FPU/SIMD 与 red zone —— 有一个时序陷阱

**现状恰好安全**：JHYY 全 spill 到栈槽，没有真正的寄存器分配器 ⇒ 当前**没有机会**把值溢出到 XMM。栈帧是显式 `pushq %rbp / movq %rsp,%rbp / subq $N,%rsp` ⇒ 当前**没有使用** SysV red zone。

**但这正是陷阱**：P2 一旦引入 linear scan，XMM 就可能成为溢出目标；一旦做"叶子函数省略帧"优化，red zone 就可能出现。**问题是在 P2 那一刻诞生的。**

> ✅ **2026-10-30 已接进版本轴**（`docs/plans/v4/version-schedule.md` § 五）:
> **v4.4.0 阶段二**（emit 层消费寄存器）**同期**加「禁 XMM 溢出 + 禁 red zone」持久断言 ——
> 否则约束会晚一版落地,而那正是它开始发作的时刻。
> ⚠️ 顺带补上一处**总纲漏项**:`决策总纲 §4` 的 P2 任务表**没有**这一条
> ⇒ 总纲比自审宽松 ⇒ 已按本修正补入。

> **修正**：这两个约束必须与 P2 的寄存器分配**同一期落地**，不能等 P2.5。而且要在 P2 之前先写一条持久断言——"**内核上下文函数不得使用 XMM 作为溢出目标；不得省略栈帧或启用 red zone**"，作为编译期上下文属性。

### 3.2 Rcu / PerCpu / 侵入式容器 —— 决定"内核能不能写出来"

第一轮原话："**做不到这一点，语言在内核里就活不下去**——Rust for Linux 至今的拉锯都在这。"

我的需求清单把它列为第 11/12 项，但**路线图里没有任何阶段承接**。这是个结构性错误：我所有的 P 阶段都在解决"内核安不安全"，**没有一个阶段在解决"内核能不能用这门语言表达出来"**。

> **修正**：新增 **P4c 内核数据结构原语**。
>
> 关键判断：它与 capability **正交**（不依赖 `Cap<T,R>` 类型化），所以**不必等到 P4b**，可以与 P3 并行。它主要是类型系统工作 + 少量 codegen（`PerCpu<T>` 需 `gs:` 段寻址）。

### 3.3 效果系统排期 —— 我压低了自己称"最高价值"的东西

第一轮称效果系统为"最高价值项"，我排到了 P3.5（依赖 P3 的函数类型与闭包）。这个依赖链**是真的**，但我低估了一件事：

**"穷人版"效果系统不需要等。** 只做两个效果 `irq_ctx` 和 `may_sleep`，机制是：

- 函数签名上写 `with { irq_ctx }` / `with { may_sleep }`
- 调用点做**直接禁止检查**（不做全推导、不做多态效果、不做效果变量）

这就足以拦住 Linux 最高频的两类 bug——`might_sleep()` 现在守的那两个位置。成本极低，不需要块表达式或 `fn` 类型。

> **修正**：在 P2.5 之后插入 **P2.75 效果最小集**（仅 `irq_ctx` + `may_sleep` + 直接禁止规则），完整效果系统仍留 P3.5。

## §4 外挂工具 → 语言内化对照表

这是第一轮判据的**可度量形式**。每完成一期，对着这张表数。

| 外挂工具 | 它守的规则 | JHYY 内化形态 | 阶段 | 状态 |
|---|---|---|---|---|
| **objtool** | 栈帧校验、入口契约、noinstr | 栈深度双上界 pass + `#[naked]`/interrupt 契约检查 | P0.5 / P2 | ✅ 有排期 |
| **lockdep** | 运行时锁序环检测 | 编译期锁序图 + 环检测 | P3.5 | ✅ 有排期 |

| **pahole** | 结构体布局检查 | ABI 布局哈希 + 布局差分测试 | P2.5 | ✅ 有排期 |
| **`-fstack-usage`** | 事后栈用量报告 | per-function facts → contract section | P0.5 | ✅ 有排期 |

## §5 修正后的路线图

**新增 3 个阶段**（P2.75 / P4c / P2 约束），其余不动。

| 阶段 | 变更 | 内容 | 验收门 |
|---|---|---|---|
| **P2（改）** | 加约束 | linear scan **与** 上下文寄存器约束同期：禁 XMM 溢出、禁省略栈帧/red zone | 内核上下文函数中 XMM 溢出点 = 0；red zone 使用点 = 0 |
| **P2.75（新增）** | 效果最小集 | `with { irq_ctx }` / `with { may_sleep }` + 调用点直接禁止 | `irq_ctx` 内调用 `sleep()`/`alloc()` 编译失败 |
| **P3（改）** | 加一项 | 原四项 + **结构化内联汇编**（类型化操作数、显式 clobber、效果签名） | `asm!` 块声明效果签名；clobber 未声明即报错 |
| **P3.5（改）** | 加一项 | 原有效果 + **`ptr<user>`/`ptr<kernel>` 与别名分析** | `ptr<user>` 直接解引用编译失败；`copy_from_user` 是唯一跨界通道 |
| **P4b（改）** | 加两项 | 原能力类型化 + **register block 语法** + **endpoint ABI 单一真源** | 一处 endpoint 声明生成内核侧 + client stub + dispatch 表 + 契约元数据 |
| **P4c（新增）** | 内核数据结构 | `Rcu<T>`（grace period 类型）、`PerCpu<T>`（`gs:` 寻址）、侵入式容器 | 一个内核链表 + RCU 读侧能用 JHYY 自然表达，无需 unsafe |
| **P4.5（改）** | 加一项 | 原插桩 + **per-function section / 冷热分离 / frame pointer 或 ORC** | `__init` 段可在启动后丢弃；unwind 表可被内核消费 |

### 一条贯穿性验收标准（补第一轮"人的因素"）

> **每个新特性都要回答：有经验的 C 程序员两周内能上手吗？**

设计上目前是**符合**的——8 个内置 rights 类型、无借用检查、无生命周期标注，学习曲线远低于 Rust。但这条**必须写成验收门**，否则会随着特性堆叠悄悄失守。建议直接放进语言规范的"新特性准入检查表"。

## §6 诚实的两句话

**第一句**：我第二轮发现了静默错误和 229 KiB 这些实证问题之后，注意力被完全吸走了。第一轮那张顶层清单——尤其是我自己标注为"最容易被忽略但收益最直接"的后端 pass——被我自己搁置了。**这是注意力分配的错误，不是判断的错误。**

**第二句**：但这轮审查也暴露了框架本身的问题。第一轮是以 Linux 为隐含参照系写的，Kconfig / Coccinelle / static keys 这三样是 Linux 的历史包袱产物，**JHYY 没有这些包袱是优势**。所以缺口要分两类处理：FPU/red zone/RCU/PerCpu/侵入式容器是**硬件与内核惯用法的硬约束，必须补**；Kconfig/Coccinelle/static keys 是**框架错配，应当明确写进"不做"清单并说明理由**。
