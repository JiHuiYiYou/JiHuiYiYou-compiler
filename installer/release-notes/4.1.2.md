**`jhyy --version` 从来就不存在 + 版本号自动化(单一真相源)。**
(非破坏性变更;但有一处**用户可见的行为修正** —— 以前文档/release note 让人跑一个
根本不存在的命令。)

- **`jhyy --version` 是个不存在的命令。** `main.jhyy` 的 CLI 全集只有
  `compile` / `build` / `run` / `dump` 四个子命令 + `--target=` / `--no-link` /
  `--help` 三个 flag。**没有 `--version`** ⇒ 跑它会落到 `unknown command` 分支 ⇒
  stderr 打一行 `unknown command` + **exit 1**。
  ⇒ 文档 / release note 里此前写的「`jhyy --version` → 版本号」全部改成
  **`jhyy --help` 的首行**(`jhyy compiler v<版本> (self-hosted)`)。
- **编译器的版本横幅一直是陈旧的。** 两条横幅路径各写死了一个历史版本号:
  无参数 ⇒ `v1.8.3.2`、`--help` ⇒ `v2.5.0`。现在都跟当前版本一致。
- **installer 的 EULA** 里那个「Version 1.8.3」也刷到了当前版本(它一直停在 v1.8.3)。
- **VSCode 扩展的 PATH 探测**从 `spawnSync(jhyy, ['--version'])` 改成 `['--help']`。
- **`jhyy --help` 里 `compile` / `build` 的说明以前是反的。** 实际语义是
  **`compile` = 编译 + 链接(产出 .exe)**、`build` = **只编译**(产出 .s,不链接);
  旧文案写的是「compile → .obj」+「build → compile + link to .exe」
  ⇒ 照着 help 跑 `jhyy build hello.jhyy` **拿不到 exe**(只出 hello.s)。
  ⇒ 现在 help / README / 本说明里的命令都跟实现对齐了:**要 exe 用 `jhyy compile`**。

### 顺带修掉的构建链缺陷

- **`build.ps1 bundle` 会静默复用陈旧的 MSI** ⇒ 改完编译器再打包，**装出来的
  仍是旧编译器**（两轮 MSI 的 sha256 逐字节相同）。现在改成「MSI 不存在 **或**
  有输入比它新 ⇒ 重建」，并打印是哪一项比它新。CI 不受影响（fresh checkout
  一定重建），但本地发版前验证产物那一环每次都踩。

### 版本号从此不再手改

版本号此前散在 **6 个地方、3 种格式**,手改必漏一处 —— 而漏了的后果都一样:
**tag 上写着 v4.1.2,装出来的编译器自报 v4.1.1**。

现在:

- `VERSION` 文件是**唯一真相源**;
- `python scripts/dev/bump_version.py set 4.1.2` **一条命令**刷全仓
  (编译器横幅字面量 / EULA / scoop manifest / winget manifest 目录名 + 3 个 yaml /
  changelog 段);
- `python scripts/dev/bump_version.py finalize` 在产物出来后回填 sha256;
- `python scripts/dev/bump_version.py check` 是**零漂移门** —— CI 里跑,
  任何一处版本串跟 `VERSION` 不符就翻红;
- **release.yml 在构建之前**断言 `VERSION` == tag(不符 ⇒ 直接拒发)。

### 上一版(v4.1.1)的要点:VSCode 终端 profile 探测真实 bash

VSCode 自带的 `bash (MSYS2)` profile 路径是**写死**的(`C:\msys64\usr\bin\bash.exe`)
**且不会回落到别的 bash** ⇒ MSYS2 装在别处的用户、或只有 Git for Windows 的用户,
会看到 "the terminal profile is not available"。现在改为写自己的 `bash (JHYY)` profile,
指向**探测到的** bash:`$env:MSYS2_ROOT` → `C:\msys64` → MSYS2 注册表的
`InstallLocation` → Git for Windows → PATH。**探测不到就什么都不改**(终端用
PowerShell 完全正常,`jhyy.exe` 本来就在系统 PATH 上)。
另新增 `jhyy-bash.cmd`(装到 `C:\Program Files\JHYY\bin\`):自己找 bash 并启动,
顺带把 `JHYY\bin` 塞进 PATH 并设 `MSYS2_PATH_TYPE=inherit`。

### 再上一版(v4.1.0)的要点:installer 自带工具链

**installer 自带工具链** —— 从 v4.1.0 起,装机用户**不需要 MSYS2** 也能编译 `.jhyy`。

之前 MSI 里有 `<Launch Condition="Installed OR MSYS2_GCC_FOUND">` + 4 路 MSYS2 探测
⇒ **没装 MSYS2 的机器根本装不上这个编译器**;装上了的人用的也是**他自己那份** gcc
⇒ 版本不受控,且「PATH 顺序 ⇒ 链接失败且 stderr 零输出」那个坑照样发作。

- **内置一份最小原生 MSYS2 ucrt64 工具链**(gcc + binutils + CRT + 编译器自用的头文件
  闭包)⇒ MSI ~28 MB、installer.exe ~55 MB。
- **默认用内置那份**:解析顺序 `JHY_GCC` → `%JHYY_HOME%\env.txt` → **内置** →
  `C:\msys64` → PATH → 裸 `gcc` ⇒ 确定性 + 版本受控 + **不依赖用户 PATH 形态**。
- **两条护栏**:链接失败时必打一行 `using gcc: <path> (source: bundled|JHY_GCC|env.txt|
  msys2|PATH)`(解析结果**可见**);installer **不**代写 `env.txt`(留给用户显式覆盖)。
- **预编 `.o`**:随包发 `runtime.o` / `jhyy_helpers.o` ⇒ 每次链接 5045 ms → **531 ms**。
- **TMP 护栏**:spawn gcc 前补 `TMP`/`TEMP`/`TMPDIR`(gcc 在这三个全 unset 时把中间
  产物写到 cwd ⇒ 只读目录下链接失败)。
- **拆门槛**:删掉 MSI 的 LaunchCondition 与 4 路 MSYS2 探测。
- **合规**:随包发各包许可证原文 + `SOURCES.txt`(实际装着的包版本 + 上游源码获取方式)。
- **6 条常驻门**(可重定位 / 头闭包 / poisoned PATH / 无 PATH / windres / 预编 `.o`
  字节一致)⇒ 在 gcc 15.2.0 与 gcc 16.2.0 上都 6/6 PASS。
  (DLL 闭包属于**采集**阶段 —— `collect-toolchain.ps1` 扫 import table 自动求闭包 ——
  **不是**一道门。门清单见 `installer/toolchain/README.md`。)

> ⚠️ **v4.1.0 的破坏性变更**:默认 gcc 从「你自己机器上的 MSYS2」变成「内置那份」。
> 想用回自己的:`JHY_GCC=<gcc.exe 全路径>` 或在 `%JHYY_HOME%\env.txt` 里写一行
> `JHY_GCC=<gcc.exe 全路径>`。
